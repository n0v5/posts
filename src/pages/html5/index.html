Part 0 · Orientation

导言：先建立判断标准

HTML5 不是一组需要背诵的标签，而是一套关于文档、样式、脚本、媒体、网络与设备的浏览器契约。AI 时代没有改变这套契约，只是让“结构是否清晰、接口是否稳定、权限是否克制”变得更值钱。

0.1 什么是“HTML5”：从 2014 规范到 HTML Living Standard

今天说“HTML5”，通常指的不是 2014 年那个一次性发布的规范，而是持续演进的 HTML Living Standard，再加上浏览器周边的一整套 Web 平台 API：Canvas、Web Storage、WebSocket、媒体元素、Web Workers、Geolocation、WebRTC、WebGPU 等。它们共享同一个运行环境、同一套安全模型和同一种渐进增强哲学。

理解这一点很重要：本页不会把知识切成“HTML5 标签”和“别的 API”两半，而是按能力域组织。你在做产品时面对的不是规范章节，而是一个具体问题：怎样让表单被 Agent 正确填写？怎样让视频字幕可访问？怎样把推理移出主线程？

它不是一套必须全部启用的功能清单；不是“用了 <section> 就语义化”的标签游戏；也不是某个框架的替代品。
它是浏览器与开发者之间的稳定契约：文档结构、交互、媒体、网络、存储、设备权限与安全边界。

本页的兼容性说明统一采用运行时特性检测，不写死版本号。规范与浏览器实现会变化，唯一可靠的判断方式是：if ('api' in navigator)，然后为不可用的情况设计降级。

0.2 AI 时代的 Web：六条判断标准

AI 生成界面、Agent 操作网页、浏览器内置模型，正在改变“网页给谁看、由谁操作”。但越是这样，越需要回到 Web 的基本面。下面六条可以作为你评估任何前端方案的尺子。

1. 语义优先标题、landmark、label、可访问名称是机器和人都能读的接口。不要用 div 模拟一切。
2. 渐进增强先保证无 JS、弱网、旧浏览器可用，再叠加交互；不要让核心内容依赖单个 API。
3. 可访问性键盘、屏幕阅读器、减少动效、对比度不是加分项，而是 Agent 与人共享的导航层。
4. 本地优先能在设备上完成的，不要上传；能缓存的，不要每次请求。隐私与延迟通常同向。
5. 可组合用标准元素、标准事件和清晰 DOM 契约组合能力，而不是把一切封进黑盒组件。
6. 可验证特性检测、能力标签、降级路径、明确错误。AI 生成的代码尤其需要可验证的边界。
AI 视角：LLM 与 Agent 不理解你的设计系统，但能理解 <main>、<label for>、name、aria-label、JSON-LD 和稳定的 DOM。语义化不是“给 SEO 看的”，而是给人类与机器共同使用的公共接口。

Part 1 · Document & Semantics

文档与语义：先让页面“可被理解”

视觉层可以重做，语义层一旦腐烂就会持续付出代价。这一部分从文档骨架讲到 landmark、表格、可访问性与 Agent 可读性，目标是让页面在没有 CSS、没有 JS、甚至被自动化工具解析时仍然成立。

1.1 文档骨架与 <head>

一份可靠的 HTML 文档从五个声明开始：doctype、lang、charset、viewport 和 title。它们分别告诉浏览器：使用标准模式、页面语言、字符编码、移动端视口策略，以及这个页面是什么。缺少任何一项，后续的排版、SEO 或可访问性都会受到影响。

html最小但完整的文档头
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>页面标题：具体、可区分</title>
  <meta name="description" content="一句话说明页面内容">
  <link rel="canonical" href="https://example.com/page/">
  <meta property="og:title" content="页面标题">
  <meta property="og:type" content="article">
</head>
<body>
  <main>…</main>
</body>
</html>

几个常见误区：把 viewport 写成 user-scalable=no（阻止缩放，伤害可访问性）；用同一段标题描述所有页面；把重要内容塞进 <div> 而忽略 landmark；忘记 lang 导致屏幕阅读器用错发音。

AI 视角：标题、描述、canonical、结构化数据是检索与 Agent 理解页面的第一层信号。AI 生成的页面如果只追求视觉，往往在这一层最先失守。

1.2 语义元素与文档大纲

语义元素的价值不在“看起来更专业”，而在于它们给浏览器、辅助技术和自动化工具提供了可依赖的角色。<header>、<nav>、<main>、<article>、<section>、<aside>、<footer> 构成地标；<h1>–<h6> 构成大纲；<figure>/<figcaption>、<time>、<address>、<mark> 提供额外语义。

html一个文章页的语义骨架
<body>
  <header>
    <a href="/">站点名</a>
    <nav aria-label="主导航">…</nav>
  </header>
  <main id="main">
    <article>
      <header>
        <h1>文章标题</h1>
        <time datetime="2026-10-27">2026 年 10 月 27 日</time>
      </header>
      <section aria-labelledby="section-1">
        <h2 id="section-1">小节标题</h2>
        <p>正文…</p>
      </section>
      <figure>
        <img src="diagram.svg" alt="描述图中信息的替代文本">
        <figcaption>图 1：说明</figcaption>
      </figure>
    </article>
  </main>
  <footer>…</footer>
</body>

不要为了“有语义”而堆 <section>：每个 section 应有可命名的标题。地标也不要重复：一个页面通常只有一个 <main>。标题层级按结构递进，而不是按字号选择。

点击按钮，查看本页的标题层级与地标结构。
AI 视角：Agent 常用的页面解析策略就是读取标题树与地标。一个结构清晰的页面，等于给自动化工具提供了一张免费的地图。

1.3 链接、图像与嵌入

链接要表达“去哪里”，而不是“点这里”。图片必须有 alt：信息性图片描述信息，装饰性图片留空；复杂图表应同时提供文字说明。<picture> 与 <source> 让浏览器按格式/媒体条件选择资源；loading="lazy" 推迟离屏图片加载，但不能滥用——首屏关键图不要懒加载。

html响应式图片与安全嵌入
<picture>
  <source srcset="hero.avif" type="image/avif">
  <source srcset="hero.webp" type="image/webp">
  <img src="hero.jpg" alt="一张描述具体内容的图" width="1200" height="630" loading="lazy">
</picture>

<iframe
  src="https://example.com/embed"
  title="嵌入内容的具体名称"
  loading="lazy"
  sandbox="allow-scripts allow-same-origin"
  referrerpolicy="strict-origin-when-cross-origin">
</iframe>

嵌入第三方内容时，sandbox 与 allow 是最小权限原则的第一道门；不要因为“能跑”就授予全部权限。图片设置宽高可以避免布局偏移（CLS），这也是 Core Web Vitals 的一部分。

1.4 表格与数据语义

表格只用于二维数据，不用于页面布局。<caption> 给表格命名，<th scope> 建立表头与单元格的关系，<thead>/<tbody> 让结构更清晰。移动端可用 overflow-x: auto 包裹，而不是把表格压扁。

html可访问的数据表
<table>
  <caption>2026 年浏览器能力支持概览</caption>
  <thead>
    <tr><th scope="col">能力</th><th scope="col">状态</th></tr>
  </thead>
  <tbody>
    <tr><th scope="row">WebGPU</th><td>逐步可用</td></tr>
    <tr><th scope="row">WebMCP</th><td>实验性</td></tr>
  </tbody>
</table>

数据语义还包括 <time datetime>、<data value>、<meter>。把“人类可读文本”和“机器可读值”同时给出，是 AI 时代最划算的习惯之一。

1.5 可访问性：不是附加项，而是接口

可访问性的核心是：所有用户都能通过不同输入方式完成同一件事。最小检查清单：键盘可达、焦点可见、表单有 label、错误信息可被朗读、图片有 alt、对比度达到 AA、动画尊重 prefers-reduced-motion。

  • 地标与跳转：提供 skip link，<main> 唯一，导航有 aria-label。
  • 动态内容：用 aria-live="polite" 播报结果，但不要逐帧播报；节流或只在结束时更新。
  • 焦点管理：打开 dialog 后焦点进入对话框，关闭后回到触发按钮；背景使用 inert。
  • 对比与动效：不要只靠颜色表达状态；支持减少动效与高对比度偏好。
AI 视角：可访问名称（accessible name）是自动化工具识别控件的关键。按钮只有图标、链接只有“点这里”，对人可能勉强可用，对 Agent 则等于不可解析。

1.6 Agent 可读性：让页面成为可解析的接口

“Agent 可读”不是给页面加一句“欢迎 AI 抓取”。它意味着：结构可解析、内容可提取、操作可定位、状态可验证。具体做法包括语义化 DOM、稳定的 id/name/data-* 契约、完整表单标签、JSON-LD、llms.txt 与可下载的原始数据。

html机器可读的页面声明
<main id="main">
  <article itemscope itemtype="https://schema.org/TechArticle">
    <h1 itemprop="headline">AI 时代的 HTML5 超级大全</h1>
    <time itemprop="datePublished" datetime="2026-10-27">2026-10-27</time>
    <section id="forms" aria-labelledby="forms-title">
      <h2 id="forms-title">表单</h2>
      <form action="/subscribe" method="post">
        <label for="email">邮箱</label>
        <input id="email" name="email" type="email" autocomplete="email" required>
        <button type="submit">订阅</button>
      </form>
    </section>
  </article>
</main>

更进一步，为页面提供 llms.txt（站点索引）、feed.json（文章原始内容）和 JSON-LD（结构化元数据）。对本页来说，你可以直接下载单文件 HTML；对博客文章来说，源码页就是最直接的机器可读入口。

编辑 JSON-LD 后点击解析。
AI 视角：AI 时代的“可读性”有两层：人类读者能读懂，自动化系统也能以低成本解析。语义 HTML、稳定契约与结构化数据，是同一件事的三个层次。本页的 Agent 可读契约 会给出可操作的清单。

Part 2 · Forms & Interaction

表单与交互：最被低估的 Web 能力

表单是人与系统之间最古老的接口，也是 Agent 最容易操作的接口。原生表单、校验、dialog、文件与剪贴板，能用几十行 HTML 完成很多框架组件才能做到的事。

2.1 表单与输入类型

表单的第一原则是：让浏览器知道你在收集什么。正确的 type、name、autocomplete、inputmode 会直接改善移动端键盘、密码管理器、自动填充和无障碍体验。把一个邮箱输入框写成 type="text"，等于把这些能力全部放弃。

常用类型email、url、tel、number、range、date、time、color、file、search。
关键属性name（提交键）、autocomplete、required、pattern、minlength、inputmode、enterkeyhint。
html一个对人和机器都友好的表单
<form action="/subscribe" method="post">
  <label for="email">邮箱</label>
  <input id="email" name="email" type="email"
         autocomplete="email" required
         aria-describedby="email-hint">
  <p id="email-hint">用于接收更新，不用于营销。</p>

  <label for="topic">关注主题</label>
  <select id="topic" name="topic">
    <option value="html">HTML</option>
    <option value="ai">AI 与 Web</option>
  </select>

  <button type="submit">订阅</button>
</form>

别忘了 <fieldset>/<legend>：当一组控件共同回答一个问题时，它们不是孤立的输入框。单选组、地址组、支付方式组都适用。

2.2 原生校验与 Constraint Validation API

浏览器已经内置了必填、类型、长度、范围、pattern 等约束。你可以用 :user-invalid 做“用户交互后才显示”的错误样式，用 form.reportValidity() 触发原生提示，用 setCustomValidity() 补充业务规则。

js用 ValidityState 给出可读的错误
const form = document.querySelector('#signup');
const email = form.elements.email;

form.addEventListener('submit', (event) => {
  if (!form.checkValidity()) {
    event.preventDefault();
    if (email.validity.typeMismatch) {
      email.setCustomValidity('请输入有效的邮箱地址');
    }
    form.reportValidity();
  }
});

email.addEventListener('input', () => email.setCustomValidity(''));

原生校验不是安全边界：客户端校验永远可以被绕过。服务端仍然必须校验。但对可用性来说，浏览器提示是最快、最一致的反馈来源。

2.3 控件、输出与状态

HTML 还有一批常被忽略的原生控件：<datalist>（输入建议）、<output>（计算结果）、<progress>（任务进度）、<meter>（已知范围的度量）。它们自带语义，屏幕阅读器能理解，比用 div 拼出来的“假进度条”可靠得多。

html原生状态控件
<label for="city">城市</label>
<input id="city" name="city" list="cities">
<datalist id="cities">
  <option value="上海">
  <option value="北京">
</datalist>

<label for="volume">音量</label>
<meter id="volume" min="0" max="100" low="30" high="80" optimum="60">65</meter>

<progress id="upload" max="100" value="42">42%</progress>
<output id="result" for="a b">0</output>

这些元素的视觉样式有限，但可以通过 CSS 定制；优先保留原生语义，再做外观。对于动态进度，记得同时更新文本值，不要只改变颜色或宽度。

2.4 dialog、popover 与 details

原生 <dialog> 负责模态/非模态对话框，自带焦点陷阱与 Esc 关闭；Popover API 负责轻量浮层（菜单、提示、选择器）；<details>/<summary> 负责无 JS 可用的折叠内容。三者覆盖了大部分“组件库弹层需求”。

html原生 dialog 与 popover
<button commandfor="confirm" command="show-modal">删除</button>
<dialog id="confirm" aria-labelledby="confirm-title">
  <h2 id="confirm-title">确认删除？</h2>
  <form method="dialog">
    <button value="cancel">取消</button>
    <button value="delete">删除</button>
  </form>
</dialog>

<button popovertarget="menu">打开菜单</button>
<div id="menu" popover>…</div>

现代浏览器支持 commandfor/command（声明式 dialog 控制）；不支持时用一行 JS 的 showModal()。打开模态后，背景应使用 inert 不可交互；关闭后把焦点还给触发按钮。

AI 视角：原生 dialog/popover 会给辅助技术正确的角色和焦点行为。用 div 手搓弹层时，Agent 往往无法判断“现在是不是一个需要处理的模态状态”。

2.5 文件、拖放、剪贴板与分享

File API 让浏览器读取用户选择的文件；拖放事件扩展了输入方式；Clipboard API 提供异步复制/粘贴；Web Share 调用系统分享面板。它们都需要用户手势或明确授权，且多数要求安全上下文（HTTPS 或 localhost）。

js文件拖放与剪贴板
dropzone.addEventListener('dragover', (event) => {
  event.preventDefault();
  dropzone.classList.add('is-over');
});

dropzone.addEventListener('drop', (event) => {
  event.preventDefault();
  const [file] = event.dataTransfer.files;
  console.log(file.name, file.size, file.type);
});

copyButton.addEventListener('click', async () => {
  await navigator.clipboard.writeText('要复制的内容');

Part 5 · Storage & Offline

存储与离线：把数据留在用户身边

Cookie、Web Storage、IndexedDB、Cache API、OPFS 各有边界。选错存储会带来配额、性能、隐私或同步问题；选对了，才能做真正的 local-first 页面、离线可用与本地模型缓存。

5.1 Cookie、Web Storage、配额与分区

Part 6 · Network & Realtime

AI 产品的“打字机效果”不是 UI 特效，而是流式网络的可见结果。理解 fetch、Streams、SSE、WebSocket 的边界，才能做出可取消、可重试、可降级的实时界面。

6.2 Streams 与流式 UI

Streams API 把数据视为可读的分块序列。你可以用 response.body.getReader() 逐块消费，也可以构造 ReadableStream 把本地数据变成流。AI 聊天、日志、导出大文件都适合流式处理：尽早显示、可取消、内存占用低。

js逐块读取响应
const response = await fetch('/api/stream');
const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  output.textContent += decoder.decode(value, { stream: true });
}

Part 7 · Workers & Performance

Worker 与性能：别让主线程做所有事

主线程同时负责渲染、输入、脚本和布局。把计算、解析、AI 推理移出主线程，是保持交互流畅的核心手段。这一部分从 Web Worker 讲到 Service Worker、调度 API 与性能观测。

7.2 Service Worker 与缓存策略

Service Worker 是拦截网络请求的代理，运行在浏览器后台。它可以做离线缓存、离线导航回退、资源预缓存、后台同步与推送。它是 PWA 的核心，但生命周期复杂：安装、等待、激活、fetch 事件、更新。单文件页面无法注册内联 Service Worker，本节只讲策略与代码。

js缓存优先 + 网络回退
self.addEventListener('fetch', (event) => {
  if (event.request.method !== 'GET') return;
  event.respondWith((async () => {
    const cache = await caches.open('guide-v1');
    const cached = await cache.match(event.request);
    if (cached) return cached;
    const response = await fetch(event.request);
    if (response.ok) cache.put(event.request, response.clone());
    return response;
  })());
});

更新策略要明确：skipWaiting() + clients.claim() 会让新版本立即接管，但可能导致旧页面拿到不兼容资源；更稳妥的是提示用户刷新。缓存版本号必须随发布更新。

7.3 调度与空闲：scheduler、requestIdleCallback、MessageChannel

并非所有任务都应立即执行。优先级高的用户输入要抢占；低优先级的日志、预计算可以放到空闲时间。scheduler.postTask() 提供优先级与取消；requestIdleCallback 在空闲帧执行低优先级任务；MessageChannel 可以避免 setTimeout(0) 的嵌套延迟。

Part 8 · Devices, Security & Privacy

设备、安全与隐私：能力越大，边界越重要

浏览器能访问摄像头、位置、文件、USB、蓝牙、支付与生物识别。每一项能力都伴随权限、隐私与安全风险。AI Agent 参与操作后，权限边界不再只是“用户点不点允许”，而是“谁代表用户、能做什么、如何审计”。

8.1 设备能力与权限模型

Web 权限大致分三类：用户手势触发（摄像头、麦克风、分享）、显式授权（地理位置、通知、持久存储）、策略控制（Permissions Policy、iframe allow）。权限请求必须发生在用户手势中，并且先解释用途；被拒绝后要有替代路径。

js查询权限状态与请求地理定位
const status = await navigator.permissions.query({ name: 'geolocation' });

  (error) => console.log(error.message),
  { enableHighAccuracy: false, timeout: 8000 }

不是所有权限都能通过 Permissions API 查询；以实际调用结果为准。权限状态可能随时改变，不要把它缓存成永久结论。

8.2 位置、摄像头、麦克风与屏幕捕获

8.6 安全：同源、CORS、CSP、Trusted Types、SRI 与沙箱

Web 安全的第一原则是不信任输入。XSS 来自把不可信字符串当 HTML；CSRF 来自浏览器自动携带凭据；点击劫持来自被嵌入 iframe。防线的组合是：输出编码、CSP、Trusted Types、SameSite Cookie、CSRF Token、SRI、iframe sandbox、Permissions Policy。

CSP限制脚本/样式/图片来源；尽量避免 unsafe-inline；用 nonce/hash 管理内联脚本。
Trusted Types把危险 DOM 赋值集中到受控策略，减少 DOM XSS 面。
SRI为第三方脚本/样式加完整性哈希，防止 CDN 被篡改。
sandbox嵌入不可信内容时使用最小权限 iframe，不要随意加 allow-scripts allow-same-origin。
html用 CSP 限制能力
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self' 'nonce-abc123';
               style-src 'self' 'unsafe-inline'; img-src 'self' data:;
               connect-src 'self'; frame-ancestors 'none'">

静态页面没有服务端，很多安全头只能由托管平台配置。GitHub Pages 对自定义响应头支持有限；更强的 CSP 需要反向代理或支持 headers 的托管服务。

8.7 隐私：分区、指纹面与数据最小化

现代浏览器通过存储分区、第三方 Cookie 限制、权限策略、反指纹措施降低跨站追踪。作为开发者，应默认数据最小化：不采集不需要的数据，不把敏感信息写进 URL/localStorage，不在客户端日志中输出个人信息，不上传未经用户同意的媒体。

  • 存储分区：同一第三方源在不同顶级站点下可能拥有隔离存储；不要假设跨站共享。
  • 指纹面：Canvas、WebGL、字体、设备信息都可能被组合成指纹；安全场景需评估。
  • 权限策略：用 Permissions Policy 限制 iframe 能使用哪些强能力。
  • 数据生命周期：明确收集目的、保存期限、删除方式；给出导出/清除入口。
AI 视角：Agent 代表用户操作时，权限最小化与审计日志比“能不能自动化”更重要。任何页面都不应该把“AI 可以读取/点击”误解为“AI 有权读取/点击”。

9.5 AI 生成 UI 与人类监督

AI 生成界面很快，但“能运行”不等于“可交付”。生成后的界面至少要过五关：语义结构、键盘可访问性、错误与空状态、响应式布局、真实数据边界。把 AI 当作快速起草工具，把自动化测试、Lint、可访问性检查与人工评审当作发布门槛。

  • 可验证：关键交互要有确定性测试，不依赖“看起来对”。
  • 可回滚：AI 生成的大改动用小步提交，保留可回退路径。
  • 可解释：用户需要知道哪些内容是 AI 生成的、依据是什么、能否纠正。
  • 可访问：生成器必须输出 label、alt、焦点管理和对比度达标的样式。
AI 视角：AI 时代最稀缺的不是“生成页面的能力”，而是“判断页面是否可信、可用、可维护”的能力。后者仍然是工程问题。

9.7 Agent 安全：prompt injection、工具权限与沙箱

当 Agent 读取网页内容时，网页中的文字可能成为指令（prompt injection）；当 Agent 能调用工具时，一次越权就可能造成真实损害。防护原则：把外部内容当数据，不当指令；工具默认最小权限；高风险操作需要人类确认；限制网络出口；记录审计日志；对输入做隔离与标记。

内容隔离把网页文本放在明确的“不可信数据”边界内，不让它混入系统提示。
工具白名单只暴露完成任务所需的最小工具集；默认拒绝未知工具。
人类确认发送邮件、支付、删除、授权等不可逆操作必须二次确认。
审计与回滚记录谁在何时做了什么；提供撤销与隔离能力。

页面的责任是把可执行动作与数据边界说清楚；Agent 平台的责任是执行权限与确认；用户的责任是理解授权范围。三者不能互相替代。

9.8 现在采用 vs 观望

不是所有“AI 时代”的能力都值得马上上生产。下面是一张务实的分流表。

现在就该用语义化、可访问性、原生表单、fetch/streams、IndexedDB、Worker、CSP、权限最小化、llms.txt/feed.json。
可用但需降级View Transitions、WebGPU、OPFS、Web Share、Media Session、WebSocket/SSE（需服务端）、WebAuthn。
实验/观望WebMCP、Prompt API/内置 AI、WebNN、WebTransport、WebXR、WebUSB/蓝牙等硬件 API。
不要假装没有服务端却演示真实实时连接；没有权限却声称“全自动”；用模拟数据冒充模型输出。
结论：AI 时代最可靠的策略不是追逐每一个新 API，而是把语义、渐进增强、可访问性、性能与安全做到位。它们才是模型、Agent 与人类共同依赖的地基。

C. 术语表

  • Living Standard：持续更新的 HTML 规范，而不是一次性冻结的版本。
  • 渐进增强：先提供基础可用版本，再为支持更强能力的浏览器叠加体验。
  • 特性检测：运行时判断 API 是否存在/可用，而不是猜测浏览器版本。
  • 可访问名称：辅助技术与自动化工具用来识别控件的名称，来自 label、aria-label、文本内容等。
  • 安全上下文：HTTPS 或 localhost 等被视为安全的环境；许多强能力 API 只在此环境开放。
  • local-first：数据优先保存在本地，网络是同步/协作的补充而非前提。
  • prompt injection：把恶意指令藏在模型读取的内容里，诱导模型执行非预期操作。
  • Agent 可读契约：页面以稳定语义、结构、名称与数据出口向自动化工具描述自身。
