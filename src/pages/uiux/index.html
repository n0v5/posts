Part 0 · Orientation

导言：界面是意图与实现之间的契约

UI/UX 不是“把东西画好看”，而是把用户意图翻译成结构、状态、语义和可验证的行为。AI 能快速生成界面，但前提是你能把需求说清楚。这一部分先建立全页的判断标准，再用 Flutter 作为参考实现。

0.1 为什么工程师要学 UI/UX

工程师每天都在做 UX 决策：字段顺序、错误提示、加载状态、按钮位置。区别只在于这些决策是显式的，还是碰巧发生的。

一个界面能否用，取决于三件事：用户是否知道下一步做什么（可供性/意符）、操作后是否得到反馈（系统状态可见）、出错时是否能恢复（错误预防与恢复）。这三件事与使用什么框架无关；Flutter、Web、桌面 UI 只是不同的实现介质。AI 时代的变化是：生成界面的成本下降了，但“说清楚要生成什么”的成本上升了。能准确描述结构、状态、约束和验收标准的人，会得到更可用的结果。

Structure信息放在哪里？层级、分组、布局约束是什么？
Style用什么 token、字号、色彩角色、表面与动效？
State有哪些状态？数据从哪来、谁拥有、如何变化？
Semantics控件叫什么、焦点怎么走、错误如何被读出？
需求描述示例

When 设备任务失败时，用户能看到失败原因和一个明确的重试入口；Then 重试中按钮进入 loading 且不可重复提交，成功后列表状态更新。

这段描述同时约束了结构、状态和语义，比“做一个好看的任务列表”更能指导实现。

底层原理可用性不是单一属性，而是“用户目标—界面结构—系统反馈”三者匹配的结果。Nielsen 的十条启发式、WCAG 的 POUR 原则、Material 3 的 state layer，本质上都在回答同一组问题：现在发生了什么、我能做什么、做错了怎么办。
常见坑
  • 把 UI/UX 等同于视觉美化，忽略状态、错误与边界。
  • 先写组件再想用户任务，导致界面结构服务实现而不是服务目标。
  • 用“高级、简洁、现代”这类形容词代替具体约束；AI 无法从这些词推断字号、间距和状态。

0.2 从 Flutter 出发，但不学成 Flutter 教程

Flutter 是参考实现，不是课程主体，也不是这个页面的运行时。你学的是“界面如何被组织”，Flutter 只是让这些组织方式可见、可验证。

Flutter 适合做范例：声明式 UI 让“界面是状态的函数”非常直观；Widget 树、约束布局、ThemeData、Semantics 都能直接观察；Material 3 提供了成熟的 color roles、type scale 和 state layer。博客已有 Dart 指南，本机也有 Flutter 3.47.7，可以把页面里的代码真正跑一遍。它不适合做运行时演示：单文件离线页面无法内嵌 Flutter Web，构建产物大且多文件，会破坏零外部依赖。

底层原理声明式 UI 把“界面长什么样”描述为状态的函数；命令式 UI 则通过一系列修改指令改变控件。Flutter、SwiftUI、Compose、React 更接近前者，传统桌面控件库更接近后者。无论哪种，最终都要落到树结构、布局约束、状态和语义四件事。
常见坑
  • 把 Flutter 的 Widget 名称当成通用概念；换框架后名称全变，但“树/约束/状态/语义”的问题不变。

  • 把“响应式”理解成“缩小版桌面布局”；应该重新安排信息优先级。

Part 1 · Users, Tasks & Requirements

用户、任务与需求：先决定为谁解决什么问题

界面不是从组件开始的，而是从用户任务开始的。这一部分把“用户想要什么”拆成目标、任务、内容、流程和边界，最后落成可验证的需求描述。

1.1 用户、目标与场景

先写清楚“谁、在什么场景、想完成什么”，再决定界面上放什么。

同一句“设备任务面板”，对现场运维、远程支持和管理员意味着不同任务：运维关心快速定位失败设备，支持关心重现问题，管理员关心批量策略。用户画像不是虚构人物小传，而是把关键差异写成可检验的约束：设备数量、网络稳定性、操作频率、权限、领域词汇。

现场运维手机/平板，弱网，单手操作；需要大触控目标、离线提示、快速重试。
远程支持桌面，多窗口；需要日志、复制错误码、批量筛选。
管理员桌面，低频高风险；需要确认对话框、审计信息、权限说明。

同一界面的三种场景：不是做三套 UI，而是确定优先级和必须支持的路径。

需求描述示例

主要用户是弱网环境下的现场运维；首屏必须能在 375px 宽度下完成“找到失败任务并重试”，不要求横向滚动。

底层原理用户目标决定信息优先级；场景决定输入方式、屏幕尺寸、网络与注意力预算。把这些写成约束，后续的布局、状态和验收才有依据。
常见坑
  • 用“所有用户”代替具体用户，导致所有功能都重要。
  • 只写 happy path，不写弱网、权限不足、空数据。
  • 把用户研究做成一次性访谈，不把结论转成可验证的约束。

1.2 任务分解与 JTBD

把“使用产品”拆成用户要完成的具体任务；任务是界面结构的来源。

JTBD（Jobs to be Done）关注“用户想取得什么进展”，而不是“用户点了哪个按钮”。对设备任务面板，核心任务可以拆成：发现异常 → 判断影响 → 采取动作 → 确认结果 → 记录/升级。每个任务再拆成步骤、输入、输出和失败分支。界面结构应该让主任务最短，次要任务可发现但不抢注意力。

发现异常 ├─ 扫描列表 / 筛选状态 ├─ 打开任务详情 └─ 判断影响范围 采取动作 ├─ 重试 ├─ 取消 └─ 查看日志 确认结果 ├─ 成功反馈 ├─ 失败原因 └─ 下一步建议

任务树先于组件树：先确定用户要走的路径，再决定每条路径需要哪些组件。

验收标准

Given 列表中存在失败任务，When 用户打开详情，Then 首屏同时可见失败原因和重试按钮，且重试不需要先展开菜单。

底层原理任务是用户目标与界面动作之间的中间层。任务分解能暴露缺失的输入、隐藏的分支和多余步骤；组件只有在服务某个任务步骤时才应该存在。
常见坑
  • 按数据库表/API 设计界面，而不是按用户任务。
  • 主任务被次要功能挤到首屏之外。
  • 忽略失败分支，导致错误状态没有入口。

1.3 信息架构与内容优先

先决定内容与层级，再决定视觉；内容清单是布局的原料。

信息架构（IA）回答：有哪些内容、如何分组、用什么名字、层级多深。内容优先意味着先写真实文案和字段，不用 Lorem ipsum；真实内容会暴露长度、术语和优先级问题。任务面板的内容可以分成：身份（设备/任务）、状态、时间、影响、动作、诊断。每个字段都要问“用户在当前任务里需不需要它”。

设备任务面板 ├─ 概览：失败数 / 运行中 / 队列 ├─ 任务列表：名称 · 设备 · 状态 · 时间 ├─ 任务详情：错误原因 · 日志 · 重试 └─ 设置：自动重试 · 通知 · 权限

IA 树不是页面路由；它同时约束导航、标题层级和内容优先级。

内容清单示例

列表项必须包含：任务名、设备 ID、状态、最近更新时间；详情必须包含：失败原因、最后错误码、可执行动作。没有这些字段的状态不算“可操作”。

底层原理信息架构通过分组与命名降低认知负荷；标题层级和地标也让辅助技术能建立同一张地图。内容优先能避免“先画骨架再塞文字”导致的溢出与返工。
常见坑
  • 用开发术语命名用户可见内容。
  • 层级过深，主任务需要三次以上点击。
  • 忽略空状态、错误状态和权限状态的内容设计。

1.4 用户流、分支与边界情况

主流程只占体验的一小部分；分支、失败和恢复才决定界面是否可靠。

用户流把任务树变成可执行路径：起点、决策点、动作、反馈、退出。每条主路径至少配三种边界：空数据、失败、权限不足。对重试任务，还要考虑重复提交、超时、任务已取消、设备离线。把这些写进状态清单，界面实现时就不会只做 happy path。

打开面板 ├─ 有失败任务 → 详情 → 重试 │ ├─ 成功 → 状态更新 → 列表刷新 │ ├─ 失败 → 错误原因 + 再次重试 │ └─ 超时 → 解释 + 查看日志 ├─ 无任务 → 空状态 + 创建/刷新 └─ 无权限 → 说明原因 + 申请入口

流程图不需要画得很漂亮；它需要把“用户下一步能做什么”写全。

验收标准

Given 设备离线，When 用户点击重试，Then 界面说明“设备离线，恢复后会自动重试”，并提供查看日志；不得只显示“操作失败”。

底层原理流程是状态机的用户视角：节点是界面状态，边是动作，失败分支是例外状态。把流程写成状态清单，能直接映射到代码里的 enum/状态机和验收测试。
常见坑
  • 只画主流程，不画取消、返回和失败。
  • 错误提示只写“失败”，不说明原因和下一步。
  • 重试没有防重复提交，导致状态错乱。

Part 2 · Structure & Layout

结构与布局：让信息有位置，让空间有节奏

布局不是“把东西摆上去”，而是用树、约束、间距和对齐表达优先级。这一部分从组件树讲到响应式；所有概念都不依赖 Flutter，但会为 Act II 的 Flutter 布局做铺垫。

2.1 组件树与组合

界面是一棵树：页面由区块组成，区块由组件组成，组件由更小的元素组成。

树结构让复杂界面可管理：每个节点有明确职责，父节点负责排列，子节点负责内容。好的组件边界通常与“用户能理解的一块”对齐，而不是与数据库表或 API 响应一一对应。组件树也决定了状态归属：状态应放在需要它的最近公共父节点，而不是全部堆在根节点。

TaskPanel ├─ Header (标题 + 刷新) ├─ Summary (失败数 / 运行中 / 队列) ├─ TaskList │ └─ TaskItem (名称 / 设备 / 状态 / 时间) └─ TaskDetail ├─ ErrorExplain └─ Actions (重试 / 日志)

一棵可读的组件树：父节点负责布局，叶子节点负责内容与交互。

Structure 树边界Style 继承主题State 最近公共父节点Semantics 每棵子树有名称
底层原理树是声明式 UI 的基本数据结构：重建时比较新旧树，更新差异；布局从根向下传递约束，尺寸从叶子向上返回。组件边界越清晰，状态和布局越容易推理。
常见坑
  • 按 API 结构拆组件，导致 UI 复用困难。
  • 所有状态都放在根节点，任何变化都重建全页。
  • 组件没有单一职责，样式/状态/布局混在一起。

2.2 约束式布局

父级给子级约束（最小/最大宽高），子级选择尺寸，父级再决定位置。

约束式布局的核心是“约束向下、尺寸向上、父级定位”。这解释了很多看似奇怪的现象：为什么子组件不能无限宽、为什么 Expanded 会占满剩余空间、为什么文字换行取决于父级给的宽度。通用模型里，布局至少包含：主轴方向、尺寸策略、剩余空间分配、溢出策略。Flutter 用 BoxConstraints/Flex，Web 用 flex/grid，桌面框架用 layout manager，问题结构相似。

父级约束：0 … 720px
子级选择：480px
剩余空间：240px

约束不是“建议”；子级只能在父级给的范围内选尺寸。

2.3 网格、间距与节奏

          
间距是层级的第一语言；用一套有限的间距刻度，而不是每次临时决定。

          
常见做法是 4/8pt 基础网格：4、8、12、16、24、32、48。相邻元素用较小间距，组与组之间用较大间距；间距的差异表达关系，而不是装饰。排版节奏还包括行高、区块上下留白和页面最大宽度。间距 token 让设计、实现和 AI 生成使用同一套数值。

8 · related items

            
16 · card padding

            
32 · section gap

            
间距刻度越少，界面越一致；差异越明确，关系越容易被读懂。

          

          
间距 token
space-1=4, space-2=8, space-3=12, space-4=16, space-6=24, space-8=32；卡片内边距使用 space-4，卡片之间使用 space-3，区块之间使用 space-8。

          
底层原理邻近性原则让大脑把空间接近的元素归为一组；一致的间距刻度降低视觉噪声，也让实现更可预测。间距是布局 token 中最便宜、收益最高的部分。

          
常见坑
  • 每个组件用不同的 padding，导致视觉节奏断裂。
  • 用间距表达“重要”，结果页面到处是大空白。
  • 忽略文字行高与段落间距，只调 margin。

        


        

          
2.4 对齐、分组与邻近性

          
对齐建立秩序，分组表达关系；两者都比装饰更重要。

          
优先使用一条明确的对齐线（左对齐最常见），避免每个元素各自居中。分组可以通过间距、分隔线、背景表面或标题实现，但不要同时用三种强分组手段。表单里标签与输入框的对齐、列表里主次信息的对齐，直接影响扫视效率。对齐不是“看起来整齐”，而是让用户能快速比较同类信息。

底层原理对齐线减少眼球跳转，分组降低短期记忆负担。格式塔原则（接近、相似、连续、闭合）解释了为什么间距和边框会改变用户对关系的判断。

  • 标题居中、正文左对齐、按钮右对齐，形成多条竞争对齐线。
  • 用背景色和边框同时强调所有分组，导致噪声。
  • 状态只靠颜色区分。

        


        

          
2.5 视觉层级与扫视路径

          
用户不会逐字阅读；他们扫视标题、数字、颜色和位置。层级要服务于任务，而不是装饰。

          
视觉层级通过字号、字重、颜色、间距、位置和表面来表达优先级。一个实用测试是“眯眼测试”：模糊界面后，最先看到的是否是你希望用户先看到的信息？如果所有东西都在喊，用户就什么都看不到。对任务面板，失败状态和重试动作应该比“设备型号”更显眼；但也不能让错误色淹没整个页面。

2.6 响应式与自适应

          
响应式不是把桌面布局缩小，而是根据可用空间重新安排信息与交互。

          
先定义断点和每个断点的信息优先级：手机上先看到失败任务和重试；平板上并排列表与详情；桌面上增加批量操作和日志面板。断点不是设备型号，而是内容开始拥挤/空荡的宽度。布局切换时，保持焦点、滚动位置和状态不丢失。Flutter 用 LayoutBuilder/MediaQuery，Web 用媒体查询/容器查询，桌面框架用 layout manager，但决策逻辑相同。

  • 断点切换时丢失选中状态或滚动位置。

        

      


      

        

          
Part 3 · Visual Language

          
视觉语言：让界面可读、可辨、可信

          
视觉语言不是装饰风格，而是一套可复用的决策系统：字号、色彩角色、对比度、形状、表面和动效都应有理由。这一部分把“好看”拆成可检查的规则。

        


        

          
3.1 排版系统

          
先定字号阶梯、行高和字重，再谈字体；可读性优先于个性。

          
一个够用的排版系统通常包含 5–7 个层级：display、title、body、label、caption，加上等宽字体用于代码/数字。字号差异要明显，行高随字号减小而相对增大；正文行长控制在 45–75 个字符。字重用于建立层级，但不要在同一屏里使用过多字重。数字表格可以用等宽数字（tabular figures）避免跳动。

排版规则示例
页面标题 28/34，区块标题 20/28，正文 16/26，标签 12/16；正文最大行宽 68ch；数字列表使用等宽数字。

          
底层原理字号、行高和行长共同决定阅读节奏；过长的行让眼球回扫困难，过短的行增加换行次数。层级差异来自字号/字重/颜色的组合，而不是单一维度。

          
常见坑
  • 用 13/14/15px 这种相邻字号建立层级，差异不可见。
  • 正文行高过小，长文阅读疲劳。
  • 标题和正文使用同一字重，只靠字号区分。

        


        

          
3.2 色彩角色与语义色

          
不要直接使用“红色/蓝色”，而要定义 primary、surface、error、on-error 等角色，让颜色跟随主题。

          
角色化色彩让浅色/深色、品牌换肤和高对比度模式可以复用同一套语义。Material 3 的 color roles 是一个成熟例子：primary、on-primary、primary-container、surface、surface-variant、error、on-error 等。语义色必须与文字/图标一起使用，不能只靠颜色传达状态；错误色只用于错误，不用作品牌装饰。

角色不是颜色值本身；同一个 primary 可以在亮色/暗色/高对比度下映射到不同值。

          

          
色彩规则示例
主操作用 primary；危险操作用 error；状态标签同时包含图标/文字与颜色；禁止用 error 色表达“品牌强调”。

          
底层原理语义角色把“用途”和“具体色值”解耦，使主题切换和对比度调整不需要改业务代码。角色命名也方便 AI 生成一致的主题。

          
常见坑
  • 在业务代码里硬编码十六进制颜色。
  • 用红色表示“删除”又表示“品牌”，语义冲突。
  • 只靠颜色区分成功/失败。

        


        

          
3.3 对比度与可读性

          
正文对比度至少 4.5:1，大文本至少 3:1；对比度不是“越黑越好”，而是保证可读。

          
WCAG 2.2 对普通文本要求 4.5:1，对大文本（约 18pt 或 14pt 粗体）要求 3:1；非文本控件（边框、图标、焦点环）要求 3:1。深色模式不是把颜色反过来，而是重新检查对比与表面层级。半透明文字、disabled 状态和占位符最容易低于阈值。

  • 只检查正文，忽略图标、边框和焦点环。

        


        

          
3.4 图标、形状与圆角

          
图标是语言的一部分：同一套风格、同一套尺寸、同一套语义；圆角要有一致的尺度。

          
图标风格（线性/填充）、线宽、圆角、视觉重心要统一；不要混用不同图标的细节。图标按钮必须有可访问名称，图标不能单独承担关键语义。圆角层级通常与组件层级相关：小控件 4–8px，卡片 12–16px，对话框 16–24px；不要每个组件一个值。

          

            

              
线性图标统一 1.5–2px 线宽，适合工具与导航；选中态可用填充版本。

              
圆角尺度按钮 8px、卡片 12px、对话框 20px；同一层级保持一致。

              
语义图标 + 文本优先；纯图标按钮必须有 aria-label/tooltip。

            

            
形状与圆角是设计 token 的一部分，不是每个组件的随手决定。

          

          
图标规则示例
所有图标使用同一套线性图标；图标按钮必须有可访问名称；卡片圆角统一 12px，不能因为内容不同而改变。

          
底层原理形状和圆角传递层级与亲和力；不一致的圆角会让界面显得拼凑。图标的可访问名称与文字标签是同一套语义系统的一部分。

          
常见坑
  • 混用线性/填充/彩色图标，视觉噪声大。
  • 纯图标按钮没有名称，屏幕阅读器只读“按钮”。
  • 每个卡片不同圆角，破坏组件一致性。

        


        

          
3.5 表面、层级与阴影

          
层级首先靠表面色与边界，其次才是阴影；阴影是深度的提示，不是装饰。

          
Material 3 用 tonal surface 表达层级：背景、surface、surface-container-low/high 等；阴影用于浮层（对话框、菜单、悬浮按钮）。在深色模式里，阴影几乎不可见，表面色更重要。不要给每个卡片都加大阴影；那会让页面像一堆漂浮的纸片，层级反而消失。

表面色 + 细边界表达大部分层级；阴影只留给真正浮起的元素。

          

          
表面规则示例
页面背景使用 surface；卡片使用 surface-container；对话框使用更高的表面层级 + 遮罩；不要给静态卡片加漂浮阴影。

          
底层原理层级是“离用户多近”的隐喻：越靠近用户的浮层越需要遮罩、焦点管理和更高的表面。深色模式下应优先调整表面亮度/边界，而不是依赖阴影。

          
常见坑
  • 所有卡片都有阴影，层级彻底失效。
  • 深色模式继续依赖黑色阴影。
  • 对话框没有遮罩或焦点管理。

        


        

          
3.6 动效 token

          
动效用于解释变化，不是炫技；用有限的时长/曲线 token，并尊重减少动效偏好。

          
动效回答“什么变了、从哪里来、到哪里去”。常见 token：fast 100–150ms（状态反馈）、standard 200–300ms（展开/切换）、slow 400–500ms（大范围转场）；曲线用标准、减速、加速三类。避免同时移动位置、尺寸、颜色、阴影；选择一到两个属性。`prefers-reduced-motion` 下应关闭非必要动效，保留即时状态变化。

          

            

              
fast · 120ms按钮 hover/press、状态标签切换。

              
standard · 240ms展开/折叠、页面内导航、列表插入。

              
slow · 420ms对话框、页面转场；减少动效时立即完成。

            

            
动效 token 让“快/慢”成为系统决策，而不是每个组件的随意值。

          

          
动效规则示例
按钮反馈 120ms；列表展开 240ms；对话框 320ms；所有动效在减少动效模式下改为即时或淡入淡出。

          
底层原理动效利用人对运动与连续性的感知，帮助建立空间关系；时长与曲线影响“轻重感”。过多或过慢的动效会增加等待感，也会触发前庭不适。

          
常见坑
  • 所有交互都用 300ms，按钮反馈显得迟钝。
  • 同时动画位置、尺寸、颜色，视觉噪声大。
  • 忽略减少动效偏好。

        

      


      

        

          
Part 4 · Components, States & Interaction

          
组件、状态与交互：把行为写进界面

          
组件不是静态截图；它有解剖结构、变体、状态和语义。这一部分把按钮、表单、导航、列表、对话框拆开，再讨论反馈、校验、过渡、乐观更新和重试。Running Example 会贯穿其中。

        


        

          
4.1 组件解剖与状态矩阵

          
一个组件至少包含容器、内容、交互和状态；状态矩阵是组件的规格，不是实现细节。

          
以按钮为例：容器（背景/边框/圆角）、内容（文字/图标）、交互（点击/键盘/长按）、状态（default/hover/focus/pressed/disabled/loading）。状态矩阵要定义每个状态的视觉、可交互性、语义和过渡；否则实现者只能猜。状态越多，越需要语义标签和可访问名称保持一致。

状态矩阵示例
按钮在 loading 时保留宽度、显示进度、禁止重复点击，并向辅助技术暴露 busy 状态；disabled 时必须说明为什么不可用。

          
底层原理状态矩阵把交互状态变成可测试的规格：每个状态都有视觉、行为、语义和过渡。实现时用枚举/状态机而不是多个布尔值，避免非法组合。

  • loading 时按钮宽度跳变，导致布局抖动。
  • disabled 状态没有解释，用户不知道如何恢复。

        


        

          
4.2 按钮与操作层级

          
一屏只应有一个主操作；次要操作用低强调，破坏性操作要显式确认。

          
按钮层级通常分 primary（填充）、secondary（描边/tonal）、tertiary（文字）、destructive（错误色）。主操作随上下文变化：在任务详情里，“重试”是主操作；在批量列表里，“批量删除”应降级并要求确认。按钮文字用动词+对象（“重试任务”），不要用“确定/提交”这种含糊词。

          

            
Primary当前页面最重要的动作；填充、对比最高。

            
Secondary重要但非首选；描边/tonal。

            
Tertiary低强调；文字按钮，仍要有焦点态。

            
Destructive错误色 + 确认；不可用颜色单独表达危险。

          

          
操作层级示例
详情页主操作是“重试任务”；“查看日志”为次要操作；“删除任务”为破坏性操作，需要二次确认并说明不可恢复。

          
底层原理操作层级用视觉权重表达决策成本：主操作最容易找到，破坏性操作最难误触。按钮的语义、快捷键和焦点顺序也应与视觉层级一致。

          
常见坑
  • 所有按钮都是主色，用户不知道先点哪个。
  • “确定”不说明确定什么。
  • 破坏性操作没有确认或撤销。

        


        

          
4.3 输入与表单

          
表单的目标是让用户一次填对；标签、帮助、错误和状态都属于控件本身。

          
输入框至少包含：可见标签、占位符（只作提示）、帮助文本、错误文本、必填/可选说明、焦点态和禁用态。错误应在提交前尽量预防，提交后在字段附近说明原因与修复方法；不要只把错误汇总在页面顶部。对数字/端口/设备 ID 这类字段，给出格式示例和约束，而不是让用户猜。

          

            

              
重试设置

标签、帮助、错误、约束和当前值应同时可见。

          

          
表单规则示例
每个输入有可见标签；错误在字段下方；提交失败时焦点移到第一个错误字段；不得只用占位符代替标签。

          
底层原理表单是“用户输入 → 校验 → 反馈”的状态机；错误预防的成本低于错误修复。标签与错误文本也是可访问名称/描述的一部分。

  • 用占位符当标签，输入后标签消失。
  • 错误只显示红色边框，不说明原因。
  • 提交后焦点停留在按钮，用户不知道哪里错了。

  • 返回后丢失筛选/滚动位置。

4.5 列表、卡片与空状态

          
列表项要支持扫视与比较；空状态要解释为什么空、下一步做什么。

          
列表项通常包含主标题、次要信息、状态和可选操作。主次信息用字号/颜色区分，状态右对齐便于比较。空状态不是一句“暂无数据”，而是说明原因（还没创建/筛选无结果/加载失败）和下一步（创建/清除筛选/重试）。加载时用骨架屏或占位，避免布局跳动。

  • 空状态只有“暂无数据”，没有下一步。
  • 加载时列表高度塌陷，页面跳动。
  • 状态只靠颜色，没有文字。

        


        

          
4.6 对话框与破坏性操作

          
对话框打断用户，只用于需要确认或必须立即处理的事；破坏性操作必须说明后果。

          
对话框适合：不可逆操作确认、需要立即输入的关键信息、阻塞性错误。不要把普通表单、长内容或可内联的操作放进对话框。破坏性确认要写清楚对象、后果和替代方案；“取消”应是默认焦点，“删除”用错误色且需要明确动作。对话框要有标题、可访问名称、焦点管理和 Esc/返回关闭。

标题说明问题，正文说明后果，按钮写具体动作；取消是默认焦点。

          

          
对话框规则示例
删除任务前显示对象与后果；默认焦点在“取消”；Esc/返回可关闭；删除后提供撤销或明确不可恢复说明。

          
底层原理对话框是模态的：它暂停当前流程并要求决策。模态成本高，所以只用于必须打断的场景；焦点陷阱与恢复是可用性的硬要求。

  • 破坏性按钮是默认焦点，容易误触。
  • 删除后没有撤销，也没有说明不可恢复。

        


        

          
4.7 可供性、反馈与校验

          
让可点的东西看起来可点，让发生的事有反馈，让错误在提交前尽量被预防。

          
可供性来自形状、位置、文案和交互约定：按钮像按钮、链接像链接、可拖拽区域有把手。反馈要即时且具体：hover/focus/pressed 是微反馈，提交后的 loading/success/error 是流程反馈。校验优先在输入时给出格式提示，提交时给出字段级错误；不要用 alert 打断，也不要把错误藏在顶部。

          

            
Affordance可点击/可拖拽/可编辑的外观与光标。

            
Feedback状态变化、进度、成功/失败、下一步。

            
Prevention格式提示、约束、禁用非法操作。

            
Recovery字段级错误、重试、撤销、保留输入。

          

          
校验规则示例
端口字段输入非数字时即时提示格式；提交失败时保留已填内容，标记第一个错误字段并移动焦点；不得清空表单。

          
底层原理可供性降低“能不能点”的不确定性；反馈缩短“我做了什么”的因果链。校验是错误预防，比错误提示更便宜；恢复能力决定用户是否愿意继续。

          
常见坑
  • 只有 hover 有反馈，键盘用户没有 focus 态。
  • 提交失败后清空表单。
  • 错误提示不说明如何修复。

        


        

          
4.8 过渡、乐观更新、取消与重试

Part 5 · Accessibility & Semantics

          
无障碍与语义：让界面对所有人都成立

          
无障碍不是最后加的功能，而是结构与语义的质量指标。键盘、焦点、屏幕阅读器、对比度、动态字体和减少动效，都会反过来改善普通用户的使用体验。

        


        

          
5.1 WCAG 2.2 与 POUR

          
WCAG 用四个原则描述可访问性：可感知、可操作、可理解、健壮。

          

            
Perceivable信息不能只靠一种感官：文本替代、对比度、字幕。

            
Operable键盘可用、焦点可见、触控目标足够大、没有键盘陷阱。

            
Understandable语言明确、错误可理解、行为可预测。

            
Robust语义正确，能兼容辅助技术与未来工具。

          

          
WCAG 2.2 的 AA 级是大多数产品的合理基线：正文对比度 4.5:1、键盘可达、焦点可见、标签与错误关联、触控目标至少 24×24 CSS px（移动端实践常用 44×44）。它不是“给残障用户的附加项”，而是让所有人在强光、单手、老设备、临时分心时都能用。

          
无障碍验收示例
所有交互可用键盘完成；焦点顺序与视觉顺序一致；每个输入有可见标签；错误文本与字段关联；正文对比度 ≥4.5:1。

          
底层原理POUR 从感知、操作、理解与兼容四个层面覆盖访问障碍。很多要求（对比度、焦点、标签）同时也是普通可用性的要求，因此越早纳入结构，返工越少。

          
常见坑
  • 只做屏幕阅读器测试，忽略键盘与对比度。
  • 用 div 模拟按钮，丢失角色与键盘行为。
  • 把错误只显示为红框，没有文本说明。

        


        

          
5.2 键盘、焦点与焦点顺序

          
键盘用户通过焦点使用界面；焦点必须可见、顺序合理、不会被困住。

          
焦点顺序应遵循视觉与阅读顺序；不要用正 tabindex 打乱顺序。打开对话框时焦点进入对话框、背景不可交互；关闭后焦点回到触发元素。自定义组件需要实现键盘交互（Enter/Space/方向键），并提供可见的 focus ring。跳过导航链接、地标和标题层级能帮助键盘/屏幕阅读器快速定位。

          

            

              
              
              
            

            
焦点环必须清晰可见；示例焦点在“查看日志”，视觉顺序与 Tab 顺序一致。

          

          
焦点规则示例
Tab 顺序与视觉顺序一致；对话框打开后焦点进入标题/第一个控件，Esc 关闭并返回触发按钮；不使用正 tabindex。

          
底层原理焦点是键盘与辅助技术的“光标”。焦点丢失会让用户不知道当前在哪；焦点陷阱会让用户无法离开。焦点管理是模态组件与路由切换的必备部分。

          
常见坑
  • 用 `outline: none` 移除焦点环却没有替代。
  • 对话框打开后焦点仍在背景。
  • 自定义下拉/菜单不支持方向键与 Esc。

        


        

          
5.3 语义树与屏幕阅读器

          
屏幕阅读器读的不是像素，而是角色、名称、状态和层级；语义树是界面的“另一套 API”。

          
每个可交互元素需要角色（button/link/text field）、可访问名称（可见标签或 aria-label）、状态（checked/expanded/disabled/busy）和必要的描述（帮助/错误）。装饰性图标应被忽略；图片要有 alt；标题层级要连续；地标（main/nav/header/footer）让用户快速跳转。不要用“点击这里”作为链接文本。

语义树应能独立表达“这是什么、叫什么、当前什么状态”。

          

          
语义规则示例
重试按钮的可访问名称为“重试任务”；loading 时暴露 busy=true；错误文本通过描述与输入关联；装饰性图标不进入语义树。

          
底层原理辅助技术通过可访问性 API 读取角色/名称/状态，而不是解析视觉。语义树的质量取决于结构、标签与状态是否同步；视觉隐藏但语义存在的文本（sr-only）也是工具之一。

          
常见坑
  • 图标按钮没有可访问名称。
  • 用视觉标题样式但不用 heading 语义。
  • loading 状态没有 busy 或文字提示。

        


        

          
5.4 非颜色编码与动态字体

          
状态不能只靠颜色；文字必须能随用户字号设置缩放而不破版。

          
色觉差异、强光、低质量屏幕都会让颜色失真。成功/失败/警告应同时有图标、文字或形状。动态字体（系统字号放大）会改变行高与换行，布局要能容纳 200% 缩放；不要用固定高度裁切文本，也不要用图片承载关键文字。数字与代码可以使用等宽字体，但仍要支持缩放。

颜色是增强，不是唯一通道；文字与形状是稳定的语义载体。

          

          
非颜色规则示例
失败状态同时显示“失败”文字与错误图标；正文放大到 200% 时，列表项高度自适应，不出现截断或横向滚动。

          
底层原理颜色感知因人而异，文字/形状提供冗余编码。动态字体改变文本度量，布局必须基于内容而不是固定像素；这也是响应式布局的一部分。

          
常见坑
  • 只靠红/绿区分成功失败。
  • 固定高度卡片，放大字体后文字被裁切。
  • 用图片展示关键状态或错误信息。

        


        

          
5.5 触控目标、缩放与减少动效

          
触控目标要足够大，页面要能缩放，动效要尊重减少动效偏好。

          
移动端常用 44×44 CSS px 作为触控目标下限；图标按钮的视觉尺寸可以更小，但点击区域要补足。允许双指缩放（不要 `user-scalable=no`）；横屏/窄屏不应出现页面级横向滚动。减少动效偏好下，转场改为淡入或即时，避免大范围位移与视差。

  • 禁止页面缩放以“保持布局”。

Part 6 · Design Systems, Requirements & Portability

          
设计系统、需求与迁移：把经验变成可交付的语言

          
设计系统让界面可复用，需求简报让实现可验证，迁移工作表让知识可带走。这一部分是 Act I 的收束，也是 Act II 的输入：先写出完整需求，再用 Flutter 实现。

        


        

          
6.1 Token 分层

          
token 分三层：primitive（原始值）、semantic（语义角色）、component（组件专用）。

          
primitive token 是颜色值、间距、字号、圆角、时长等原始刻度；semantic token 把它们映射为背景、文本、边框、错误、主操作等角色；component token 再为具体组件提供别名。业务代码只应引用 semantic/component token，不直接引用 primitive。这样换主题、调对比度、做暗色模式时只需改映射。

Token 规则示例
业务代码只使用 `color.text.primary`、`space.card.padding`、`radius.card`；不直接写 `#18181b`、`16px`、`12px`。亮暗主题只改 semantic 映射。

          
底层原理token 分层把“可选值”和“用途”分开：primitive 提供刻度，semantic 提供语义，component 提供局部约束。层级越清晰，主题切换、对比度调整和跨平台映射越稳定。

          
常见坑
  • 业务代码直接引用 primitive 颜色，换主题时到处改。
  • token 命名按颜色（blue-500）而不是用途（primary）。
  • 组件 token 过多，失去系统一致性。

        


        

          
6.2 组件 API 与变体约束

          
组件 API 不是属性越多越好；用有限的变体、槽位和状态覆盖真实场景。

          
组件 API 应回答：有哪些变体（primary/secondary/destructive）、尺寸（sm/md/lg）、状态（default/loading/disabled）、内容槽位（icon/leading/trailing）、可访问名称和事件。不要用一堆布尔值组合出非法状态；用枚举/变体表达互斥状态。组件文档要给出“何时用/何时不用”和可访问性要求。

底层原理组件 API 是设计与代码的共同契约；变体把“允许的差异”编码进类型，非法组合在编译/检查期就被排除。槽位让内容组合，而不增加布尔开关。

          
常见坑
  • 用 10 个布尔属性控制样式，组合爆炸。
  • 组件没有可访问名称入口。
  • 变体命名按外观而不是用途。

        


        

          
6.3 主题、文档与版本治理

          
主题是 token 的映射；设计系统需要文档、版本和弃用策略，否则会变成一套过时组件。

          
主题至少覆盖亮/暗、品牌色、密度、对比度；组件文档要包含用法、变体、状态、可访问性、代码示例和变更记录。版本治理包括语义化版本、弃用周期、迁移指南和视觉回归测试。不要把“主题”做成全局变量集合；它应该是可切换的 token 映射。

          

            
Theme亮/暗、品牌、密度、对比度；只改 semantic 映射。

            
Docs何时用/不用、变体、状态、a11y、代码。

            
Versionsemver、弃用、迁移指南、视觉回归。

            
Governance谁提案、谁评审、如何发布、如何反馈。

          

          
治理规则示例
新增组件先提交使用场景与 a11y 要求；破坏性变更升主版本并提供 codemod/迁移说明；所有变体有视觉回归基线。

          
底层原理设计系统是产品与工程的共享基础设施；它的价值来自一致性，成本来自维护。版本治理确保一致性不会变成停滞，弃用策略让系统可以演进。

          
常见坑
  • 组件没有文档，靠读源码使用。
  • 破坏性变更不发版/不写迁移。
  • 主题只支持亮色，暗色靠反色滤镜。

6.5 验收标准与状态清单

          
验收标准用 Given/When/Then 描述可观察行为；状态清单确保没有漏掉 loading、空、错误和权限。

          
好的验收标准是具体的、可测试的、与用户行为相关。不要写“界面要美观”，而要写“在 375px 宽度下，失败原因和重试按钮同时可见，且不出现横向滚动”。状态清单至少覆盖：初始、加载、空、错误、成功、禁用、无权限、离线、取消/重试。每条状态都要有视觉、语义和下一步。

          

            
Given 设备任务失败且原因已知
When 用户打开任务详情
Then 首屏显示失败原因和重试按钮
And 重试按钮在提交中显示 loading 且不可重复点击
And 失败后保留已填上下文并给出下一步

            
Given/When/Then 不是测试框架专属；它是需求与实现之间的可验证语言。

          

          
状态清单
idle · loading · empty · error · success · disabled · no-permission · offline · optimistic · rollback · cancelled。

          
底层原理验收标准把“完成”定义为可观察行为，而不是主观判断；状态清单把异步流程的边界显式化，二者一起构成可测试的 UI 契约。

          
常见坑
  • 验收标准只覆盖 happy path。
  • 用“应该”“尽量”这种不可测措辞。
  • 状态清单没有无权限/离线。

7.1 Widget / Element / Render 三棵树

          
Widget 是不可变配置，Element 是树上的实例，RenderObject 负责布局、绘制与命中测试。

          
每次 build 都会创建新的 Widget 配置；Flutter 比较新旧 Widget，复用/更新 Element，再让 RenderObject 重新布局和绘制。理解这点能解释两个常见问题：为什么 Widget 可以 const、为什么“重建”不等于“重绘”。StatelessWidget 没有可变状态；StatefulWidget 的 State 持有跨帧状态。

迁移问题
目标框架的“配置”和“实例”分别是什么？重建/更新的粒度是什么？有没有等价于 Element 的复用层？

          
底层原理Flutter 的 build 是纯配置构造，Element 树负责生命周期与复用，RenderObject 树负责布局/绘制。三棵树分离让声明式写法与高性能更新可以共存。

  • 把 State 当成全局状态容器。

        


        

          
7.2 约束向下、尺寸向上、父级定位

          
Flutter 布局的核心规则：父级传约束，子级选尺寸，父级决定位置。理解它，很多“为什么不能这样”就有答案。

          
SizedBox 强加固定尺寸，Expanded/Flexible 分配剩余空间，ConstrainedBox 限制范围。不要在无限约束里使用 Expanded；不要给所有子项固定宽度；溢出时先检查父级给了多少空间，而不是直接缩小字体。

7.4 LayoutBuilder、MediaQuery 与响应式

8.4 共享状态与数据流

          
跨组件共享的状态需要明确的拥有者；用 InheritedWidget/ValueNotifier 起步，复杂项目再引入 Provider/Riverpod。

8.5 FutureBuilder 与异步状态

          
异步界面必须显式处理 waiting/error/empty/success；FutureBuilder 是起点，复杂流程用状态机。

          
FutureBuilder 适合一次性加载；StreamBuilder 适合持续事件。不要在 build 里创建新的 Future，否则每次重建都会重新请求。错误要可读，空数据要与错误区分；重试通过重新触发 Future/状态实现。

          

            
dartFutureBuilder 的四种状态已验证

            
import 'package:flutter/material.dart';

class TaskListScreen extends StatelessWidget {
  const TaskListScreen({super.key, required this.tasks});

  final Future<List<String>> tasks;

  @override
  Widget build(BuildContext context) {
    return FutureBuilder<List<String>>(
      future: tasks,
      builder: (context, snapshot) {
        if (snapshot.connectionState == ConnectionState.waiting) {
          return const Center(child: CircularProgressIndicator());
        }
        if (snapshot.hasError) {
          return Center(child: Text('加载失败：${snapshot.error}'));
        }
        final items = snapshot.data ?? const <String>[];
        if (items.isEmpty) {
          return const Center(child: Text('暂无任务'));
        }
        return ListView(
          children: [for (final item in items) ListTile(title: Text(item))],
        );
      },
    );
  }
}

          

          
迁移问题
目标框架的异步状态 API 是什么？如何在重建间缓存 Future/请求？错误/空/重试如何表达？

          
底层原理FutureBuilder 订阅 Future 的完成状态并重建；它不负责缓存或取消。生产代码通常把 Future 放在 State/控制器中，避免 build 重新创建；复杂流程用显式状态机。

          
常见坑
  • 在 build 里调用 API 创建 Future。

  • Affordance / 可供性：控件外观暗示的操作方式。
    • 
            
  • Semantics / 语义：角色、名称、状态和描述，供辅助技术使用。
    • 
            
  • Design token：可复用的设计决策值，分 primitive/semantic/component。
    • 
            
  • Constraint / 约束：父级给子级的可用空间范围。
    • 
            
  • State / 状态：界面在某一时刻的数据与交互条件。
    • 
            
  • State matrix：组件在默认/悬停/焦点/按下/禁用/加载等状态下的规格。
    • 
            
  • Optimistic UI：先更新本地界面，再等服务端确认，失败时回滚。
    • 
            
  • Information architecture：内容的组织、命名与层级。
    • 
            
  • WCAG / POUR：可感知、可操作、可理解、健壮的无障碍原则。
    • 
            
  • Golden test：比较渲染图像的视觉回归测试。
    • 
            
  • Hot Reload：保留部分状态快速更新 Flutter 代码。
    • 
            
  • Given/When/Then：验收标准的可测试表达。
    • 
            
  • Running Example：本页贯穿始终的设备任务面板。
    • 
            
  • Four contracts：Structure / Style / State / Semantics。
