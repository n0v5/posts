Part 0 · Orientation

导言：把已知映射到未知

Dart 的语法看起来像 Java/JavaScript，但你从 C++ 与 Python 带来的经验大部分可以直接复用。真正需要换脑的只有三处：类型与空安全、对象与内存、并发模型。这一部分先建立判断标准，后面每一章都按同一套结构展开。

0.1 为什么用已有经验学 Dart

Dart 是一门为客户端优化的、健全类型（soundly typed）的面向对象语言：开发时用 JIT，发布时编译为原生代码、JavaScript 或 WebAssembly；每个 isolate 内部是单线程事件循环。

它由 Google 维护，最广为人知的下游是 Flutter，但 Dart 本身也能写 CLI、服务端和 Web 程序。对 C++/Python 开发者来说，Dart 的吸引力不在“又学一门语法”，而在于它把一些你熟悉的取舍重新组合了：静态类型加类型推断、GC 但无共享内存的并发、类与接口加 mixin/extension、以及一套统一的包管理与测试工具。

适合你的场景Flutter 跨平台 UI；需要 AOT 单文件可执行的 CLI；对启动时间敏感的 Web/Wasm；想把 Python 脚本重写成类型更稳、部署更简单的工具。
不适合硬套的场景数据科学栈（Python 生态仍更强）；系统编程/驱动/实时控制（C++/Rust 仍更合适）；需要成熟 JVM 生态的企业后端。
dart 最小程序：hello.dart DartPad ↗ 
void main() {
  final name = 'Dart';
  final year = 2026;
  print('Hello, $name! ($year)');
}

运行方式很简单：安装 Dart SDK 后执行 dart run hello.dart。没有头文件、没有链接步骤、没有虚拟环境；main 是入口，所有顶层声明都在同一个库里。

如果你来自 C++/Python
C++入口是 int main(int argc, char** argv)，需要编译与链接。Dart 的 main 可以直接接收 List<String> args，由运行时负责启动。
Python入口通常是模块底部的 if __name__ == '__main__':。Dart 没有“模块被导入时执行”的隐式入口，只有 main。
Dartvoid main() 或 Future<void> main() async。每个文件是一个库，_ 前缀表示库内私有。
底层原理Dart 开发时由 VM 以 JIT 运行，支持热重载；发布时可用 AOT 编译为原生可执行文件，或编译为 JavaScript / WebAssembly。同一套语言语义，三种运行时形态，具体差异在第七部分展开。
常见坑
  • 不要把 Dart 当成“带花括号的 Python”：Dart 是静态类型，类型错误通常在运行前就被分析器拦下。
  • 不要寻找头文件或前向声明：导入的是库，不是文本包含。
  • 不要把 main 写成 C++ 的 int main()；Dart 的返回值通常是 void 或 Future<void>。

先把六组概念对齐，后面读代码时就不会把 C++/Python 的直觉错误地套上来。

三个必须换掉的习惯1）不要用“指针 + 手动生命周期”思考对象；2）不要把 async 当成线程；3）不要用 Python 的“运行时什么都可能”来设计 API，先让空安全与 sealed 类帮你排除状态。
三个可以直接复用的习惯1）先定义数据与不变量；2）用小函数和组合取代深层继承；3）为边界写测试。Dart 的 package:test 与 C++/Python 的测试思路几乎一致。
如果你来自 C++/Python
C++你习惯值语义、析构函数和线程共享堆。Dart 里所有变量都是对象引用，资源释放交给 GC；跨 isolate 不能共享可变对象。
Python你习惯动态类型、None 和 GIL。Dart 在编译期就区分可空/非空，async 是单线程并发，CPU 并行要靠 isolate。
Dart先问三个问题：这个值能为空吗？这个对象会被共享吗？这段工作是 I/O 密集还是 CPU 密集？答案会直接决定类型、并发与 API 形状。
底层原理Dart 没有 C++ 意义上的未定义行为；所有值都是对象，int/bool 也不例外。GC 负责回收不可达对象，因此没有析构器式的确定性释放；需要确定性清理时用 try/finally 或 Finalizer。
常见坑
  • final 不等于“对象不可变”：final list = [1]; list.add(2) 合法。
  • async 不会创建线程；它只是让出事件循环。
  • Dart 的 int 在原生平台是 64 位，在 Web 上受 JavaScript 数字精度限制；跨平台代码不要假设任意精度。

Part 1 · Language & Type System

语言基础与类型系统：先把类型想清楚

Dart 的语法门槛不高，真正的差异在类型系统：它既不像 C++ 模板那样在编译期展开，也不像 Python 注解那样只做静态检查。Dart 的类型在运行时仍然存在，泛型具体化，空安全健全。这一部分从入口与变量讲到 records、函数与泛型。

1.1 入口与项目结构

一个 Dart 文件就是一个库；main 是唯一入口，导入的是库而不是文本。

最小的命令行程序只需要一个 main。参数通过 List<String> 传入，返回值可以是 void，也可以是 Future<void>。Dart 没有头文件、宏和预处理；所有声明在库级别可见，_ 前缀把名字限制在当前库内。

dart带参数与导入的入口DartPad ↗
import 'dart:math' as math;

void main(List<String> args) {
  final radius = args.isEmpty ? 1.0 : double.parse(args.first);
  final area = math.pi * radius * radius;
  print('area: ${area.toStringAsFixed(2)}');
}

常见目录约定：bin/ 放命令行入口，lib/ 放库代码，test/ 放测试，pubspec.yaml 描述包。lib/src/ 里的实现默认不对外暴露，公共 API 从 lib/<package>.dart 导出。这是 Dart 的“公开 API 边界”，比 C++ 的头文件目录约定更接近 Python 包的 __all__。

如果你来自 C++/Python
C++#include 是文本替换，需要头文件、include guard、前向声明与链接。Dart 的 import 直接按库解析，没有这些步骤。
Pythonimport 执行模块顶层代码；Dart 导入只建立库的命名空间，不会自动执行 main。Dart 的库级私有是 _name，不是下划线约定。
Dartimport 'dart:math' as math; 给库起前缀；show/hide 控制暴露的符号；part 只用于代码生成等少数场景，日常不要用。
常见坑
  • dart:io 在 Web 平台不可用；跨平台库要用条件导入或在入口层隔离平台代码。
  • 包内相对导入与 package: 导入混用会触发 lint；同一文件尽量只用一种风格。
  • 不要用 part 来模拟 C++ 的“把实现拆文件”；优先拆库和 export。

1.2 变量、推断与 final/const

var 让编译器推断类型，final 让引用只赋值一次，const 要求编译期常量并做规范化。

Dart 的局部变量几乎总是用类型推断：var 不是“动态类型”，推断出来的类型是静态的，之后不能改变。final 只禁止重新赋值，不冻结对象内部；const 更强，要求表达式在编译期可求值，并对相同常量做规范化（canonicalization），因此两个 const 对象可能共享同一实例。

dartvar / final / const 的实际差别DartPad ↗
void main() {
  var count = 0;            // int
  final name = 'Ada';       // String，不能重新赋值
  const pi = 3.14159;       // 编译期常量
  final list = <int>[1, 2]; // final 只固定引用
  list.add(3);              // 可以修改内容
  count++;
  print('$count $name $pi $list');
  // name = 'Grace';        // 编译错误
  // const other = pi * 2;  // 合法：pi 是 const
}

如果你来自 C++/Python

            

              
C++auto 推断但类型仍静态；const 表示不可修改；constexpr 才接近 Dart 的 const。C++ 的值语义与 const 的深不可变不是一回事。

              
Python没有语言级 const；Final 只是类型检查器的约束。Dart 的 const 由编译器强制执行，并影响运行时常量池。

              
Dartvar 静态推断；final 运行期一次性赋值；const 编译期常量。dynamic 会关闭静态检查，Object? 加流分析才是安全的多类型选择。

            

          

          
底层原理const 对象在编译期求值并被规范化：相同的 const 表达式通常指向同一个实例。因此 const 集合是深度不可变的，而 final 集合只是引用不可重新绑定。

          
常见坑
  • 把 final 当成“不可变对象”；它只固定引用。
  • 以为 var x = null 能随后赋任意值：推断类型是 Null，只能持有 null。
  • 在需要运行时值的地方写 const，例如 const x = DateTime.now()，会直接编译失败。

        


        

          
1.3 内建类型

          
Dart 的内建类型很少，但数值与字符串的细节和 C++/Python 都不一样，尤其是整数精度与 UTF-16 长度。

          
int、double、num、String、bool、List、Set、Map 是最常用的类型。Dart 没有隐式的 int → double 转换，但数值字面量可以按上下文推断；/ 总是返回 double，整除要用 ~/。字符串不可变，索引与 length 按 UTF-16 代码单元计数。

          

            
dart内建类型与数值/字符串细节DartPad ↗

            
void main() {
  int a = 42;
  double b = 3.14;
  num c = a + b;
  String s = 'Dart';
  bool ok = s.isNotEmpty;
  List<int> xs = [1, 2, 3];
  Set<String> tags = {'dart', 'flutter'};
  Map<String, int> scores = {'Ada': 100};

  print('$a $b $c $s $ok $xs $tags $scores');
  print(s.length);        // 4 个 UTF-16 代码单元
  print(1 / 2);           // 0.5，总是 double
  print(1 ~/ 2);          // 0，整除
  print(1 + 2.0);         // 3.0
  print(r'raw\nstring');  // 原始字符串，反斜杠不转义
}

          

          
String 支持插值 '$name'、三引号多行、相邻字符串拼接和原始字符串 r'...'。但 length 不是“用户看到的字符数”：一个 emoji 可能占多个 UTF-16 代码单元。需要按字形簇处理时，用 package:characters 的 characters。

浮点float/doublefloat（通常 64 位）double（64 位 IEEE-754）

除法整数除法截断/ 浮点，// 整除/ 返回 double，~/ 整除

              
            

          

          

            
如果你来自 C++/Python

            

              
C++你会习惯 int32_t/int64_t 与溢出语义；Dart 不暴露固定宽度整数，跨平台时要注意 Web 的精度上限。

              
Python你会习惯 len(s) 数码点、int 任意精度；Dart 的 length 是 UTF-16 单元，int 不是任意精度。

              
Dart用 toStringAsFixed 控制小数显示；需要码点/字形处理时引入 characters；跨平台大整数用 BigInt 或字符串协议。

常见坑
  • 以为 1 / 2 得到 0；在 Dart 中它是 0.5。
  • 用 s.length 统计用户可见字符数；emoji 与组合字符会失真。
  • 在 Web 上处理超过 253 的整数仍然假设精确；需要时用 BigInt。

        


        

          
1.4 Records：多返回值与结构化数据

          
Record 是位置字段或命名字段组成的不可变值类型，自带结构化相等与解构，适合“临时组合几个值”而不想新建类。

          
Dart 3 的 record 用圆括号声明：(int, String) 是位置记录，({String name, int age}) 是命名记录。它没有方法、不能继承，字段默认 final；== 与 hashCode 按结构生成。需要行为时用类，需要轻量数据载体时用 record。

          

            
dart命名 record、解构与结构化相等DartPad ↗

            
({String name, int age}) makeUser() => (name: 'Ada', age: 36);

void main() {
  final (:name, :age) = makeUser();
  final point = (1, 2);
  print('$name $age $point');
  print(point.$1 + point.$2);
  print((1, 2) == (1, 2)); // true：结构化相等
  const origin = (0, 0);
  print(origin);
}

          

          

            
如果你来自 C++/Python

            

              
C++你会想到 std::pair/std::tuple 或临时 struct。Dart record 有命名字段与结构化相等，但同样没有方法；需要行为就用 class。

              
Python你会想到 tuple 或 namedtuple。Dart record 的命名字段是类型的一部分，解构语法更统一；dataclass 则更接近 Dart class。

              
Dart返回多个值、解析中间结果、switch 解构时优先 record；需要序列化、校验或方法时用 class 加 fromJson/toJson。

            

          

          
底层原理Record 是值类型：赋值与传参传递的是字段值的组合，两个字段相同的 record 相等。字段本身若是可变对象，record 仍只固定字段引用，不会深拷贝。

          
常见坑
  • 把 record 当类用，试图加方法；record 不能声明方法。
  • 以为 record 会深拷贝内部对象；它只是字段不可重新赋值。
  • 位置 record 与命名 record 是不同类型，不能因为字段相同就互换。

        


        

          
1.5 函数与参数

          
Dart 用命名参数替代函数重载；可选位置参数与命名参数都支持默认值，函数本身是一等对象。

          
位置参数按顺序传递；命名参数用 {} 声明，调用时写 name:，可读性更好；可选位置参数用 []。默认值必须是编译期常量。required 用于命名参数，表示调用方必须提供。Dart 不支持按参数类型重载，通常用不同函数名、命名参数或密封类区分。

          

            
dart命名参数、默认值、闭包与一等函数DartPad ↗

            
int add(int a, int b) => a + b;

String greet(String name, {String greeting = 'Hello', bool shout = false}) {
  final text = '$greeting, $name';
  return shout ? text.toUpperCase() : text;
}

void main() {
  print(add(1, 2));
  print(greet('Ada'));
  print(greet('Ada', greeting: 'Hi', shout: true));
  final twice = (int x) => x * 2;
  print(twice(21));
  final addTen = (int x) => add(x, 10);
  print(addTen(5));
}

          

          
函数可以被赋值、作为参数传递、从函数返回；闭包会捕获外部变量。方法可以“撕下”成 tear-off：final f = list.add;。这些能力让 Dart 的集合管道与回调风格接近 Python 的高阶函数，但类型检查更严格。

          

            
如果你来自 C++/Python

            

              
C++你会用重载与默认参数；Dart 没有重载，命名参数承担了“可选、可读”的职责。C++ 的函数对象/ lambda 对应 Dart 的函数值。

              
Python你会用 *args/**kwargs；Dart 的命名参数是静态声明，调用方不能传未声明的名字。默认参数同样在声明处求值。

              
Dart参数超过两个时优先命名参数；需要“重载”时用不同函数名或 sealed 参数类型，不要依赖运行时判断。

            

          

          
底层原理Dart 的函数是对象，闭包捕获的是变量而不是值；被闭包捕获的变量会延长生命周期。默认参数在编译期必须可求值，因此不能写 DateTime.now()。

          
常见坑
  • 把命名参数写成位置参数调用：greet('Ada', 'Hi') 不合法，必须写 greeting: 'Hi'。
  • 以为可以有同名不同参数类型的重载；Dart 会直接报重复定义。
  • 在可选参数里使用运行时表达式作为默认值。

        


        

          
1.6 类型系统与泛型

          
Dart 的类型是健全的、静态的、可推断的；泛型在运行时保留，因此可以检查 List<int>，也要为协变带来的运行时检查付出代价。

          
Dart 的泛型是具体化的（reified）：List<int> 与 List<String> 在运行时是不同的类型，runtimeType 能看到类型参数。这与 C++ 模板的编译期实例化、Python 类型注解的运行时擦除都不同。Dart 的泛型默认协变：List<int> 可以赋给 List<num>，但向其中添加 double 会在运行时失败。

          

            
dart泛型函数、运行时类型与 typedefDartPad ↗

T first<T>(List<T> items) => items.first;

void main() {
  final ints = <int>[1, 2, 3];
  final strings = <String>['a'];
  print(first(ints));
  print(first(strings));
  print(ints.runtimeType); // List<int>

  final Json data = {'ok': true};
  if (data['ok'] is bool) {
    print(data['ok'] as bool);
  }
}

如果你来自 C++/Python

            

              
C++模板在编译期为每组类型参数生成代码，类型信息不一定保留到运行时；Dart 的泛型是一套运行时类型系统，支持 is 检查和反射式 runtimeType。

              
Pythonlist[int] 注解主要供类型检查器使用，运行时通常没有约束；Dart 会在运行时检查泛型实参。

底层原理具体化泛型让 Dart 能在运行时执行 is List<int> 这样的检查，也让协变容器在写入时插入运行时类型检查。C++ 模板把检查前移到编译期，Python 注解则往往不参与运行时。

          
常见坑
  • 把 List<int> 当 List<num> 随意写入；编译通过，运行时可能抛类型错误。
  • 用 dynamic 逃避类型设计；它会关闭静态检查，错误推迟到运行时。
  • 以为 typedef 会创建新类型；它只是别名，不提供额外类型安全（需要时用 extension type）。

        

      


      

        

          
Part 2 · Sound Null Safety

          
空安全：让“可能为空”成为类型的一部分

          
Dart 默认不允许 null 进入非空类型；可空必须显式写成 T?，并由流分析在编译期证明安全。! 不是“把 null 变成非 null”，而是“我保证这里不为 null，否则运行时炸”。这一部分讲清楚可空、提升、late 与迁移。

        


        

          
2.1 可空与非空

          
在 Dart 里，String 永远不是 null；要允许 null，必须写 String?。

          
这是健全空安全（sound null safety）：类型系统保证非空变量永远不会是 null，编译器因此可以做优化，也能在编译期发现大量空指针问题。可空类型是一个真正的联合类型 String | Null，你不能直接调用 String 的成员，必须先证明非空或使用空感知操作符。

          

            
dart非空与可空DartPad ↗

            
void main() {
  String name = 'Ada';
  String? nickname = null;
  print(name.length);       // 非空，安全
  print(nickname?.length);  // 可空，返回 int?
  // print(nickname.length); // 编译错误
}

          

          

            
如果你来自 C++/Python

            

              
C++指针、引用与 std::optional 都可能为空/无效。Dart 没有空指针，只有可空引用；非空类型必须在构造时初始化。

              
Python所有引用都可能是 None，类型注解里的 Optional[T] 主要给检查器看。Dart 把可空性放进类型系统并由编译器强制执行。

              
Dart默认非空；字段要么在构造器初始化，要么用 late；集合元素与集合本身的可空性要分开写：List<String?> vs List<String>?。

            

          

          
底层原理健全空安全意味着“非空类型里永远没有 null”，而不是“运行时尽量检查”。这允许编译器省略部分空检查并优化表示；代价是开发者必须显式处理可空性。

          
常见坑
  • 把字段声明成非空但忘记在构造器初始化；分析器会直接报错。
  • 混淆 List<String?>（元素可空）与 List<String>?（列表本身可空）。
  • 用 null 表示“尚未初始化”；更清晰的建模是 sealed 状态或 optional 类型。

        


        

          
2.2 操作符与流分析

          
空安全的核心不是 !，而是流分析：当编译器能证明非空时，可空变量会自动提升为非空类型。

          
?. 在接收者为 null 时短路并返回 null；?? 提供默认值；??= 仅在为 null 时赋值；! 是开发者断言非空，失败会抛运行时错误。流分析会跟踪 if (x != null)、is 检查、提前返回等路径，在安全的分支内把 T? 提升为 T。赋值、闭包捕获等情况可能让提升失效。

          

            
dart空感知操作符与类型提升DartPad ↗

            
String? findNickname(String name) => name == 'Ada' ? 'countess' : null;

void main() {
  final nickname = findNickname('Ada');
  print(nickname?.length);        // 8
  if (nickname != null) {
    print(nickname.toUpperCase()); // 提升为 String
  }

  String? mutable = nickname;
  mutable = null;
  try {
    print(mutable!.length);       // 运行时错误
  } catch (error) {
    print('caught: $error');
  }
  print(mutable?.length ?? 0);    // 0
}

如果你来自 C++/Python

            

              
C++你会写 if (p) 或 opt.has_value()；Dart 的流分析在 if (x != null) 之后自动提升类型，不需要额外解包。

              
Python你会写 if x is not None:；Dart 的 x?.foo 与 x ?? fallback 更短，但 ! 的语义是“断言”，不是“安全转换”。

  • 以为类型提升能跨过任意函数调用或闭包；可变捕获可能让提升失效。
  • 把 ?? 当成“空字符串/0/false 的默认值”；它只判断 null。

        


        

          
2.3 late 与延迟初始化

          
late 允许非空字段稍后初始化，或在首次读取时计算；它把编译期的“必须初始化”变成运行时的“读取前必须已初始化”。

          
典型场景：字段依赖构造完成后才能拿到的上下文（Flutter 的 initState）、昂贵的懒加载、或者无法在初始化列表里表达的非空赋值。late final 常用于“只赋值一次”的延迟字段。读取未初始化的 late 字段会抛 LateInitializationError，不是返回 null。

          

            
dartlate final 的两种用法DartPad ↗

            
class Config {
  late final String apiBase;
  late final int retries = 3;

  void init() {
    apiBase = 'https://example.com';
  }
}

void main() {
  final config = Config()..init();
  print(config.apiBase);
  print(config.retries);
}

          

          

            
如果你来自 C++/Python

            

              
C++未初始化变量是未定义行为；Dart 的 late 会做运行时检查，读取未初始化值会抛错，而不是读到垃圾内存。

              
Python属性未设置会抛 AttributeError；late 的失败更接近“声明了但尚未赋值”，错误信息更明确。

              
Dart能用构造器/初始化列表解决就不要用 late；late 是给生命周期确实分阶段的字段用的，不是给“懒得设计初始化”用的。

            

          

          
底层原理late 字段在运行时有一个“未初始化”哨兵；读取时检查并可能触发初始化表达式。它不会改变空安全规则，只是把初始化检查从编译期推迟到运行期，因此仍然可能失败。

          
常见坑
  • 用 late 绕开构造器设计，结果在错误时机读取导致崩溃。
  • 把 late 与可空混淆：late String 不是 String?，读取前必须初始化。
  • 在 late final 字段上重复赋值；第二次会抛错。

        


        

          
2.4 集合与空安全

          
“元素可空”和“集合本身可空”是两件事，必须分别建模。

          
List<String?> 表示列表一定存在，但元素可能是 null；List<String>? 表示列表本身可能不存在，但元素一定非空。两者不能互相赋值。处理元素可空时用 whereType<T>() 过滤；处理集合可空时用 ?? const [] 或提前返回。

          

            
dart两层可空性DartPad ↗

            
void main() {
  List<String?> maybe = ['a', null];
  List<String>? allOrNothing = null;

  print(maybe.whereType<String>().toList()); // [a]
  print(allOrNothing ?? const <String>[]);   // []

  Map<String, dynamic> json = {'name': 'Ada'};
  final name = json['name'] as String? ?? 'unknown';
  print(name);
}

          

          

            
如果你来自 C++/Python

            

              
C++std::vector<std::optional<T>> 与 std::optional<std::vector<T>> 是两种类型；Dart 的写法更短，但语义完全对应。

              
Pythonlist[str | None] 与 list[str] | None 也是两层；Dart 在编译期强制你区分。

              
Dart元素可空用 whereType 收窄；集合可空用 ?? 提供空集合；不要用 ! 把整层可空性抹掉。

            

          

          
底层原理可空性是类型构造器的一部分：List<T?> 与 List<T>? 在类型系统中不同，运行时泛型检查也会区分它们。JSON 解析得到的是 dynamic，在边界处用 as/模式匹配收窄。

          
常见坑
  • 把 List<String?> 直接传给需要 List<String> 的函数；需要过滤或重建列表。
  • 用 cast<String>() 把 List<String?> 强转；它是惰性的，遇到 null 会在迭代时抛错。
  • 对可空集合直接调用 .length，忘记集合本身也可能为 null。

        


        

          
2.5 迁移旧代码与 JSON 边界

          
历史代码迁移先标注边界，再逐步收紧：可空的地方显式写 ?，必须存在的地方用 required 或构造器校验，! 只作为最后手段。

          
Dart 3 起所有代码都运行在健全空安全下，旧的混合模式已经成为历史。迁移时的顺序通常是：先让分析器报错，区分“确实可空”“暂时未知”“不可能为空”；对确实可空的字段加 ?，对必须由调用方提供的参数加 required，对生命周期分阶段的字段用 late，对 JSON 等动态边界做显式校验。

          

            
dart在动态边界收窄类型DartPad ↗

            
import 'dart:convert';

void main() {
  final data = jsonDecode('{"name":"Ada","age":36}') as Map<String, dynamic>;
  final name = data['name'] as String? ?? 'unknown';
  final age = data['age'] as int?;
  print('$name ${age ?? '?'}');
}

          

          

            
如果你来自 C++/Python

            

              
C++你会把外部输入解析到一个强类型 struct，并检查每个字段；Dart 的 jsonDecode 返回 dynamic，同样需要在边界做显式收窄。

              
Python你会写 data.get('name') 与类型检查；Dart 的 as String? 是运行期检查，失败会抛错，?? 处理 null。

              
Dart把 JSON 解析集中在少数工厂构造器里；内部代码只接收强类型对象。不要在业务逻辑里到处传 Map<String, dynamic>。

            

          

          
底层原理健全空安全在编译期保证内部代码的非空性，但 dynamic、JSON、平台通道等边界仍然可能引入 null。迁移的关键不是消灭所有 ?，而是把动态边界隔离在一层适配代码里。

          
常见坑
  • 用 as String 解析可能缺失的 JSON 字段，字段缺失时直接抛错。
  • 把 ! 当成迁移快捷键，导致运行时才发现问题。
  • 在公共 API 里大量暴露 dynamic，把空安全优势又还回去。

        

      


      

        

          
Part 3 · Objects & Reuse

          
OOP 与代码复用：单继承 + 接口 + 组合

          
Dart 是单继承语言，但提供了隐式接口、mixin、extension 与 class modifiers，足以表达大多数 C++ 多继承/模板技巧想解决的问题。这一部分按“构造对象 → 建立契约 → 复用实现 → 封闭层次 → 定义相等”的顺序展开。

        


        

          
3.1 类与构造器

          
Dart 的构造器有默认、命名、factory、const 四种常见形态；Dart 3.13 的 primary constructor 把“字段 + 构造器”合并成一行。

          
Dart 的构造器支持初始化列表（initializer list）与 super 参数，用于在构造器体执行前初始化字段；此外还有命名构造器、factory 构造器与 const 构造器。字段默认是公开的，_ 前缀表示库内私有；final 字段必须在构造器或初始化列表中赋值。const 构造器要求所有字段 final 且参数在编译期可求值，适合值对象与配置。

          

            
dart经典构造器：命名、factory、const、重定向DartPad ↗

            
class Point {
  final double x;
  final double y;

  Point(this.x, this.y);
  Point.origin() : this(0, 0);
  factory Point.fromJson(Map<String, num> json) =>
      Point(json['x']!.toDouble(), json['y']!.toDouble());
  const Point.zero() : x = 0, y = 0;

  @override
  String toString() => 'Point($x, $y)';
}

void main() {
  final p = Point(1, 2);
  print(p);
  print(Point.origin());
  print(Point.fromJson({'x': 3, 'y': 4}));
  print(const Point.zero());
}

          

          

            
dartDart 3.13+：primary constructorsDart 3.13+DartPad ↗

Primary constructor 适合字段少、以数据为主的类；它把 final 参数自动变成字段，构造器体仍然可以声明方法、getter 和其他成员。它不能替代所有构造器形态；需要命名构造器、factory 或复杂初始化时，退回经典写法更清楚。

          

            
如果你来自 C++/Python

            

              
C++你会用成员初始化列表、委托构造、拷贝/移动构造。Dart 没有拷贝构造与移动语义，对象通过引用传递；需要复制时显式写 copyWith 或工厂。

              
Python你会用 __init__、@classmethod、@dataclass。Dart 的命名构造器接近 classmethod，factory 可以返回缓存/子类型，const 构造器提供编译期值对象。

              
Dart字段默认私有性靠 _；需要“只读”就写 final；需要“可选”就写可空类型或命名参数；不要为每个字段写 getter/setter，Dart 的字段本身就是访问器。

            

          

          
底层原理Dart 对象全部分配在堆上，变量持有引用；没有 C++ 的栈上对象与析构时机。GC 负责回收，const 构造器产生的对象会被规范化并可能共享实例，因此不能用可变状态去修改 const 对象。

          
常见坑
  • 忘记给 final 字段赋值；分析器会报“字段必须初始化”。
  • 把 factory 构造器写成普通构造器再 return this；factory 必须显式返回实例。
  • 在 const 构造器里使用运行时参数，例如 DateTime.now()。
  • 以为 Dart 有拷贝构造；对象赋值只是复制引用。

        


        

          
3.2 继承、抽象类与隐式接口

          
Dart 的每个类都隐式定义了一个接口；extends 继承实现，implements 只继承契约。

          
extends 是单继承，子类获得父类的字段与方法实现；implements 要求实现接口声明的所有成员，但不继承任何实现。Dart 没有单独的 interface 关键字（class modifier 里的 interface 是另一回事）；任何类都可以被 implements。抽象类用 abstract class 声明，不能实例化，可以包含抽象成员与具体实现。

          

            
dartextends vs implementsDartPad ↗

            
abstract class Shape {
  double area();
}

class Circle implements Shape {
  final double radius;
  Circle(this.radius);

  @override
  double area() => 3.14159 * radius * radius;
}

class Square extends Shape {
  final double side;
  Square(this.side);

  @override
  double area() => side * side;
}

void main() {
  final shapes = <Shape>[Circle(1), Square(2)];
  for (final shape in shapes) {
    print(shape.area());
  }
}

          

          
Circle implements Shape 与 Square extends Shape 都能放进 List<Shape>，但前者必须自己实现 area，后者可以复用父类已有的实现。@override 是注解，帮助分析器检查拼写与方法签名；不写不会改变语义，但建议始终写。

          

            
如果你来自 C++/Python

            

              
C++纯虚函数/抽象基类接近 Dart 的 abstract class + implements；Dart 没有虚析构、没有多重继承，接口分派仍是动态的。

              
Python你会用 ABC 或鸭子类型；Dart 的 implements 是显式契约，编译器会检查所有成员，不依赖运行时属性查找。

              
Dart“is-a”用 extends；“can-do”用 implements；想复用实现又不想建立父子关系时用 mixin 或组合。

            

          

          
底层原理Dart 是单继承 + 接口：对象只有一个父类实现链，但可以实现任意多个接口。接口方法调用是动态分派；具体走哪张方法表由运行时对象类型决定，而不是变量的静态类型。

          
常见坑
  • 用 implements 后忘记实现某个成员；分析器会报错。
  • 把 extends 当成“实现接口”；它会继承父类实现，耦合更强。
  • 在 Dart 里寻找 virtual/override 关键字；Dart 默认方法可重写，用 @override 标注即可。

        


        

          
3.3 Mixin：横向复用实现

          
mixin 把一组实现“混入”到类里；with 的顺序决定方法解析顺序，后混入的覆盖先混入的。

          
mixin 不能单独实例化，也不能声明生成式构造器；它可以有字段、方法和 on 约束。on Walker 表示这个 mixin 只能混入 Walker 的子类型，并且内部可以调用 Walker 的成员。多个 mixin 形成线性化链：class Duck with Walker, Swimmer 中，Swimmer 在 Walker 之后，super 调用会沿链向上。

          

            
dartmixin、on 约束与 withDartPad ↗

            
mixin Walker {
  void walk() => print('walking');
}

mixin Swimmer on Walker {
  void swim() {
    walk();
    print('swimming');
  }
}

class Duck with Walker, Swimmer {}

void main() {
  final duck = Duck();
  duck.swim();
}

          

          

            
如果你来自 C++/Python

            

              
C++你会想到多继承与菱形问题。Dart 用单继承 + mixin 线性化避免菱形；没有虚基类，方法解析按 with 顺序决定。

              
Python你会想到 mixin 类与 MRO。Dart 的线性化更简单：后写的 mixin 优先；on 约束替代了部分协作继承。

              
Dart用 mixin 复用“行为片段”（日志、重试、缓存），用组合复用“有状态的对象”；不要用 mixin 模拟多继承的数据模型。

            

          

          
底层原理mixin 在编译时被展开到类的实现链中，方法解析顺序是确定的线性化。混入的字段与类字段一样存在于对象中；mixin 不能有自己的生成式构造器，因此不能强制初始化参数。

          
常见坑
  • 以为 with A, B 与 with B, A 等价；顺序会改变覆盖关系。
  • 在 mixin 里声明构造器；mixin 不支持生成式构造器。
  • 忘记 on 约束导致 mixin 调用了不存在的方法。

        


        

          
3.4 Extension 与扩展类型

          
extension 给已有类型添加静态解析的成员；extension type 在 3.3 起提供零成本的类型包装。

          
extension 可以为第三方类型或 String/int 等内建类型添加方法、getter、setter 和运算符。它是静态分派：调用点根据变量的静态类型选择扩展，不会进入运行时方法表，也不能被子类“重写”。extension type 是更严格的包装：运行时表示就是底层类型，但编译器提供独立的静态类型与成员，适合给 int、String 加上领域含义（如 UserId）。

}

}

          

          

            
如果你来自 C++/Python

常见坑
  • 以为 extension 可以重写类自己的方法；同名成员优先走类的方法，extension 不会覆盖。
  • 两个扩展提供同名成员且都被导入；需要 show/hide 或显式调用解决冲突。
  • 把 extension type 当运行时品牌；它没有独立的运行时类型。

  • 在 switch 里漏掉新子类型；好在 sealed 会让分析器直接报非穷尽。

        


        

          
3.6 相等性与运算符

          
Dart 的默认 == 是引用相等；需要值相等时，必须同时重写 == 与 hashCode。

          
类默认继承 Object 的 ==（identity）与 hashCode（身份哈希）。records 是例外，它们自带结构化相等。集合（List/Map/Set）的 == 也是引用相等，所以两个内容相同的列表并不相等；需要内容比较时用 package:collection 的 listEquals/DeepCollectionEquality，或把数据建模成 record。

          

            
dart重写 == 与 hashCode，并实现运算符DartPad ↗

            
class Money {
  final int cents;
  const Money(this.cents);

  @override
  bool operator ==(Object other) => other is Money && other.cents == cents;

  @override
  int get hashCode => cents.hashCode;

  Money operator +(Money other) => Money(cents + other.cents);

  @override
  String toString() => 'Money(${cents / 100})';
}

void main() {
  const a = Money(100);
  const b = Money(100);
  print(a == b);       // true
  print(a + b);        // Money(2.0)
  print([a] == [b]);   // false：集合默认按引用比较
}

          

          

            
如果你来自 C++/Python

            

              
C++你会重载 operator==，C++20 还可生成 <=>；Dart 没有自动生成，必须手写 == 与 hashCode。

              
Python你会实现 __eq__/__hash__；Dart 的契约相同：相等对象必须有相同哈希，哈希字段应不可变。

              
Dart值对象优先用 record 或不可变类；重写相等时只使用 final 字段；集合内容比较显式调用工具函数，不要假设 == 会深比较。

            

          

          
底层原理HashMap/HashSet 先用 hashCode 分桶，再用 == 确认。若两个对象相等但哈希不同，它们会落进不同桶，集合查找就会失败；若哈希依赖可变字段，对象放进 Set 后修改字段会“消失”。

          
常见坑
  • 只重写 == 不重写 hashCode；在 Set/Map 中行为错误。
  • 用可变字段计算 hashCode；对象状态变化后无法从哈希集合中找回。
  • 以为 [1, 2] == [1, 2] 为 true；它是 false。

4.1 集合与集合管道

          
Dart 的 List/Set/Map 字面量支持 spread、collection if/for；where/map 返回惰性 Iterable，需要 List 时再 toList()。

void main() {
  final numbers = [1, 2, 3, 4];
  final doubled = [
    for (final n in numbers)
      if (n.isEven) n * 10,
  ];
  final withSpread = [0, ...doubled, 100];
  final names = {'Ada': 36, 'Grace': 85};
  final adults = names.entries
      .where((e) => e.value >= 18)
      .map((e) => e.key)
      .toList();
  final total = numbers.fold<int>(0, (sum, n) => sum + n);

  print(doubled);    // [20, 40]
  print(withSpread); // [0, 20, 40, 100]
  print(adults);     // [Ada, Grace]
  print(total);      // 10
}

4.2 高阶函数与推导式

          
Dart 的集合方法接近 Python 的高阶函数，但返回类型与惰性语义需要分清。

dart惰性 Iterable 与立即求值DartPad ↗

            
void main() {
  final xs = [1, 2, 3, 4];
  final evens = xs.where((x) => x.isEven);
  final labels = evens.map((x) => 'E$x');

  print(labels);         // (E2, E4)：仍然是 Iterable
  print(labels.toList()); // [E2, E4]：物化
  print(xs.any((x) => x > 3));  // true
  print(xs.every((x) => x > 0)); // true
  print(xs.fold<int>(0, (sum, x) => sum + x)); // 10
}

          

          

            
如果你来自 C++/Python

            

              
C++C++20 ranges 的 view 与 Dart 的惰性 Iterable 类似；Dart 没有编译期 range 管道优化，链式调用仍是对象协议。

              
Python生成器表达式是惰性的；Dart 的 where/map 同样惰性，但类型更严格，链式结果通常要 toList() 才能按 List 使用。

              
Dart纯数据变换用链式；需要索引、提前退出、复杂控制流时用 for；不要在惰性管道里做有副作用的操作。

            

          

          
底层原理Iterable 通过 Iterator 协议逐个产出元素；链式操作不会立即遍历，只有终端操作（toList、fold、for-in 等）才启动迭代。每次重新迭代都会重新执行整条管道。

          
常见坑
  • 对惰性管道调用多次终端操作，导致重复计算与重复副作用。
  • 在 map 回调里修改原集合，行为难以预测。
  • 为了风格强行链式，牺牲可读性与调试性。

        


        

          
4.3 模式匹配

          
Dart 3 的 patterns 把类型检查、解构与分支合并到一个 switch 表达式里，配合 sealed 类可以获得编译期穷尽性。

          
模式可以匹配常量、类型、record 字段、List/Map 结构、对象 getter；可以绑定变量（:final value）、加 guard（when）、用逻辑模式（||/&&）组合。switch 语句不再自动 fallthrough；空的 case 可以共享同一个体。switch 表达式必须有返回值，且每个分支都要覆盖。

          

            
dartsealed 类 + switch 表达式 + if-caseDartPad ↗

            
sealed class Shape {}

class Circle extends Shape {
  final double radius;
  Circle(this.radius);
}

class Rect extends Shape {
  final double width;
  final double height;
  Rect(this.width, this.height);
}

double area(Shape shape) => switch (shape) {
      Circle(:final radius) => 3.14159 * radius * radius,
      Rect(:final width, :final height) => width * height,
    };

void main() {
  final shapes = <Shape>[Circle(1), Rect(2, 3)];
  for (final shape in shapes) {
    print(area(shape));
  }

  final (a, b) = (1, 2);
  print(a + b);

  if (shapes.first case Circle(:final radius)) {
    print('circle $radius');
  }
}

4.4 sealed 与穷尽性

          
sealed 把“所有可能的状态”封闭在一个库内，新增状态时编译器会迫使你更新所有分支。

          
典型用法是 Result<T>、加载状态、协议消息、表达式树。与 base/final 相比，sealed 的关键不是禁止继承，而是“直接子类型集合可枚举”，从而支持穷尽检查。sealed 类隐式抽象，不能直接实例化；所有直接子类型必须在同一库，间接子类型可以放到其他库，但会被父类的分支覆盖，因此实际写法通常把它们放在同一文件。

          

            
如果你来自 C++/Python

            

              
C++你会用 std::variant 表示封闭集合，用 std::visit/overloaded 处理；Dart 的 sealed switch 不需要额外的 visitor 模板。

              
Python你会用基类 + match + 约定；Dart 把“新增子类必须更新分支”变成编译期错误。

              
Dart状态、结果、事件优先 sealed；只在库内部扩展的类型用 default；需要外部实现契约时用 interface class，不要用 sealed。

            

          

          
底层原理穷尽性检查依赖“封闭世界”假设：编译器知道 sealed 类型的所有直接子类型，因此能证明 switch 覆盖完整。跨库新增直接子类型会破坏这个假设，所以 sealed 的直接子类被限制在同一库。

          
常见坑
  • 把 sealed 的直接子类分散到不同库，导致编译错误。
  • 在 switch 中漏掉 null；如果输入是 Result?，需要额外处理 null。
  • 为了“以后可能扩展”而不用 sealed，结果失去穷尽检查；需要外部扩展时改用 interface。

}

    •

常见坑
  • 用 List.filled(n, []) 初始化二维结构；使用 List.generate。
  • 用 == 比较列表内容；需要显式内容比较。
  • 在遍历集合时删除元素；先收集再删除，或使用迭代器。

        

      


      

        

          
Part 5 · Asynchrony

          
异步：单线程事件循环上的并发

          
Dart 的 async 不是多线程，而是把 I/O 等待交给事件循环。理解 microtask 与 event 的顺序，是用好 Future/Stream 的前提；理解“一个 isolate 只有一个事件循环”，是用好 Isolate 的前提。

        


        

          
5.1 事件循环与微任务

          
每个 isolate 一条事件循环：先清空 microtask 队列，再取下一个 event；await 之后的代码通常以 microtask 形式继续。

          
同步代码先执行完，然后事件循环开始工作。microtask（Future.microtask、scheduleMicrotask、await 的续体）优先级高于 event（Timer、I/O、Future() 构造的异步任务）。每处理一个 event，都会先把当时积累的 microtask 全部清空。下面的程序输出是 A D C B E，而不是 A B C D E。

          

            
dartmicrotask 与 event 的顺序DartPad ↗

            
Future<void> main() async {
  print('A');
  Future(() => print('B'));        // event
  Future.microtask(() => print('C')); // microtask
  print('D');
  await Future<void>.delayed(Duration.zero);
  print('E');

      如果你来自 C++/Python

      5.2 Future 与 async/await
      
          
      async 函数在第一个 await 之前同步执行；返回的 Future 代表最终值或错误，await 会暂停当前函数并把续体排入 microtask。

      5.3 组合、超时与错误
      
          
      Future.wait 等待一组 Future，Future.any 取第一个完成，timeout 只让等待超时，不会取消底层任务。

      Part 6 · Isolates
      
          
      Isolate 并发：用消息代替共享内存
      
          
      Dart 没有“线程 + 锁”的默认并发模型。每个 isolate 有独立堆与事件循环，彼此只能通过消息通信。这消除了数据竞争，也意味着你不能靠共享变量协调任务。这一部分讲清楚 isolate 的边界、通信方式与适用场景。
      
        
      

        
      
          
      6.1 Isolate 模型
      
          
      Isolate 是内存隔离的执行单元：独立堆、独立事件循环，消息按值/复制传递，没有共享可变状态。
      
          
      主 isolate 负责 UI/主逻辑；计算密集任务可以放到 worker isolate，避免阻塞事件循环。isolate 之间通过 SendPort 发送消息，接收端用 ReceivePort 监听。消息不是共享引用，而是复制（或转移）过去；因此不存在 C++ 的锁、条件变量、原子操作这一套，也不需要担心数据竞争。

    var sum = 0;
    for (var i = 1; i <= 1_000_000; i++) {
      sum += i;
    }
    return sum;
  });
  print(result); // 500000500000
}

      C++你会用 std::thread + mutex 共享数据；Dart 里没有共享可变堆，消息传递取代了锁，但复制大对象有成本。
      
              
      PythonGIL 让线程难以并行 CPU；Dart 的 isolate 没有 GIL，但每个 isolate 独立 GC、独立堆，通信靠消息而不是共享对象。
      
              
      Dart主 isolate 保持轻量；CPU 任务用 Isolate.run 或长驻 worker；I/O 任务仍用 async，不要为每个请求 spawn isolate。
      
            
      
          
      
          
      底层原理isolate 可以共享代码与不可变对象（同一 isolate group），但不共享可变堆。消息发送会复制对象图或转移可转移数据；接收端拿到的是独立副本。并行来自多个 isolate 跑在不同平台线程上。
      
          
      常见坑
      • 试图在 isolate 之间共享可变对象；编译/运行时会阻止不可发送对象。
      • 为每个小任务 spawn 一个 isolate；启动与复制成本可能远超任务本身。
      • 忘记关闭 ReceivePort；监听器与端口会持续占用资源。
      
        
      

        
      
          
      6.2 Isolate.run 与长驻 worker
      
          
      一次性任务用 Isolate.run；需要反复通信时用 Isolate.spawn + 端口，维护一个长驻 worker。
      
          
      Isolate.run 适合“输入 → 计算 → 一个结果”的场景，它自动创建 isolate、执行闭包、返回结果并关闭。长驻 worker 适合需要多次请求/响应的场景：主 isolate 把自己的 SendPort 交给 worker，worker 再把自己的接收端口发回来，双方通过端口交换消息。端口是单向的；双向通信需要两个端口。
      
          
      
            
      dart长驻 worker：端口握手与回传DartPad ↗
      
            
      import 'dart:async';
import 'dart:isolate';

void worker(SendPort mainPort) {
  final port = ReceivePort();
  mainPort.send(port.sendPort);
  port.listen((message) => mainPort.send('echo: $message'));
}

Future<void> main() async {
  final mainPort = ReceivePort();
  final workerPortCompleter = Completer<SendPort>();
  mainPort.listen((message) {
    if (message is SendPort) {
      workerPortCompleter.complete(message);
    } else {
      print('main received: $message');
    }
  });

  await Isolate.spawn(worker, mainPort.sendPort);
  final workerPort = await workerPortCompleter.future;
  workerPort.send('ping');
  await Future<void>.delayed(const Duration(milliseconds: 200));
  mainPort.close();
}
      
          
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++你会用线程池 + 条件变量实现 worker；Dart 用端口消息与 Future 组合，没有共享队列与锁。
      
              
      Pythonmultiprocessing 的 Pipe/Queue 与 Dart 端口类似；但 Dart 的 isolate 更轻，且消息对象有可发送性限制。
      
              
      Dart一次性任务 Isolate.run；多次请求用长驻 worker；需要请求 ID 时自己带在消息里，端口不提供 RPC 语义。
      
            
      
          
      
          
      底层原理端口是异步消息队列；发送方不等待接收方处理。消息顺序在同一发送方到同一接收方之间保持，但多个发送方之间没有全局顺序。worker 的异常若不处理，会终止该 isolate，主 isolate 需要通过 onError/onExit 监听。
      
          
      常见坑
      • 对同一个 ReceivePort 调用 .first 后又 .listen；单订阅流不能重复监听。
      • 只创建 ReceivePort 不关闭；资源泄漏。
      • 假设 worker 消息会按发送方之外的全局顺序到达。
      
        
      

        
      
          
      6.3 消息与性能
      
          
      Isolate 通信不是免费的：对象要复制，频繁的小消息可能比计算本身更贵。
      
          
      大多数普通 Dart 对象都可以通过端口发送，但发送的是副本；SendPort、ReceivePort、Function 等有特殊规则。Uint8List 等大块二进制可以复制，也可以用 TransferableTypedData 转移所有权，避免复制。闭包会连同捕获的变量一起复制，因此不要捕获巨大的对象图。
      
          
        
            
      • 批量：把多个小任务合并成一批消息，减少握手与复制次数。
        • 
            
      • 转移：大块字节用 TransferableTypedData；发送后原引用不可再用。
        • 
            
      • 结果：一次性任务用 Isolate.run 直接返回值，避免自己搭端口。
        • 
            
      • 测量：先在主 isolate 做性能分析，确认 CPU 是瓶颈，再引入 isolate。
        • 
          
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++共享内存 + 锁的通信几乎零拷贝；Dart 的默认消息是复制，省掉了同步却增加了序列化/复制成本。
      
              
      Pythonmultiprocessing 也要 pickle/复制；Dart 的消息限制更严格，但类型系统能在发送前发现部分不可发送对象。
      
              
      Dart小消息合并、大字节转移、频繁请求用长驻 worker；不要用 isolate 模拟共享内存数据库。
      
            
      
          
      
          
      底层原理同一 isolate group 内，消息传递可能共享不可变对象（如字符串、代码），但可变对象图需要复制。转移型数据把所有权移交给接收方，避免复制；发送方之后不能再使用原对象。
      
          
      常见坑
      • 发送包含打开文件/原生资源的对象；这些对象不可发送或不可安全复制。
      • 每次请求都传大 JSON；考虑传字节或拆成更小的批。
      • 在 worker 里同步阻塞太久，导致主 isolate 的请求排队。
      
        
      

        
      
          
      6.4 常见架构
      
          
      把 isolate 当成 actor：每个 worker 有独立状态，主 isolate 负责编排与超时。
      
          
      常见结构是“一个主 isolate + 一个或多个长驻 worker”。主 isolate 维护任务 ID、超时与取消协议；worker 只处理消息并回传结果。任务有顺序要求时，在 worker 内用队列串行处理；需要并行时启动多个 worker，但要限制并发数，避免内存与 CPU 过载。
      
          
      
            
      一次性计算Isolate.run：解析大文件、压缩、图像处理、复杂搜索。简单、无状态、结果单一。
      
            
      长驻服务Isolate.spawn + 端口：数据库代理、编解码器、需要缓存/预热的重计算。需要协议、超时与关闭流程。
      
          
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++你会设计线程池、无锁队列、任务窃取；Dart 的 worker 之间不共享队列，任务分发要经过消息。
      
              
      Python你会用 ProcessPoolExecutor；Dart 的长驻 worker 更像手工管理的进程池，协议与生命周期要自己写。
      
              
      Dart先做简单的单 worker；需要吞吐再扩多个；为每个请求带 ID、超时与取消消息，避免主 isolate 无限等待。
      
            
      
          
      
          
      底层原理isolate 之间没有共享调度器；每个 isolate 自己跑事件循环。主 isolate 的“并发”来自同时向多个 worker 发送消息，以及每个 worker 在不同平台线程上独立执行。
      
          
      常见坑
      • 没有超时与取消协议；worker 卡住时主 isolate 一直等。
      • worker 崩溃后不重建；后续请求全部失败。
      • 无限制地 spawn worker；内存与 CPU 反而更差。
      
        
      

        
      
          
      6.5 何时不该用 Isolate
      
          
      I/O 密集用 async；只有 CPU 密集、且确实阻塞事件循环时，才值得引入 isolate。
      
          
      网络请求、文件读写、数据库访问本身已经是异步的，用 await 就能让出事件循环，不需要 isolate。Isolate 适合纯 CPU 计算：大循环、解析、压缩、加密、图像处理。引入 isolate 前先测量；如果主线程没有明显卡顿，收益可能为负。
      
          
      
            
      
              
      任务推荐原因
      
              
                
      HTTP 请求、文件 I/Oasync/awaitI/O 等待由事件循环处理，不占 CPU
      
                
      大 JSON 解析先测量；必要时 isolate解析是 CPU 工作，但小数据不值得复制成本
      
                
      图像/音视频处理Isolate纯 CPU、耗时长，阻塞主线程会影响 UI
      
                
      频繁小计算主 isolate消息与启动成本高于计算本身
      
                    
            
      
          
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++你会默认“开线程”；Dart 里线程不是默认选项，先问任务是不是 CPU 密集，再决定是否 isolate。
      
              
      Python你会用多进程绕开 GIL；Dart 没有 GIL，但 isolate 仍有启动与复制成本，不是所有任务都值得。
      
              
      DartI/O 用 async；CPU 用 isolate；不确定就先 profile。不要在架构上预先假设“并发越多越好”。
      
            
      
          
      
          
      底层原理并发是“同时处理多件事”，并行是“同一时刻真正同时执行”。事件循环提供并发，isolate 提供并行；两者的成本模型不同，不能互相替代。
      
          
      常见坑
      • 用 isolate 包裹一个本来就在 await I/O 的函数；没有收益。
      • 在小任务上频繁 spawn isolate；启动成本主导。
      • 用 isolate 共享缓存；每个 isolate 有独立堆，缓存不共享。
      
        
      
      
      

      
      
        
      
          
      Part 7 · Toolchain
      
          
      工具链、测试与编译产物
      
          
      Dart 的工具链比 C++ 简单得多：一个 SDK 自带格式化、分析、测试、编译与调试入口。这一部分按“建项目 → 静态检查 → 测试 → 编译 → 调试”走一遍，并对照 CMake/Conan 与 pip/pytest。
      
        
      

        
      
          
      7.1 SDK 与项目
      
          
      dart create 生成项目骨架，pubspec.yaml 描述依赖与 SDK 约束，dart pub 解析版本。
      
          
      
            
      shell创建、添加依赖、运行
      
            
      dart create -t console full_name
cd full_name
dart pub add args
dart run
dart test
      
          
      
          
      
            
      yamlpubspec.yaml 的核心字段
      
            
      name: full_name
description: A sample command-line application.
version: 1.0.0
environment:
  sdk: ^3.13.0

dependencies:
  args: ^2.0.0

dev_dependencies:
  lints: ^6.0.0
  test: ^1.25.0
      
          
      
          
      应用（application）通常提交 pubspec.lock，保证部署可重复；库（package）通常不提交 lockfile，让下游解析兼容版本。SDK 约束 ^3.13.0 表示 3.13 及以上、4.0 以下。dart pub add 会自动写入合适的约束并更新 lockfile。
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++CMake + Conan/vcpkg 需要分别管理构建与依赖；Dart 的 pubspec.yaml 同时描述元数据、SDK 约束与依赖，dart run 直接构建运行。
      
              
      Pythonpyproject.toml + lockfile 与 pubspec + pubspec.lock 类似；但 Dart 没有虚拟环境，包缓存在全局 PUB_CACHE，项目通过 lockfile 固定版本。
      
              
      Dartbin/ 放入口，lib/ 放库，test/ 放测试；公共 API 从 lib/<package>.dart 导出，lib/src/ 视为内部实现。
      
            
      
          
      
          
      底层原理pub 使用版本求解器解析依赖图，并写入 lockfile。SDK 约束参与求解；语言版本由 SDK 约束决定，分析器据此启用对应语法与 lint。
      
          
      常见坑
      • 库项目提交 lockfile，限制下游解析；应用则应提交。
      • SDK 约束写得过窄，导致新 SDK 无法使用；用 caret 约束。
      • 把内部实现放在 lib/ 根目录，意外成为公共 API；内部代码放 lib/src/。
      
        
      

        
      
          
      7.2 analyze / format / fix
      
          
      Dart 自带格式化、静态分析与自动修复；把这三件事放进 CI，比事后 code review 更便宜。
      
          
      
            
      shell日常三件套
      
            
      dart format .
dart analyze
dart fix --apply
      
          
      
          
      
            
      yamlanalysis_options.yaml：更严格的静态检查
      
            
      include: package:lints/recommended.yaml

analyzer:
  language:
    strict-casts: true
    strict-inference: true
    strict-raw-types: true

linter:
  rules:
    - prefer_final_locals
    - unawaited_futures
      
          
      
          
      dart format 没有配置项，统一风格；dart analyze 检查类型、未使用变量、可疑代码与 lint；dart fix --apply 自动修复可安全修复的问题。严格模式会让隐式 dynamic、未标注泛型、隐式转换更容易暴露，适合新项目。
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++clang-format 对应 dart format，clang-tidy 对应 dart analyze + lint；Dart 的配置集中在一个 YAML 文件。
      
              
      Pythonruff format 对应 dart format，ruff check/mypy 对应 dart analyze；Dart 不需要额外安装这些工具。
      
              
      Dart格式化在保存时自动运行；分析零警告作为 CI 门槛；dart fix 后仍要 review，不要盲信自动修改。
      
            
      
          
      
          
      底层原理分析器基于 CFE（Common Front End）构建 AST 并做类型推断；lint 是分析器插件规则。严格模式不是运行时检查，而是把更多隐式行为变成静态诊断。
      
          
      常见坑
      • 把 dart fix --apply 的结果直接提交；自动修复可能改变语义。
      • 一开始就开启所有 lint；噪声过多导致团队忽略分析结果。
      • 格式化与生成代码混在一起；生成文件用 // dart format off 或忽略规则。
      
        
      

        
      
          
      7.3 测试
      
          
      package:test 提供 test/group/expect、异步测试、流匹配与覆盖率；测试文件放在 test/，用 dart test 运行。
      
          
      
            
      dart同步与异步测试DartPad ↗
      
            
      import 'package:test/test.dart';

int add(int a, int b) => a + b;

void main() {
  group('add', () {
    test('adds positive numbers', () {
      expect(add(1, 2), 3);
    });

    test('works asynchronously', () async {
      await Future<void>.delayed(const Duration(milliseconds: 10));
      expect(add(2, 3), 5);
    });
  });
}
      
          
      
          
      常用 API：setUp/tearDown 管理夹具，expectLater 匹配 Stream 的 emitsInOrder，throwsA 断言异常，dart test --coverage=coverage 生成覆盖率。需要 mock 时用 mocktail 或手写 fake，不要 mock 值对象。
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++GoogleTest/Catch2 的 TEST/TEST_F 对应 test/group，断言对应 expect；Dart 测试文件也是普通 Dart 文件。
      
              
      Pythonpytest 的 fixture 对应 setUp/tearDown 或自定义辅助函数；参数化测试用循环或 for 生成多个 test。
      
              
      Dart测试公开行为而不是私有实现；异步测试必须 await；Stream 用 expectLater；测试之间不要共享可变全局状态。
      
            
      
          
      
          
      底层原理dart test 会为测试套件建立隔离的运行环境，按文件/组组织执行；异步测试由测试框架等待 Future 完成。测试失败会给出期望值与实际值差异。
      
          
      常见坑
      • 异步测试忘记 async/await，测试在回调执行前就结束。
      • 测试依赖执行顺序或共享全局状态；单独运行就失败。
      • 对 Stream 只 expect 一次，漏掉后续事件；用 expectLater。
      
        
      

        
      
          
      7.4 编译与运行产物
      
          
      开发用 JIT，发布按目标选择 AOT 原生、JavaScript 或 WebAssembly；不同目标的库可用性与启动特性不同。
      
          
      
            
      shell常见构建命令
      
            
      dart run bin/main.dart
dart compile exe bin/main.dart -o build/app
dart compile js -O2 web/main.dart -o web/main.dart.js
dart compile wasm bin/main.dart -o build/app.wasm
      
          
      
          
      
            
      
              
      目标命令特点典型场景
      
              
                
      JIT / VMdart run启动快、支持热重载、带调试信息开发、脚本、测试
      
                
      AOT 原生dart compile exe单文件可执行、启动快、平台相关CLI、服务端
      
                
      JavaScriptdart compile js浏览器兼容性最好、产物较大Web
      
                
      WebAssemblydart compile wasm性能接近原生、依赖浏览器 WasmGC 支持现代 Web、Flutter Web
      
                    
            
      
          
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++AOT 原生编译接近常规编译链接，但没有头文件/链接器脚本；不同平台要分别构建，交叉编译不是默认能力。
      
              
      PythonJIT 开发体验接近解释器，但 Dart 代码在运行前仍会编译为 kernel；发布时 AOT 不再需要运行时解释器。
      
              
      DartCLI 发布用 dart compile exe；Web 用 dart2js 或 Wasm；Flutter 发布走 AOT。先明确目标平台，再选库（dart:io 不能进 Web）。
      
            
      
          
      
          
      底层原理JIT 先把源码编译为 kernel，再由 VM 执行并做优化；AOT 在构建时生成机器码并做 tree shaking；dart2js 把 Dart 转换为 JavaScript；Wasm 目标输出 WebAssembly。不同产物共享语言语义，但平台库与启动路径不同。
      
          
      常见坑
      • 在 Web 目标导入 dart:io；分析能过，构建失败。
      • 用 AOT 产物做性能测试却保留调试信息/断言；用 release 配置。
      • 忽略 dart2js 体积；按需拆分入口、避免大依赖。
      
        
      

        
      
          
      7.5 DevTools 与调试
      
          
      Dart DevTools 提供断点、调用栈、堆快照、CPU profile 与日志；它通过 VM Service 连接运行中的程序。
      
          
      
            
      shell启动调试与 DevTools
      
            
      dart run --observe bin/main.dart
dart devtools
      
          
      
          
      VS Code 的 Dart 扩展提供图形化断点、变量查看与热重载；命令行工具适合服务器/CI 环境。性能问题先用 CPU profile 找热点，再用堆快照查内存增长；不要凭直觉优化。
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++gdb/lldb 对应 Dart 调试器，perf 对应 CPU profile，heaptrack/valgrind 对应堆快照；Dart 的工具链一体化程度更高。
      
              
      Pythonpdb 对应断点调试，cProfile/py-spy 对应 CPU profile，tracemalloc 对应堆快照；Dart DevTools 是图形化统一入口。
      
              
      Dart开发时保留调试信息，发布时用 release 配置；profile 要在接近真实的负载下做，不要用 toy 数据下结论。
      
            
      
          
      
          
      底层原理VM Service 是运行时的调试/观测协议；DevTools 只是客户端。调试器、profile、堆快照都通过该协议读取运行时状态，因此远程调试需要开放端口并注意安全。
      
          
      常见坑
      • 在生产环境开放 VM Service 端口；这是严重的安全风险。
      • 在 debug/JIT 模式下做性能结论；与 AOT release 差异明显。
      • 只看平均耗时，不看长尾与事件循环阻塞。
      
        
      
      
      

      
      
        
      
          
      Part 8 · Ecosystem & Boundaries
      
          
      生态与边界：Dart 能去哪里
      
          
      Dart 的主要舞台是 Flutter，但语言本身也能写服务端、CLI 与 Web。这一部分给出生态地图与边界：哪些值得深入，哪些只需知道存在，以及如何与既有 C++/Python 代码互操作。
      
        
      

        
      
          
      8.1 pub.dev 与包管理
      
          
      pub.dev 是 Dart 的包仓库；语义化版本 + caret 约束 + lockfile 构成依赖管理的基本盘。
      
          
      依赖分 dependencies 与 dev_dependencies。库的使用者会继承你的依赖约束；应用则通过 lockfile 固定完整依赖图。pub.dev 的包页面会显示平台支持、评分、维护活跃度与安全 advisories；选择包时不要只看下载量。
      
          
      
            
      shell依赖排查常用命令
      
            
      dart pub deps
dart pub outdated
dart pub upgrade
dart pub downgrade
      
          
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++Conan/vcpkg 的依赖图与 pub 类似；Dart 的包是源码包，没有 ABI 兼容负担，但也没有系统库/编译选项的概念。
      
              
      Pythonpip/uv/poetry 的锁文件与 pubspec.lock 类似；Dart 的全局包缓存按版本共享，项目之间不会互相污染。
      
              
      Dart应用提交 lockfile；库放宽约束；上线前跑 dart pub outdated；对不维护的包准备替代方案。
      
            
      
          
      
          
      底层原理pub 的版本求解器会在所有约束的交集里选版本；caret 约束 ^1.2.3 允许不破坏 API 的升级。lockfile 记录解析结果，保证同一项目在不同机器上安装一致。
      
          
      常见坑
      • 在库里锁死精确版本，导致下游冲突。
      • 盲目升级主版本；先读 changelog 与迁移指南。
      • 使用长期不维护的包；检查最近发布时间与 issue 响应。
      
        
      

        
      
          
      8.2 Flutter：Dart 的主要下游
      
          
      Flutter 用 Dart 写 UI；本页只给一个最小 Widget 示例，帮助你建立“Dart 代码在真实项目里长什么样”的画面，不承担 Flutter 教学。
      
          
      
            
      dart最小 Flutter Widget（需 Flutter SDK，未在本页执行）需 Flutter
      
            
      import 'package:flutter/material.dart';

void main() => runApp(const HelloApp());

class HelloApp extends StatelessWidget {
  const HelloApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: Scaffold(
        appBar: AppBar(title: const Text('Dart × Flutter')),
        body: const Center(child: Text('Hello from Dart')),
      ),
    );
  }
}
      
          
      
          
      Flutter 项目里，Dart 负责业务逻辑、状态与 UI 声明；框架提供 Widget 树、布局、渲染与平台通道。开发时热重载，发布时 AOT 编译。Dart 语言本身的知识可以完全复用，但 Flutter 的 Widget/状态管理/平台适配是另一套需要单独学习的内容。
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++如果你用过 Qt，Widget 树 + build 方法有点类似声明式 UI；Flutter 不依赖原生控件，而是自绘。
      
              
      Python如果你用过 Kivy/Tkinter，Flutter 的类型安全与热重载更强；但响应式布局与状态管理需要重新学。
      
              
      Dart先掌握本页的语言部分，再学 Flutter 的 Widget、状态与路由；不要把 Flutter 的框架惯例误当成 Dart 语言规则。
      
            
      
          
      
          
      底层原理Flutter 在 Dart 之上实现 Widget/Element/RenderObject 树，通过 Skia/Impeller 自绘；Dart 的 AOT 产物与引擎一起打包。热重载依赖 JIT 与 kernel 增量更新。
      
          
      常见坑
      • 把 Flutter 的 Widget 当成普通 Dart 类去 new；Widget 是不可变配置，build 返回新的树。
      • 在 build 里做重计算/副作用；会频繁执行。
      • 把本页当 Flutter 教程；生态章只是地图，不是路线。
      
        
      

        
      
          
      8.3 服务端与 CLI
      
          
      Dart 可以编译成单文件可执行程序，做 CLI 与服务端都很直接；生态规模比 Python/Node 小，但类型与部署体验是优势。
      
          
      
            
      dart最小 HTTP 服务（需本地运行，未在本页启动）需运行环境
      
            
      import 'dart:io';

Future<void> main() async {
  final server = await HttpServer.bind(InternetAddress.loopbackIPv4, 8080);
  print('listening on http://${server.address.host}:${server.port}');
  await for (final request in server) {
    request.response
      ..write('Hello from Dart')
      ..close();
  }
}
      
          
      
          
      更完整的服务端通常使用 shelf（中间件组合）或 dart_frog（文件路由）等框架。CLI 可以直接用 dart compile exe 发布单文件，启动快、无运行时依赖。CPU 密集的请求处理仍要考虑 isolate，避免阻塞事件循环。
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++你会用 Boost.Asio/HTTP 库；Dart 的 dart:io 更简单，但生态与底层控制不如 C++。发布单文件体验优于大多数 C++ 项目。
      
              
      PythonFlask/FastAPI 的体验接近 shelf/dart_frog；Dart 的静态类型与 AOT 单文件部署是差异点，但第三方库数量少。
      
              
      Dart小型服务/内部工具/CLI 很适合；大型后端要评估生态、数据库驱动、可观测性与团队熟悉度。
      
            
      
          
      
          
      底层原理dart:io 的服务端基于事件循环：每个请求的回调不应长时间阻塞；文件/数据库 I/O 用异步 API。需要 CPU 并行时把工作交给 isolate，主 isolate 继续接收请求。
      
          
      常见坑
      • 在请求处理里跑同步 CPU 循环；整个服务被阻塞。
      • 忽略进程管理/优雅关闭；生产环境需要信号处理与连接排空。
      • 把单文件可执行当成跨平台产物；每个平台要分别编译。
      
        
      

        
      
          
      8.4 与 C++/Python 互操作
      
          
      Dart 通过 C ABI（dart:ffi）调用原生库，通过 Process/JSON/stdio 与 Python 等进程协作；边界越窄，维护成本越低。
      
          
      
            
      dartFFI 片段：调用 C ABI（需本地 libmath，未执行）需本地库
      
            
      import 'dart:ffi';

typedef NativeAdd = Int32 Function(Int32, Int32);
typedef DartAdd = int Function(int, int);

void main() {
  final lib = DynamicLibrary.open('libmath.so');
  final add = lib.lookupFunction<NativeAdd, DartAdd>('add');
  print(add(2, 3));
}
      
          
      
          
      
            
      dart通过进程调用 Python（需 python3，未在本页执行）需 Python
      
            
      import 'dart:io';

Future<void> main() async {
  final result = await Process.run('python3', ['-c', 'print(6 * 7)']);
  print(result.stdout);
}
      
          
      
          
      FFI 只理解 C ABI：C++ 需要 extern "C" 包装，不能直接调用带名称修饰的 C++ 符号；字符串/内存需要手动管理，通常配合 package:ffi 的 Utf8/malloc。Python 互操作优先用进程 + JSON/stdio 或 HTTP，除非性能要求必须同进程。
      
          
      
            
      如果你来自 C++/Python
      
            
      
              
      C++FFI 相当于手写 C 接口绑定；没有 pybind11 那样的自动 C++ 绑定。C++ 侧要暴露稳定的 C ABI，并处理内存所有权。
      
              
      PythonProcess.run 类似 subprocess；JSON/HTTP 是更松耦合的边界。需要共享内存时考虑 FFI + 明确的所有权协议。
      
              
      Dart优先进程/JSON 边界；性能敏感再上 FFI；FFI 调用要保持短小，重计算放 isolate，避免阻塞主线程。
      
            
      
          
      
          
      底层原理dart:ffi 直接调用动态库的 C 符号；Dart 的 GC 不知道原生内存，必须显式分配/释放。DynamicLibrary.open 按平台加载 .so/.dll/.dylib；ABI 不匹配会导致崩溃而不是异常。
      
          
      常见坑
      • 直接查找 C++ 符号；名称修饰导致找不到，需 extern "C"。
      • 把 Dart 字符串直接传给 C；需要 UTF-8 编码与生命周期管理。
      • 在 FFI 调用中做长时间计算；阻塞事件循环。
      
        
      

        
      
          
      8.5 继续学习路径
      
          
      先写一个能跑的小项目，再按目标选路线；不要从框架文档第一页开始“收集式学习”。
      
          
      
            
      路线 A：Flutter语言 → Widget/布局 → 状态管理 → 路由/网络/存储 → 平台通道。适合做跨平台 UI。
      
            
      路线 B：服务端/CLI语言 → dart:io → shelf/dart_frog → 数据库/部署 → isolate/性能。适合工具与后端。
      
          
      
          
        
            
      • 练习 1：把一个小 Python 脚本改写成 Dart CLI，保留原有输入输出，补上测试。
        • 
            
      • 练习 2：用 sealed 类建模一个状态机，用 switch 表达式穷尽处理。
        • 
            
      • 练习 3：写一个事件循环小程序，观察 microtask 与 event 的顺序。
        • 
            
      • 练习 4：把一个 CPU 密集循环移到 Isolate.run，对比主线程响应。
        • 
          
      
          
      官方资源：Dart 语言导览、Dart language evolution、Dart API 文档、pub.dev、Flutter 文档。
      
          
      底层原理学习迁移的难点不是语法，而是心智模型：类型/空安全、GC/引用、事件循环/isolate、工具链/构建目标。把这四组模型校准，剩下的 API 都能查文档。
      
          
      常见坑
      • 只看教程不动手；Dart 的很多细节只有在编译器报错时才会真正记住。
      • 同时学 Dart 与 Flutter；先把语言与事件循环跑通。
      • 过度设计类型层次；先从简单函数与数据类开始。

      B. 常见坑清单
      
          
        
            
      1. final 不是不可变：final list = [1]; list.add(2) 合法。
        2. 
            
      2. 集合 == 是引用相等：[1, 2] == [1, 2] 为 false。
        3. 
            
      3. const 是深不可变：const [1, 2] 不能修改；final 可以。
        4. 
            
      4. late 可能抛错：读取未初始化的 late 字段会抛 LateInitializationError。
        5. 
            
      5. ! 是断言：为 null 时抛运行时错误，不是安全转换。
        6. 
            
      6. async 不是线程：它只让出事件循环；CPU 并行要用 Isolate。
        7. 
            
      7. Future 没有取消：timeout 只让等待方失败，底层任务可能继续。
        8. 
            
      8. 单订阅 Stream：默认只能 listen 一次；需要多订阅用 .broadcast()。
        9. 
            
      9. Web int 精度：超过 253 的整数在 Web 上可能不精确。
        10. 
            
      10. String.length 是 UTF-16 单元：不是用户可见字符数。
        11. 
            
      11. 没有函数重载：用命名参数或不同函数名。
        12. 
            
      12. extension 是静态分派：不会覆盖类方法，也不参与运行时多态。
        13. 
            
      13. List.filled 共享元素：用 List.generate 创建独立元素。
        14. 
            
      14. sealed 直接子类必须同库：间接子类可以跨库，但会被父类分支覆盖。
        15. 
            
      15. FFI 只认 C ABI：C++ 符号需要 extern "C" 包装。
        16. 
            
      16. dart:io 不能进 Web：目标平台决定可用库。
        17. 
          
      
          
      最后一条建议：迁移代码时先让分析器全绿，再处理性能与架构；Dart 的静态检查能免费帮你发现大量 C++/Python 运行时才会暴露的问题。
      
        
      

        
      
          
      C. 术语表
      
          
        
            
      • 健全空安全（sound null safety）：非空类型保证永不为 null，编译器可据此检查与优化。
        • 
            
      • 流分析（flow analysis）：编译器按控制流路径推断变量的已知类型，用于空安全提升等。
        • 
            
      • 具体化泛型（reified generics）：泛型实参保留到运行时，可做 is List<int> 检查。
        • 
            
      • 规范化（canonicalization）：相同 const 表达式共享实例的编译期优化。
        • 
            
      • mixin：把实现混入类的可复用代码单元，按 with 顺序线性化。
        • 
            
      • extension：给已有类型添加静态解析成员的机制，不修改原类型。
        • 
            
      • extension type：零成本静态包装，运行时表示就是底层类型。
        • 
            
      • sealed：封闭直接子类型集合的类修饰符，支持 switch 穷尽检查。
        • 
            
      • record：位置/命名字段组成的不可变值类型，自带结构化相等。
        • 
            
      • pattern：类型检查 + 解构 + 绑定的语法结构，用于 switch/if-case。
        • 
            
      • event loop：单线程事件循环，按 microtask → event 的顺序调度。
        • 
            
      • microtask：优先级高于 event 的短任务队列，await 续体通常走这里。
        • 
            
      • isolate：独立堆与事件循环的执行单元，通过消息通信。
        • 
            
      • JIT/AOT：即时编译/提前编译；开发与发布的两种运行形态。
        • 
            
      • tree shaking：构建时移除未使用代码，减小发布产物。
        • 
            
      • tear-off：把方法或函数引用当作值传递，如 list.add。
