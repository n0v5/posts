Part 0 · Orientation

导言：先换脑，再换语法

Rust 的语法看起来像 C++/TypeScript 的混合体，但它的核心是所有权与借用。你从 C++/Python 带来的经验一半可以直接复用，另一半需要重新校准。这一部分先建立判断标准，后面每一章都按同一套结构展开。

0.1 Rust 是什么、不是什么

Rust 是一门用编译期检查替代 GC 的系统语言：所有权保证内存安全，借用规则保证别名与可变性互斥，trait 提供零成本抽象。

Rust 的三个核心承诺是：无 GC 的内存安全、无畏并发（fearless concurrency）、零成本抽象。代价是所有权与生命周期需要显式设计，编译器会更频繁地拒绝你的代码；async、unsafe 与宏也各有自己的复杂度。它适合 CLI、服务端、嵌入式、WebAssembly、区块链与需要稳定性能的系统组件。

它不是“更安全的 C++”：Rust 没有 C++ 的继承体系、模板元编程与稳定 ABI，也不试图兼容 C++ 的对象模型。它也不是“更快的 Python”：动态类型的便利需要用 trait、枚举与显式错误处理来重建。把 Rust 当成一门需要重新设计数据所有权的语言，而不是换一套关键字。

rusthello.rsPlayground ↗
fn main() {
    let name = "Rust";
    let edition = 2024;
    println!("Hello, {name}! (Edition {edition})");
}
如果你来自 C++/Python
C++你熟悉 RAII、值语义、模板与手动内存管理。Rust 保留了“资源在作用域结束时释放”的直觉，但把释放交给 Drop，并用借用检查器阻止悬垂引用与数据竞争。
Python你熟悉引用、GC、鸭子类型与异常。Rust 用所有权替代 GC，用 trait 替代隐式协议，用 Result 替代异常作为可恢复错误的主路径。
Rust先问三个问题：这个值归谁所有？谁需要借用它？借用会持续多久？答案会决定类型、函数签名与数据结构。
底层原理Rust 在编译期检查所有权与借用，运行时没有 GC 扫描；值在离开作用域时由编译器插入 drop。泛型默认单态化，trait 分派可以是静态的，也可以是 vtable 动态分派；Rust 没有稳定的跨编译器 ABI，FFI 需要显式 C ABI。
常见坑
  • 用 clone() 让编译器闭嘴；先问“这个值真的需要复制吗”。
  • 把 unsafe 当成绕过所有权的快捷键；它是需要证明安全契约的工具。
  • 期待异常式错误处理；Rust 的 Result 是普通值，必须显式处理或传播。

如果你来自 C++/Python
C++赋值通常复制或移动，取决于类型与移动构造；Rust 对非 Copy 类型的赋值默认是移动，之后原变量不可再用。
Python赋值只是给同一个对象再绑定一个名字；Rust 要么移动所有权，要么显式借用，不能悄悄共享可变引用。
Rust“一个值同一时间只有一个所有者”是最重要的直觉；共享用 Rc/Arc，可变共享用 RefCell/Mutex，跨线程共享用 Arc<Mutex<T>>。
底层原理Rust 的值通常分配在栈上，堆分配由 Box/String/Vec 等类型管理；移动是位复制加所有权转移，原变量在编译期被标记为不可用。离开作用域时，编译器按声明顺序的反向插入 drop。
常见坑
  • 把 Rust 的 move 当成 C++ 的移动构造；Rust 的移动不保证调用任何用户代码。
  • 以为 Rc 能解决循环引用；Rc 不回收环，需要 Weak。
  • 用共享可变状态设计并发；Rust 会强迫你显式选择锁、通道或消息传递。

0.3 版本、Edition 与使用方式

本页以 Rust 1.99.1 / Edition 2024 为页面基线；所有完整示例只使用本机 Rust 1.96.1 已稳定的特性，并逐条通过 cargo check / cargo test。

Rust 每六周发布一个稳定版，Edition 每三年左右发布一次；Edition 不是破坏性升级，而是让新语法/默认行为在包级别生效。Edition 2024 于 Rust 1.85 稳定，包含 unsafe extern、RPIT 生命周期捕获调整、Future/IntoFuture 进入 prelude、把 gen 保留为关键字等变化。

关于“可运行”本页所有未标注环境限制的完整 Rust 示例，都在 Rust 1.96.1 / Edition 2024 下通过 cargo check，并执行核对过输出。Tokio、FFI、PyO3、Miri 与特定平台的示例会明确标注，不冒充本地已验证。
底层原理Rust 的“稳定”是编译器、标准库与 Cargo 的稳定性承诺；nightly 只用于实验特性与工具（如 Miri）。Edition 由每个 crate 的 Cargo.toml 决定，不同 crate 可以使用不同 Edition，通过 Cargo 的 resolver 协调。
常见坑
  • 在正文示例里使用 nightly 特性，读者用 stable 无法编译。
  • 把 Edition 2024 当成“Rust 4”；它仍是 Rust 1.x 的包级 Edition。
  • 忽略 Cargo.toml 的 edition 字段；新语法可能因 Edition 不同而不可用。

Part 1 · Toolchain & Project

工具链与项目：先把工程跑起来

Rust 的工具链比 C++ 统一得多：rustup 管工具链，rustc 管编译，cargo 管项目、依赖、测试、格式化和文档。这一部分从安装讲到 crate/package/module 的边界，并与 CMake/Conan 与 pip/venv 做对照。

1.1 rustup、rustc 与 cargo

rustup 管理工具链，rustc 是编译器，cargo 是项目与依赖的编排器；日常几乎只直接使用 cargo。

rustup 负责安装 stable/beta/nightly、切换默认工具链、安装组件（rustfmt、clippy、rust-analyzer）和交叉编译 target。rustc 是实际的编译器，通常由 cargo 调用。cargo 读取 Cargo.toml，解析依赖、调用 rustc、运行测试、生成文档并管理 target 目录。

shell安装与检查工具链
rustup show
rustup component add rustfmt clippy rust-analyzer
rustup target add x86_64-unknown-linux-gnu
rustc --version
cargo --version
如果你来自 C++/Python
C++编译器（gcc/clang/MSVC）、构建系统（CMake/Make/Ninja）与包管理器（Conan/vcpkg）是分开的；Rust 把三者收进 rustup + cargo 一套入口。
Pythonpyenv/venv 管解释器与虚拟环境，pip/uv 管包；Rust 的 rustup 管工具链，cargo 同时管依赖、构建、测试与文档。
Rust项目内用 cargo；只有需要直接传 rustc 参数、查看 LLVM IR 或做特殊构建时才直接调用 rustc。
底层原理rustup 通过 toolchain 目录与 shim 选择 rustc/cargo 版本；target triple 描述 CPU/厂商/系统/ABI。cargo 最终把编译单元交给 rustc，并管理依赖图与增量编译缓存（target/）。
常见坑
  • 混用系统包管理器安装的 Rust 与 rustup 的 Rust，导致版本不可控。
  • 把 nightly 设为全局默认，却忘记项目需要 stable。
  • 直接调用 rustc 编译多文件项目，绕过 cargo 的依赖与特性解析。

1.2 创建项目与 Cargo.toml

cargo new 生成项目骨架，Cargo.toml 描述包元数据、Edition、依赖、features 与 workspace。

一个 package 至少包含一个 crate：src/main.rs 是二进制 crate，src/lib.rs 是库 crate；也可以同时存在。Cargo.lock 固定依赖解析结果；应用通常提交 lockfile，库通常不提交。workspace 让多个 package 共享依赖与 target 目录。

toml最小 Cargo.toml
[package]
name = "hello_rust"
version = "0.1.0"
edition = "2024"

[dependencies]
# serde = { version = "1", features = ["derive"] }
tomlworkspace：多个 package 共享依赖与 target
[workspace]
members = ["app", "core", "cli"]
resolver = "3"
如果你来自 C++/Python
C++Cargo.toml 同时承担包描述、依赖声明与构建配置；没有 CMakeLists 的 target/link 语法，构建脚本通过 build.rs 扩展。
Pythonpyproject.toml 与 Cargo.toml 类似，但 Cargo 的 feature、workspace 与 lockfile 语义更严格；Rust 没有虚拟环境，依赖缓存在全局 registry。
Rust应用提交 Cargo.lock；库放宽依赖约束，不提交 lockfile；workspace 适合 monorepo 与“核心库 + CLI + 服务”结构。
底层原理Cargo 使用语义化版本与 resolver 解析依赖图，features 是编译期开关，可能改变依赖图与 API。workspace 共享 lockfile 与 target 目录，减少重复编译。
常见坑
  • 在库里锁死精确版本，导致下游依赖冲突。
  • 把 Cargo.lock 忽略掉，部署时版本漂移。
  • 在 workspace 中忘记统一 Edition/MSRV，导致成员 crate 行为不一致。

1.3 第一个程序与日常命令

cargo run 构建并运行，cargo test 跑测试，cargo fmt/clippy 管格式与 lint，cargo doc 生成文档。

先写一个带单元测试的最小程序。测试模块用 #[cfg(test)] 只在测试构建中编译；cargo test 会运行所有测试。cargo clippy -- -D warnings 把 lint 警告当作错误，适合 CI。

读编译错误的顺序：先看 error 的位置与 span，再看 help 建议，最后看 note。Rust 的错误信息通常会给出“为什么”和“怎么修”；borrow checker 错误尤其如此。不要第一反应加 clone()，先理解借用冲突。

如果你来自 C++/Python
C++cargo build/run/test 替代 make/cmake + 测试框架 + 文档工具的组合；编译错误通常比模板报错更可读。
Pythoncargo test 内建测试运行器，cargo doc 内建文档生成；不需要 pytest + sphinx 才能开始。
Rust把 cargo fmt/clippy 放进保存钩子与 CI；把 cargo test 作为最低门槛。
底层原理cargo 默认使用 dev profile（调试信息、溢出检查开启），--release 使用 release profile（优化、溢出检查默认关闭）。测试、示例、基准可各自有 profile 配置。
常见坑
  • 用 cargo run --release 才发现整数溢出行为变了。
  • 忽略 clippy 的 needless_clone/borrow_deref_ref 等提示，长期积累坏习惯。
  • 把 unwrap() 留在库代码里，调用方无法选择错误处理策略。

1.4 crate、package 与 module

package 是 Cargo 管理的单位，crate 是编译单位，module 是命名空间与可见性边界。

一个 package 可以包含一个库 crate 和多个二进制 crate；src/lib.rs 是库根，src/main.rs 是默认二进制根，src/bin/*.rs 是额外二进制。module 用 mod 声明，默认私有；pub 暴露给外部，pub(crate) 只在当前 crate 可见。

rust模块、可见性与路径Playground ↗
mod math {
    pub fn add(a: i32, b: i32) -> i32 {
        a + b
    }

    pub mod stats {
        pub fn mean(values: &[f64]) -> Option<f64> {
            if values.is_empty() {
                return None;
            }
            Some(values.iter().sum::<f64>() / values.len() as f64)
        }
    }
}

fn main() {
    println!("{}", math::add(2, 3));
    println!("{:?}", math::stats::mean(&[1.0, 2.0, 3.0]));
}

外部依赖从 crates.io 获取，文档在 docs.rs；Rust Playground 适合验证 std-only 片段。发布库时，公共 API 从 lib.rs 用 pub use 导出，内部实现放在私有 module 中。

如果你来自 C++/Python
C++namespace 只影响名字，不影响链接边界；crate 是编译/链接单位，module 是可见性单位。Rust 没有头文件，接口由 pub 决定。
Pythonmodule 是 .py 文件，package 是目录；Rust 的 crate 更接近“编译好的库”，module 才是命名空间。
Rustpub 到最小必要范围；内部实现放私有 module；公共 API 用 pub use 收敛入口。
底层原理crate 是 rustc 的编译单元，crate 之间通过 metadata 与目标文件链接；module 在编译期解析为路径与可见性。Rust 没有稳定 ABI，crate 之间的接口由编译器版本与 metadata 保证兼容。
常见坑
  • 把 pub 加在 mod 上以为成员自动公开；成员仍需单独 pub。
  • 把内部实现放在 lib.rs 根，意外成为公共 API。
  • 混淆 crate::、super::、self:: 的路径起点。

  • 忽略 MSRV；新 Cargo 版本可能默认要求更高的 rustc。

Part 2 · Syntax & Types

语法与类型系统：把 C++/Python 直觉校准

Rust 的语法不复杂，但默认不可变、没有隐式数值转换、字符串是 UTF-8、模式匹配必须穷尽。这些规则共同构成“编译器先帮你排除一类错误”的基础。这一部分从变量讲到模块与模式匹配。

2.1 变量、可变性与 shadowing

Rust 变量默认不可变；需要修改时显式写 mut。shadowing 用新的 let 绑定覆盖旧名字，可以改变类型。

let 是绑定，不是赋值；let x = 1; let x = x + 1; 创建了一个新的绑定，旧值被遮蔽。这与 mut 修改同一个变量不同：shadowing 可以改变类型，也可以让变量在后续代码中重新变为不可变。const 要求编译期常量，static 是全局静态量，访问可变静态量需要 unsafe（Edition 2024 对 static mut 有更严格限制）。

rustlet、mut、shadowing 与 constPlayground ↗
fn main() {
    let x = 1;
    let x = x + 1; // shadowing：新绑定，类型可以改变
    let mut y = 10;
    y += 5; // 修改同一个变量
    const MAX: u32 = 100;
    println!("{x} {y} {MAX}");
}
如果你来自 C++/Python
C++auto 推断但默认可变；Rust 默认不可变，let mut 才可变。C++ 的 const 与 Rust 的 const 语义不同：Rust 的 const 是编译期常量，不占运行时存储。
Python名字只是绑定，随时可重新赋值；Rust 用 mut 明确允许修改，用 shadowing 表达“换一个值/类型继续用同一个名字”。
Rust默认不可变，需要时再加 mut；不要为了避免 mut 而滥用 shadowing；const 与 static 只在确实需要全局/编译期值时使用。
底层原理不可变绑定让编译器更容易做别名与优化分析；mut 只表示“这个绑定允许可变借用”，不代表运行时锁或线程安全。shadowing 的旧变量仍在作用域内，只是名字被新绑定遮蔽。
常见坑
  • 到处写 let mut，失去“默认不可变”的设计信号。
  • 把 shadowing 当作修改原变量；旧值仍然存在，只是不可访问。
  • 用 static mut 做全局状态；优先 OnceLock/Mutex/Atomic*。

2.2 标量与复合类型

Rust 的整数有明确位宽，溢出行为在 debug/release 下不同；char 是 Unicode 标量值，不是单字节。

整数类型包括 i8–i128、u8–u128、isize/usize；浮点是 f32/f64；bool、char 是独立类型。tuple 是固定长度、可异构的组合；array 是固定长度、同类型；slice 是借用的一段连续元素。Rust 不做隐式数值转换，as 是显式转换，可能截断。

rust标量、tuple、array 与 slicePlayground ↗
fn main() {
    let a: i32 = 42;
    let b = 2.5;
    let c = '中';
    let t = (1, "two", 3.0);
    let arr = [1, 2, 3];
    let slice = &arr[1..];
    println!("{a} {b} {c} {t:?} {slice:?}");
}
如果你来自 C++/Python
C++Rust 默认没有隐式数值转换，整数溢出在 debug 下 panic、release 下按二进制补码回绕（可通过 profile 配置改变）；char 是 4 字节 Unicode 标量，不是 char8_t。
Pythonint 是任意精度；Rust 的整数有固定位宽，Web/跨平台场景要显式选择类型。Python 的字符串索引是码点，Rust 的字符串不能按整数索引。
Rust需要跨平台稳定宽度时用 i32/u64 等；索引用 usize；边界处显式 try_into()，不要依赖 as 的截断。
底层原理Rust 的数组长度是类型的一部分（[T; N]），slice 是“指针 + 长度”的胖指针；索引会做边界检查，越界 panic。整数溢出检查由编译 profile 控制。
常见坑
  • 把 usize 与固定宽度整数混用，导致 32/64 位平台差异。
  • 用 as 做有损转换而不检查范围。
  • 把 char 当 UTF-8 字节；一个 char 可能占多个字节。

2.3 String、&str 与切片

String 拥有堆上的 UTF-8 字节，&str 是借用的字符串切片；字符串不能按整数下标索引。

String 可增长、可修改，&str 是对 UTF-8 字节的借用视图；字符串字面量是 &'static str。Rust 不允许 s[0]，因为 UTF-8 字符长度可变；需要按字节用 as_bytes()，按 Unicode 标量用 chars()，按用户可见字形用 unicode-segmentation 等库。

rustString、&str、chars 与 format!Playground ↗
fn main() {
    let owned = String::from("hello");
    let view: &str = &owned;
    println!("{view} len={}", view.len());
    for ch in "你好".chars() {
        println!("{ch}");
    }
    let s = format!("{owned}, world");
    println!("{s}");
}
如果你来自 C++/Python
C++String 类似拥有所有权的 std::string，&str 类似 std::string_view；Rust 保证 UTF-8 有效，长度是字节数。
Pythonstr 是不可变 Unicode 码点序列，切片按码点；Rust 的 &str 按字节切片，切在非字符边界会 panic，需要用 char_indices() 或库。
Rust函数参数优先 &str，返回/存储用 String；需要修改时用 String 或 &mut str（有限场景）。
底层原理&str 是“指针 + 字节长度”的胖指针；String 是 Vec<u8> 的 UTF-8 封装。切片越界或切在 UTF-8 非边界处会 panic；chars() 解码 UTF-8，bytes() 遍历原始字节。
常见坑
  • 写 s[0] 取第一个字符；应使用 chars().next()。
  • 用 &String 作为函数参数；优先 &str。
  • 按字节切片中文/emoji，切在字符中间导致 panic。

2.4 函数与控制流

Rust 是表达式导向的语言：块的值是最后一个表达式；if/match/loop 都能产生值。

函数签名必须标注参数与返回类型；最后一行没有分号时是返回值，有分号则返回 ()。if 可以作为表达式，但各分支类型必须一致；loop 可以用 break value 返回值；match 必须穷尽。

rust表达式、match 与 loopPlayground ↗
fn classify(n: i32) -> &'static str {
    match n {
        0 => "zero",
        x if x < 0 => "negative",
        _ => "positive",
    }
}

fn main() {
    for n in [-1, 0, 1] {
        println!("{}: {}", n, classify(n));
    }
    let mut i = 0;
    let result = loop {
        i += 1;
        if i == 3 {
            break i * 10;
        }
    };
    println!("{result}");
}
如果你来自 C++/Python
C++if/switch 是语句；Rust 的 if/match 是表达式。for 在 Rust 中遍历 IntoIterator，不是 C 风格三段式。
PythonPython 的 for 也是迭代；Rust 的 match 更像带类型解构的 match，但必须穷尽，且没有隐式 fallthrough。
Rust用 match 表达分支与解构；用 if let 处理单个模式；用 let else 提前返回；用 loop 表达无限循环与带值退出。
底层原理表达式导向让控制流与值组合更自然；! 是发散类型（return/panic!/break），可以出现在任何需要值的位置。match 的穷尽性由类型系统检查。
常见坑
  • 在最后一行加了分号，函数返回 () 而不是目标类型。
  • 在 if 两个分支返回不同类型，导致类型错误。
  • 在 match 中漏掉分支；编译器会报非穷尽。

2.5 模块、路径与可见性

Rust 用 module 组织命名空间，用 pub 控制可见性；路径以 crate/super/self 或外部 crate 名开头。

内联 module 用 mod name { ... }，文件 module 用 mod name; 并在同目录提供 name.rs 或 name/mod.rs。默认私有；pub 公开给外部，pub(crate) 只在当前 crate 公开，pub(super) 只在父 module 公开。use 只是引入名字，不会自动重导出；需要重导出时写 pub use。

rust模块树与 pub(crate)Playground ↗
mod api {
    pub(crate) fn version() -> &'static str {
        "1.0"
    }

    pub fn health() -> String {
        format!("ok {}", version())
    }
}

fn main() {
    println!("{}", api::health());
}
如果你来自 C++/Python
C++namespace 不控制链接可见性；Rust 的 pub 是编译期可见性。Rust 没有头文件，公共 API 由 pub 与 pub use 决定。
Pythonmodule/package 的边界更松，下划线只是约定；Rust 的私有是强制的，外部 crate 无法访问非 pub 项。
Rust把公共 API 收敛到 lib.rs 的 pub use；内部 module 保持私有；跨 module 共享用 pub(crate)。
底层原理module 在编译期形成名称解析树；可见性检查发生在类型检查阶段。crate 是隐私边界，pub(crate) 不会泄露到外部 crate。Rust 没有头文件，因此不需要“声明与定义分离”。
常见坑
  • 给 mod 加 pub 却忘记给其中成员加 pub。
  • 用 use 以为会重导出；外部仍然看不到。
  • 文件 module 的路径与 mod 声明不匹配，导致找不到模块。

2.6 模式匹配与解构

模式匹配把类型检查、解构与绑定合并在一起；Rust 的 match 必须穷尽，if let/while let/let else 处理单个分支。

模式可以匹配字面量、范围、tuple、struct、enum、引用与切片；| 组合模式，@ 绑定同时测试，_ 忽略值。match ergonomics 让匹配引用时自动按引用绑定，减少 ref/& 噪声。

ruststruct 解构、if let 与 let elsePlayground ↗
struct Point {
    x: i32,
    y: i32,
}

fn main() {
    let p = Point { x: 0, y: 2 };
    let Point { x, y } = p;
    println!("{x} {y}");
    if let Point { x: 0, y } = p {
        println!("on y-axis at {y}");
    }
    let Some(n) = Some(5) else {
        return;
    };
    println!("{n}");
}
如果你来自 C++/Python
C++switch 只匹配整数/枚举，容易 fallthrough；Rust 的 match 可以解构任意类型，且必须穷尽。
Pythonmatch 也支持结构模式，但不是编译期穷尽检查；Rust 在 enum/struct 上会强制覆盖所有 variant/字段组合。
Rust用 enum + match 建模状态；用 let else 提前返回；用 @ 同时绑定与测试；避免在模式里塞复杂逻辑。
底层原理模式匹配在编译期展开为类型测试与字段访问；match 的穷尽性由类型定义（尤其是 enum/sealed 风格）保证。匹配可能移动或借用被匹配的值，取决于模式与类型是否 Copy。
常见坑
  • 在 match 中移动了值，之后还想使用原变量。
  • 忘记 _ 兜底，导致非穷尽错误。
  • 在 if let 中匹配引用时，对绑定类型感到困惑；先看 match ergonomics。

Part 3 · Ownership & Borrowing

所有权与借用：Rust 的核心

所有权不是“Rust 的 GC 替代品”这么简单，它是一套关于值、别名与生命周期的编译期约束。理解 move、borrow 与 NLL，后面的生命周期、并发与 async 才有地基。这一部分建议慢读，并配合 D01 演示。

3.1 所有权三条规则

所有权（ownership）：每个值有且只有一个所有者；所有者离开作用域时值被 drop；赋值或传参默认移动所有权（Copy 类型除外）。

所有权让 Rust 在没有 GC 的情况下保证内存安全：不会 double free，也不会有悬垂引用。代价是你必须设计“谁拥有这个值”。String、Vec、Box 等拥有堆数据的类型在赋值时移动；i32、bool、char、不可变引用等实现了 Copy，赋值时按位复制。

rust移动、克隆与作用域结束Playground ↗
fn consume(s: String) {
    println!("{s}");
}

fn main() {
    let a = String::from("hello");
    consume(a);
    // println!("{a}"); // error: moved
    let b = String::from("world");
    let c = b.clone();
    println!("{b} {c}");
}
如果你来自 C++/Python
C++RAII 也把释放绑定到作用域，但 C++ 允许复制、移动、共享与悬垂指针；Rust 把“谁拥有”变成编译期唯一所有权，悬垂引用直接编译失败。
Python引用计数 + GC 让多个名字共享对象；Rust 的非 Copy 赋值会移动，原名字失效。需要共享时显式用 Rc/Arc。
Rust函数接收 String 表示“拿走所有权”；接收 &str/&T 表示“只借用”。先设计所有权，再写函数签名。
底层原理移动是位复制 + 所有权转移，编译器把原变量标记为不可用；不会调用 C++ 那样的移动构造。所有权结束时，编译器插入 drop 调用，按字段声明顺序反向释放。
常见坑
  • 移出结构体字段后继续使用整个结构体；部分移动会让原值不可用。
  • 以为 clone() 总是廉价；它可能是深拷贝。
  • 把引用当拥有者返回；返回局部变量的引用会被拒绝。

3.2 Move、Copy 与 Clone

Copy 是隐式的按位复制，Clone 是显式的可能深拷贝；非 Copy 类型赋值默认移动。

Copy 只能用于所有字段都 Copy 的类型，且不能与 Drop 共存；它让赋值、传参、数组重复等行为像整数一样简单。Clone 需要显式调用 .clone()，可以是浅拷贝也可以是深拷贝，取决于实现。需要从借用中拿走值时，常用 std::mem::take/replace，或先 clone。

rustCopy 与 move 的行为差异Playground ↗
fn main() {
    let x = 5;
    let y = x; // Copy：x 仍然可用
    println!("{x} {y}");

    let s = String::from("hi");
    let t = s; // Move：s 不再可用
    println!("{t}");
    // println!("{s}"); // error
}
如果你来自 C++/Python
C++复制/移动由拷贝构造、移动构造与赋值运算符决定；Rust 的移动是编译器行为，不调用用户代码。Clone 更接近显式深拷贝。
Python赋值永远绑定同一个对象；Rust 的 move 让原名字失效，避免两个所有者同时释放同一块内存。
Rust小类型优先 Copy；大对象需要复制时显式 clone；从 &mut T 拿走值用 mem::take/replace，避免无谓 clone。
底层原理Copy 类型按位复制，不拥有堆资源；Clone 可以分配新内存并复制内容。移动不复制堆数据，只复制指针/长度等元数据并转移所有权。带 Drop 的类型不能实现 Copy，否则会出现双重释放。
常见坑
  • 给带 Drop 的类型实现 Copy，编译器会拒绝。
  • 从借用内容中 move 出来；需要 clone 或 mem::take。
  • 为了“简单”给所有类型 derive Copy，扩大值复制成本。

3.3 借用与 NLL

借用（borrowing）：同一时间要么有多个共享借用 &T，要么有一个可变借用 &mut T；借用范围由 NLL 按实际使用计算。

借用检查器阻止数据竞争与悬垂引用：共享借用只读，可变借用独占。NLL（Non-Lexical Lifetimes）让借用在使用结束后就释放，而不是等到整个作用域结束，因此很多“看起来冲突”的代码可以通过。冲突的常见修法是缩小借用范围、拆分结构体、返回拥有所有权的值，或显式使用 clone。

rust共享借用结束后再可变借用Playground ↗
fn main() {
    let mut s = String::from("hello");
    let r = &s;
    println!("{}", r.len());
    // s.push_str("!"); // error while r is borrowed
    let m = &mut s;
    m.push('!');
    println!("{s}");
}

3.4 所有权 API 设计

          
函数参数能借用就不要拿走所有权；返回新值而不是返回局部引用；需要灵活输入时用 &str/&[T]/impl AsRef。

          
常见 API 约定：只读参数用 &T，字符串用 &str，切片用 &[T]；需要存储或返回时用拥有所有权的类型；需要接受多种字符串类型时用 impl AsRef<str> 或 impl Into<String>；需要“有时借用、有时拥有”时用 Cow<'a, str>。

fn main() {
    let owned = String::from("Ada");
    println!("{}", greet(&owned));
    println!("{}", greet("Grace"));
}

          

          

            
如果你来自 C++/Python

            

              
C++你会用 const T& 表示只读借用；Rust 的 &T 类似，但没有空引用，且借用检查器保证生命周期。

              
Python你不需要声明借用；Rust 的签名是 API 契约，告诉调用方“会不会拿走你的对象”。

常见坑
  • 返回 &String 而不是 &str，限制调用方。
  • 为了“通用”给所有参数加 impl AsRef，导致类型推断困难与代码膨胀。
  • 接受 &Vec<T> 而实际只需要切片。

C++Rust 没有“手动 new/delete”的日常路径，也没有拷贝构造/移动构造；对象默认 move，复制要显式 clone。这消除了大量悬垂指针与双重释放。

Rust先用所有权与借用解决 90% 的问题；剩下的共享/内部可变性再用 Rc/RefCell/Arc/Mutex，不要反过来。

            

          

          
底层原理Rust 的所有权检查在编译期完成，运行时没有引用计数开销（除非显式使用 Rc/Arc）；Python 的引用计数在运行时维护，GC 处理循环；C++ 的 RAII 依赖作用域与正确实现。

          
常见坑
  • 把 Rust 当成“没有 GC 的 Python”，忽视所有权设计。
  • 把 Rc 当线程安全共享；Rc 不是 Send。
  • 用 Arc<Mutex<T>> 保护所有东西，造成锁竞争。

        

      


      

        

          
Part 4 · Lifetimes & Smart Pointers

          
生命周期与智能指针：让借用活得足够久

          
生命周期不是“值活多久”，而是“引用在多长时间内保证有效”。当借用无法用栈上的单一所有者表达时，就需要智能指针与内部可变性。这一部分从 'a 讲到 Pin，并给出常见错误的修法。

        


        

          
4.1 生命周期标注与省略

          
生命周期（lifetime）参数描述引用之间的有效范围关系；大多数函数不需要手写，省略规则会推断常见模式。

          
'a 是生命周期参数，不是“让值活得更久”的开关。编译器用它证明返回的引用不会超过输入引用的有效期。函数返回引用时，如果无法从参数唯一确定生命周期，就需要显式标注；结构体持有引用时，也需要生命周期参数。省略规则覆盖了 &self、单个输入引用、以及“输出与唯一输入同生命周期”等常见情况。

          

            
rust返回两个输入中较长的引用Playground ↗

            
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

fn main() {
    let a = String::from("long");
    let b = String::from("short");
    println!("{}", longest(&a, &b));
}

如果你来自 C++/Python

            

              
C++引用/指针的有效期由开发者保证；Rust 把“引用不能比所指对象活得更久”变成编译期约束。生命周期参数不是运行时对象。

              
Python引用由 GC 保活；Rust 没有 GC 保活，必须证明引用在有效范围内。返回局部变量引用在 Rust 中直接编译失败。

              
Rust先让编译器推断；只有返回引用、结构体持引用、多个输入引用时才考虑标注。不要为了“看起来严谨”给所有引用加 'a。

            

          

          
底层原理生命周期是借用检查器使用的符号区间；编译器用子类型关系验证“长生命周期引用可以当作短生命周期引用使用”。标注不会改变运行时行为，只提供证明所需的关系。

          
常见坑
  • 把 'static 当成“所有引用都该是 static”；它表示整个程序有效，通常只用于字面量或真正的全局数据。
  • 返回局部变量的引用；应返回拥有所有权的值。
  • 给所有函数加生命周期参数，导致签名复杂；先看省略规则。

        


        

          
4.2 常见生命周期错误

          
结构体持有引用时必须带生命周期；返回的引用必须来自输入或 'static 数据；'static 不是“静态变量”的同义词。

          
解析器、视图、零拷贝切片等类型常持有 &'a str。这要求结构体实例不能比输入数据活得更久。impl<'a> Parser<'a> 中的 'a 连接了结构体字段与输入。若确实需要跨作用域保存，改用 String 拥有数据，或使用索引/区间而不是引用。

          

            
rust结构体持有引用：Parser<'a>Playground ↗

            
struct Parser<'a> {
    input: &'a str,
}

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self {
        Self { input }
    }

    fn rest(&self) -> &'a str {
        self.input
    }
}

fn main() {
    let text = String::from("abc");
    let p = Parser::new(&text);
    println!("{}", p.rest());
}

          

          

            
如果你来自 C++/Python

            

              
C++string_view 不拥有数据，持有者必须保证原字符串存活；Rust 的 Parser<'a> 把同一约束写进类型，编译器会阻止悬垂。

              
Python切片会创建新对象（或至少由 GC 管理），不存在悬垂；Rust 的零拷贝视图更高效，但必须显式管理生命周期。

              
Rust需要“视图”时先问：它会不会比原数据活得更久？会，就用拥有所有权的类型；不会，再用生命周期参数。

            

          

          
底层原理结构体中的引用字段必须有一个生命周期参数，表示“这个结构体不能比引用数据活得更久”。编译器在结构体实例的整个生命周期内检查该约束；返回 &'a str 时，'a 来自输入而不是局部变量。

          
常见坑
  • 把 'static 加到局部引用上，试图消除错误；编译器会拒绝。
  • 结构体字段用 &str 却不想加生命周期参数；改用 String。
  • 返回 &self.field 时错误地标成输入的生命周期；应遵循省略规则或显式绑定 &self。

        


        

          
4.3 Box、Rc、Arc 与 Weak

          
Box 是独占堆分配，Rc 是单线程共享所有权，Arc 是线程安全共享所有权，Weak 打破循环引用。

          
Box<T> 把值放到堆上，常用于递归类型（如链表节点）和 trait object。Rc<T> 通过非原子引用计数共享所有权，克隆只增加计数，不是深拷贝；Arc<T> 使用原子计数，可跨线程，但开销更大。Rc/Arc 不会自动处理循环引用，需要 Weak 持有“不拥有”的引用。

          

            
rustBox、Rc 与 ArcPlayground ↗

            
use std::rc::Rc;
use std::sync::Arc;

fn main() {
    let boxed = Box::new(5);
    println!("{}", *boxed);

    let a = Rc::new(String::from("shared"));
    let b = Rc::clone(&a);
    println!("{} {}", a, b);

    let c = Arc::new(7);
    println!("{}", c);
}

          

          

            
如果你来自 C++/Python

            

              
C++Box 类似 unique_ptr，Rc/Arc 类似 shared_ptr，Weak 类似 weak_ptr；Rust 的 Rc 不是线程安全的。

              
Python所有对象都由引用计数/GC 管理，没有“独占 vs 共享”的显式类型；Rust 让共享成本可见，Arc 的原子操作不是免费的。

              
Rust能独占就 Box；单线程共享用 Rc；跨线程共享用 Arc；有环就用 Weak 或重构数据结构。

            

          

          
底层原理Box 是一个指针，析构时释放堆内存；Rc 在堆上维护强/弱计数，计数归零时释放值；Arc 用原子操作维护计数，因此可在多线程间共享。Weak 不增加强计数，升级时可能失败。

          
常见坑
  • 用 Rc 跨线程；它不实现 Send，编译器会拒绝。
  • 构造 Rc/Arc 循环引用，导致内存泄漏；用 Weak 打破环。
  • 在热路径频繁克隆 Arc，原子操作成为瓶颈。

        


        

          
4.4 内部可变性

          
Cell/RefCell 在单线程内把借用检查推迟到运行时；Mutex/RwLock 在多线程内提供同步。

          
有时你需要在共享引用后面修改数据：RefCell<T> 在运行时检查“共享/可变借用”规则，违反会 panic；Mutex<T> 用锁保护数据，RwLock<T> 允许多个读者或一个写者。它们不是“绕过借用检查”的免费通行证：RefCell 不能跨线程，Mutex 有锁竞争与中毒，RwLock 有写者饥饿风险。

          

            
rustRc<RefCell<T>>：单线程共享可变Playground ↗

            
use std::cell::RefCell;
use std::rc::Rc;

fn main() {
    let value = Rc::new(RefCell::new(0));
    let a = Rc::clone(&value);
    *a.borrow_mut() += 1;
    println!("{}", value.borrow());
}

          

          

            
如果你来自 C++/Python

            

              
C++mutable 允许 const 方法修改成员；Mutex/RwLock 提供同步。Rust 把“共享 + 可变”显式建模为 RefCell 或锁。

              
Python对象默认可变，GIL 让单线程语义简单；Rust 会在编译期阻止共享可变引用，迫使你选择运行时检查或锁。

              
Rust优先重构为“所有权 + 消息传递”；确实需要共享可变状态时，单线程用 Rc<RefCell<T>>，多线程用 Arc<Mutex<T>>。

            

          

          
底层原理RefCell 内部维护借用标志，borrow/borrow_mut 在运行时检查规则，冲突时 panic；Mutex 用操作系统锁，锁中毒表示持锁线程 panic；RwLock 维护读者/写者计数。

          
常见坑
  • 同时持有 RefCell 的 borrow 与 borrow_mut，运行时 panic。
  • 把 Rc<RefCell<T>> 跨线程使用；它不是 Send。
  • 在持有 MutexGuard 时执行长时间操作，扩大锁竞争。

        


        

          
4.5 自引用与 Pin

          
Pin 保证被固定的值不会在内存中移动；async Future 可能持有指向自身字段的引用，因此需要 Pin。

          
Rust 默认可以移动值；自引用结构一旦移动，内部指针就会悬垂。Pin<P> 是一个包装，承诺“只要不被 Unpin，值就不会被移动”。大多数类型实现了 Unpin，可以自由移动；async 块生成的 Future 通常是 !Unpin，需要用 Box::pin 或运行时提供的 pin! 固定。日常业务代码很少需要手写自引用结构，优先用索引、String 或 Arc 重构。

          

            
rustPin 的基本用法Playground ↗

            
use std::pin::Pin;

fn main() {
    let value = String::from("pinned");
    let pinned: Pin<&String> = Pin::new(&value);
    println!("{}", pinned.len());
}

          

          

            
如果你来自 C++/Python

            

              
C++移动构造可能让对象地址变化；自引用类型需要特殊处理。Pin 把“地址稳定”变成类型层面的承诺，而不是口头约定。

              
Python对象地址由运行时管理，自引用很常见；Rust 没有移动 GC，Future 需要 Pin 保证状态机地址稳定。

              
Rust业务代码优先避免自引用；async 代码让运行时处理 Pin；只有手写 Future/底层库时才深入 Pin 投影。

            

          

          
底层原理Pin<P> 通过类型系统限制对 P 的可变访问：如果 P: !Unpin，不能安全地拿到 &mut P 并移动它。Unpin 是自动 trait，大多数类型都实现它；async 状态机通常不实现。

          
常见坑
  • 以为 Pin 能阻止所有移动；Unpin 类型仍可移动。
  • 手写自引用结构却不使用 Pin，得到悬垂指针。
  • 在 async 代码里手动 mem::swap 被 pin 的值；编译器会阻止安全代码这样做。

        

      


      

        

          
Part 5 · Data Modeling

          
结构体、枚举、Trait 与泛型：用类型建模

          
Rust 没有类和继承的层级，而是用 struct/enum 建模数据，用 trait 建模行为，用泛型与 impl Trait 组合。把“状态”写成 enum，把“能力”写成 trait，通常比继承更清晰。这一部分从 struct 讲到静态/动态分派。

        


        

          
5.1 Struct 与方法

          
struct 定义数据，impl 定义行为；方法接收 &self/&mut self/self，关联函数不带 self。

          
Rust 的 struct 没有继承，字段默认私有（在 module 内可见）。方法通过 impl 块定义；Self 指当前类型。构造器是约定俗成的 new 关联函数，不是语言关键字。&self 借用，&mut self 可变借用，self 拿走所有权。

          

            
ruststruct、impl 与方法Playground ↗

            
struct Point {
    x: f64,
    y: f64,
}

impl Point {
    fn new(x: f64, y: f64) -> Self {
        Self { x, y }
    }

    fn distance(&self, other: &Point) -> f64 {
        ((self.x - other.x).powi(2) + (self.y - other.y).powi(2)).sqrt()
    }
}

fn main() {
    let a = Point::new(0.0, 0.0);
    let b = Point::new(3.0, 4.0);
    println!("{}", a.distance(&b));
}

          

          

            
如果你来自 C++/Python

            

              
C++没有继承、虚析构与构造函数重载；用关联函数/不同名字表达构造方式，用 trait 表达接口。字段默认私有，pub 才对外。

              
Python__init__ 是构造器，self 显式；Rust 的 self 只在方法签名中出现，调用时自动传递。

              
Rust数据与行为分离：struct 只管数据，impl 提供行为；不要为了“面向对象”把所有逻辑塞进一个巨大的 impl。

            

          

          
底层原理struct 的字段布局默认由编译器重排以优化大小/对齐（除非 #[repr(C)]）；方法调用是静态分派到具体类型，trait 方法才可能走 vtable。

          
常见坑
  • 把字段默认当成公开；外部 module 需要 pub。
  • 在方法里用 self 拿走所有权，导致调用方之后无法使用对象。
  • 误以为 new 是语言强制构造器；它只是惯用名。

        


        

          
5.2 Enum 与 Option

          
enum 是带数据的代数数据类型；Option<T> 用 Some/None 取代 null，match 强制处理两种可能。

          
Rust 的 enum 比 C++ 的 enum class 强得多：每个 variant 可以携带不同类型的数据，也可以有命名字段。它与 struct 一起构成“和类型 + 积类型”的建模基础。Option<T> 是标准库 enum；Result<T, E> 也是。使用 enum 建模状态，可以避免“某些字段只在某些状态下有效”的非法状态。

          

            
rust带数据的 enum 与穷尽 matchPlayground ↗

            
enum Shape {
    Circle(f64),
    Rect { w: f64, h: f64 },
}

fn area(shape: &Shape) -> f64 {
    match shape {
        Shape::Circle(r) => std::f64::consts::PI * r * r,
        Shape::Rect { w, h } => w * h,
    }
}

fn main() {
    println!("{}", area(&Shape::Circle(1.0)));
    println!("{}", area(&Shape::Rect { w: 2.0, h: 3.0 }));
    let maybe: Option<i32> = Some(3);
    if let Some(n) = maybe {
        println!("{n}");
    }
}

          

          

            
如果你来自 C++/Python

            

              
C++std::variant 是最近的对应物；Rust enum 的匹配更直接，且编译器检查穷尽性。没有 null，空值用 Option。

              
Python你会用 None 或类层级表达状态；Rust 的 enum + match 把“所有状态”写进类型，避免漏分支。

              
Rust“状态 + 数据”用 enum；不要用一堆 bool/可空字段模拟状态机；Option 只表示“有/无”，不表示“错误”。

            

          

          
底层原理enum 的 variant 共享同一块存储（union + 判别标签），大小由最大 variant 决定；Option<T> 对非空指针类型可能利用无效位优化（niche optimization），因此 Option<&T> 通常与 &T 同大小。

          
常见坑
  • 用 None 表示错误；错误用 Result。
  • 漏掉 enum 的新 variant；match 会强制你处理。
  • 用多个 bool 字段表达互斥状态，产生非法组合。

        


        

          
5.3 Trait

          
trait 定义共享行为；实现者可以提供方法，trait 也可以提供默认实现；trait bound 约束泛型。

          
trait 类似 C++ 的抽象基类/概念、Python 的 Protocol，但它是静态分派与动态分派的共同基础。trait 可以有默认方法、关联类型、常量、supertrait 约束；实现 trait 需要满足孤儿规则（trait 或类型至少一个属于当前 crate）。trait 也可以作为函数参数 impl Trait 或 trait object dyn Trait。

          

            
rusttrait 与默认方法Playground ↗

            
trait Describable {
    fn name(&self) -> String;

    fn describe(&self) -> String {
        format!("I am {}", self.name())
    }
}

struct User {
    name: String,
}

impl Describable for User {
    fn name(&self) -> String {
        self.name.clone()
    }
}

fn main() {
    let u = User { name: "Ada".into() };
    println!("{}", u.describe());
}

          

          

            
如果你来自 C++/Python

            

              
C++trait 类似纯虚基类 + 模板约束；但没有继承层级，trait 可以为零成本地组合。trait object 才需要 vtable。

              
Python鸭子类型不需要显式实现；Rust 要求显式 impl Trait for Type，换来编译期检查与更好的错误信息。

              
Rust“能力”用 trait，“数据”用 struct/enum；trait 尽量小而聚焦；公共 trait 注意 semver，新增必需方法会破坏实现者。

            

          

          
底层原理trait 定义了一组方法的契约；泛型使用 trait bound 时在编译期单态化，dyn Trait 使用 vtable 在运行时查找方法。默认方法在 trait 中提供实现，实现者可以覆盖。

          
常见坑
  • trait 方法返回 Self 或泛型参数，导致无法作为 trait object。
  • 公共 trait 新增必需方法，破坏所有下游实现。
  • 为了一点点复用建巨大 trait；优先小 trait + 组合。

        


        

          
5.4 泛型与单态化

          
泛型让代码对多种类型复用，trait bound 约束能力；Rust 默认单态化，为每种具体类型生成一份代码。

          
泛型函数/struct/enum 用 <T> 声明类型参数，用 T: Trait 或 where 约束能力。单态化意味着零运行时开销，但会增加编译时间与二进制体积；dyn Trait 则相反。const generics 用常量作为泛型参数（如固定长度数组）；GAT 允许 trait 的关联类型带生命周期/类型参数。

          

            
rust泛型函数与 trait boundPlayground ↗

            
fn largest<T: PartialOrd + Copy>(items: &[T]) -> Option<T> {
    let mut iter = items.iter();
    let mut max = *iter.next()?;
    for &item in iter {
        if item > max {
            max = item;
        }
    }
    Some(max)
}

fn main() {
    println!("{:?}", largest(&[3, 1, 4, 1, 5]));
    println!("{:?}", largest(&['a', 'z', 'm']));
}

C++模板在编译期实例化，错误信息可能很长；Rust 泛型也单态化，但 trait bound 让约束更明确、错误更可读。

5.5 常用标准 trait 与 derive

          
Debug/Display 管输出，Clone/Copy 管复制，PartialEq/Eq/Hash 管比较与哈希，Default/From/Into 管转换。

          
#[derive(...)] 可以为常见 trait 生成实现；Debug 用于调试输出，Display 需要手写格式化。PartialEq 允许浮点等不完全等价，Eq 要求全等价；Hash 与 Eq 必须一致。From/Into 是转换 trait，? 依赖 From 做错误转换。

          

            
rustderive 常用 traitPlayground ↗

            
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
struct UserId(u64);

fn main() {
    let a = UserId(7);
    let b = a.clone();
    println!("{a:?} {} {:?}", a == b, a);
}

          

          

            
如果你来自 C++/Python

            

              
C++Debug 类似调试打印，Clone 类似拷贝构造，PartialEq/Hash 类似 operator==/std::hash；derive 省去样板代码。

              
Pythondataclass 也会生成 __repr__/__eq__；Rust 的 derive 是编译期生成，且可以精确控制实现哪些 trait。

              
Rust值对象优先 derive Debug, Clone, PartialEq, Eq, Hash；需要自定义输出时手写 Display；不要给含可变字段的类型 derive Hash 后又在集合中修改。

            

          

          
底层原理derive 是过程宏，在编译期生成 impl 代码；Hash 与 Eq 必须满足“相等对象哈希相同”，否则 HashMap/HashSet 行为错误。Display 不能 derive，需要手写。

          
常见坑
  • 对含 f64 的类型 derive Eq/Hash；浮点不满足全等价。
  • 只 derive PartialEq 不 derive Hash，在需要哈希的集合中不可用。
  • 用 Clone 代替借用，造成不必要的深拷贝。

        


        

          
5.6 静态分派 vs 动态分派

          
impl Trait/泛型在编译期单态化，dyn Trait 在运行时通过 vtable 分派；前者快、后者灵活。

          
泛型参数和 impl Trait 是静态分派：编译器知道具体类型，可以内联。trait object &dyn Trait/Box<dyn Trait> 是动态分派：值携带一个指向 vtable 的指针，可以在一个集合中存放不同具体类型。trait 必须对象安全（object-safe）才能作为 trait object：方法不能返回 Self、不能有泛型参数、不能有 where Self: Sized 的约束等。

          

            
rust同一 trait 的两种分派Playground ↗

            
trait Speak {
    fn speak(&self) -> &'static str;
}

struct Dog;
impl Speak for Dog {
    fn speak(&self) -> &'static str { "woof" }
}
struct Cat;
impl Speak for Cat {
    fn speak(&self) -> &'static str { "meow" }
}

fn static_speak<T: Speak>(animal: &T) -> &'static str {
    animal.speak()
}
fn dynamic_speak(animal: &dyn Speak) -> &'static str {
    animal.speak()
}

fn main() {
    let dog = Dog;
    println!("{} {}", static_speak(&dog), dynamic_speak(&dog));
    let animals: Vec<Box<dyn Speak>> = vec![Box::new(Dog), Box::new(Cat)];
    for a in &animals {
        println!("{}", a.speak());
    }
}

          

          

            
如果你来自 C++/Python

            

              
C++虚函数 + vtable 接近 dyn Trait；模板 + concepts 接近泛型单态化。Rust 没有继承，但可以用 trait object 实现运行时多态。

              
Python所有方法调用都是动态查找，接近 dyn Trait；Rust 的泛型可以在编译期消除分派开销。

              
Rust性能敏感/单类型用泛型；需要异构集合/插件式扩展用 dyn Trait；trait object 需要对象安全。

            

          

          
底层原理dyn Trait 是胖指针：数据指针 + vtable 指针；vtable 按具体类型生成，包含方法地址、大小、对齐与 drop。泛型单态化则把具体类型代入生成专用代码，没有运行时 vtable。

          
常见坑
  • 把带泛型方法/返回 Self 的 trait 当 trait object 用；对象安全不满足。
  • 为每个小函数都用 dyn，牺牲内联与性能。
  • 在 Vec<Box<dyn Trait>> 中频繁分配；考虑 enum 或泛型容器。

6.1 Option、Result 与 ?

          
Option<T> 表示“有/无”，Result<T, E> 表示“成功/失败”；? 在失败时提前返回，并用 From 转换错误。

          
Rust 没有异常作为常规控制流；可恢复错误用 Result，不可恢复/程序错误用 panic!。? 只能用在返回 Result（或 Option）的函数中；它把 Err(e) 转换为 return Err(From::from(e))。这让错误传播显式但不冗长。

          

            
rust用 ? 传播解析错误Playground ↗

            
use std::num::ParseIntError;

fn parse_pair(a: &str, b: &str) -> Result<(u16, u16), ParseIntError> {
    let a = a.parse::<u16>()?;
    let b = b.parse::<u16>()?;
    Ok((a, b))
}

fn main() {
    println!("{:?}", parse_pair("80", "443"));
    println!("{:?}", parse_pair("80", "nope"));
}

如果你来自 C++/Python

            

              
C++Result 类似 std::expected；Rust 的 ? 是语法糖，自动传播错误并转换类型，不需要手动检查每个返回值。

              
Python异常会隐式向上传播；Rust 的 ? 只传播到函数边界，调用方必须显式处理或在签名里声明 Result。

              
Rust库代码优先返回 Result；main 可以返回 Result<(), E>；unwrap 只适合示例/测试/确实不可恢复的场景。

            

          

          
底层原理Result<T, E> 是 enum，成功与错误共用一块存储；? 展开为 match，遇到 Err 立即返回并调用 From::from 转换错误。没有异常表/栈展开开销（panic 例外）。

          
常见坑
  • 在返回 () 的函数里用 ?；需要改返回类型。
  • 用 unwrap() 处理可恢复错误，导致调用方无法恢复。
  • 忽略 Result 的 #[must_use]；编译器会警告。

        


        

          
6.2 自定义错误

          
库代码用枚举错误 + std::error::Error 表达可匹配的失败；应用代码可以用 anyhow 添加上下文。

          
自定义错误枚举让调用方可以 match 具体失败原因；实现 Display、Error、From 后，? 可以自动转换。生态里常用 thiserror 生成样板，anyhow 处理应用层错误链；库的公共 API 尽量返回具体错误类型，应用层再统一包装。

          

            
rust枚举错误与 From 转换Playground ↗

            
use std::fmt;

#[derive(Debug)]
enum AppError {
    Parse(std::num::ParseIntError),
    Empty,
}

impl From<std::num::ParseIntError> for AppError {
    fn from(e: std::num::ParseIntError) -> Self {
        AppError::Parse(e)
    }
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            AppError::Parse(e) => write!(f, "parse error: {e}"),
            AppError::Empty => write!(f, "empty input"),
        }
    }
}

impl std::error::Error for AppError {}

fn read_port(s: &str) -> Result<u16, AppError> {
    if s.is_empty() {
        return Err(AppError::Empty);
    }
    Ok(s.parse::<u16>()?)
}

fn main() {
    for input in ["80", "", "nope"] {
        match read_port(input) {
            Ok(port) => println!("{input}: {port}"),
            Err(err) => println!("{input}: {err}"),
        }
    }
}

          

          

            
如果你来自 C++/Python

            

              
C++自定义异常类接近自定义错误 enum；Rust 的错误是值，可以 match、组合、在签名中声明。thiserror 类似手写异常类的模板。

              
Python异常层级 + raise ... from ... 提供因果链；Rust 的 source() 与 anyhow::Context 提供类似能力。

              
Rust库 API 用具体错误 enum；应用层用 anyhow/eyre 加 context；不要把所有错误都变成 String。

            

          

          
底层原理std::error::Error 提供 source() 返回错误链；? 通过 From 转换错误类型。错误 enum 的每个 variant 可以携带底层错误，调用方可以选择 match 或统一上报。

          
常见坑
  • 公共 API 返回 Box<dyn Error>，调用方无法 match 具体错误。
  • 忘记实现 Display/Error，导致 ? 或日志不可读。
  • 用 String 作为库错误类型，丢失结构化信息。

        


        

          
6.3 集合

          
Vec 是可变长数组，HashMap 是哈希表，BTreeMap 保持键有序；集合拥有其元素。

          
常用集合：Vec<T>、VecDeque<T>、HashMap<K, V>、BTreeMap<K, V>、HashSet<T>、BTreeSet<T>。HashMap 的迭代顺序不确定；需要有序输出用 BTreeMap 或先排序。entry API 可以避免重复查找与插入。Vec::with_capacity 预分配容量，减少扩容。

          

            
rustHashMap 的 entry API 与 VecPlayground ↗

            
use std::collections::HashMap;

fn main() {
    let mut scores = HashMap::new();
    scores.insert("Ada", 100);
    scores.entry("Grace").or_insert(90);
    *scores.entry("Ada").or_insert(0) += 5;

    let names: Vec<&str> = scores.keys().copied().collect();
    println!("{names:?}");

    let mut v = vec![1, 2, 3];
    v.push(4);
    println!("{v:?}");
}

          

          

            
如果你来自 C++/Python

            

              
C++Vec 类似 std::vector，HashMap 类似 unordered_map，BTreeMap 类似 std::map；Rust 的借用检查会影响“边遍历边修改”的写法。

              
Pythondict 保持插入顺序，Rust 的 HashMap 不保证；需要稳定顺序用 BTreeMap 或 IndexMap。

              
Rust预先 with_capacity；用 entry API 做“存在则更新/不存在则插入”；遍历时修改集合前先确认借用规则。

            

          

          
底层原理Vec 是连续内存 + 长度/容量；扩容会重新分配并移动元素。HashMap 使用哈希与开放寻址/链地址（具体实现随版本），默认哈希器有随机种子以抵抗 HashDoS；BTreeMap 用 B 树保持有序。

          
常见坑
  • 依赖 HashMap 的迭代顺序；它不保证。
  • 在遍历 Vec 时删除元素；借用检查会阻止或需要索引技巧。
  • 用 Vec::new 后大量 push 却不预分配；考虑 with_capacity。

        


        

          
6.4 迭代器

          
迭代器是惰性的：适配器只描述计算，collect/sum/for 等消费者才真正驱动。

          
iter() 借用元素，iter_mut() 可变借用，into_iter() 拿走所有权。map/filter/take/skip/flat_map 等是惰性适配器；collect/fold/sum/for_each 才会消费迭代器。自定义类型实现 Iterator 即可接入这套生态。

          

            
rust惰性适配器与 collectPlayground ↗

            
fn main() {
    let nums = [1, 2, 3, 4];
    let doubled: Vec<i32> = nums
        .iter()
        .filter(|&&n| n % 2 == 0)
        .map(|&n| n * 10)
        .collect();
    let sum: i32 = nums.iter().sum();

    println!("{doubled:?} {sum}");

    let joined = ["a", "b"]
        .iter()
        .map(|w| w.to_uppercase())
        .collect::<Vec<_>>()
        .join("-");
    println!("{joined}");
}

Python生成器表达式是惰性的；Rust 的 map/filter 也是惰性的，但类型系统会跟踪元素类型，collect 需要目标类型。

6.5 闭包

          
闭包按捕获方式实现 Fn/FnMut/FnOnce；move 强制按值捕获，常与线程一起使用。

          
闭包捕获环境的方式由使用方式决定：只读借用实现 Fn，可变借用实现 FnMut，拿走所有权实现 FnOnce。move 让闭包按值捕获，用于 thread::spawn 等需要 'static 的场景。闭包作为参数时用 impl Fn(...) 或泛型 F: Fn(...)；返回闭包时用 impl Fn(...) 或 Box<dyn Fn(...)>。

          

            
rust闭包捕获与 FnMutPlayground ↗

            
fn apply<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 {
    f(x)
}

fn main() {
    let add = 10;
    let f = |x| x + add;
    println!("{}", apply(f, 5));

    let mut count = 0;
    let mut inc = || count += 1;
    inc();
    println!("{count}");
}

          

          

            
如果你来自 C++/Python

            

              
C++lambda 的捕获列表（[=]/[&]）由你显式选择；Rust 根据使用方式推断 Fn trait，move 强制按值捕获。

              
Python闭包捕获变量（晚绑定），没有 Fn trait 区分；Rust 的 FnOnce 会在闭包消耗捕获值时限制调用次数。

              
Rust需要跨线程时用 move；需要多次调用且修改状态时用 FnMut；需要返回闭包时用 impl Fn/Box<dyn Fn>。

            

          

          
底层原理闭包是实现了 Fn/FnMut/FnOnce 的匿名类型，捕获的变量成为它的字段。FnOnce 可以消耗捕获值，FnMut 可以可变借用，Fn 只读借用；编译器根据调用方式选择最宽松的 trait。

          
常见坑
  • 在线程闭包里忘记 move，借用无法跨线程存活。
  • 闭包捕获了 &mut 后又在外部使用同一个变量。
  • 返回捕获局部引用的闭包；需要 move 或拥有数据。

        

      


      

        

          
Part 7 · Concurrency

          
并发：用类型系统排除数据竞争

          
Rust 的并发不是“更安全的锁”，而是把所有权、借用与 Send/Sync 组合起来，让数据竞争在编译期无法通过。这一部分从线程讲到通道、rayon 与线程/async 的分工。

        


        

          
7.1 线程

          
thread::spawn 创建线程，join 等待结束；闭包通常需要 move 把数据所有权带入线程。

          
Rust 的标准线程是 OS 线程。闭包默认借用环境，但线程可能比创建它的栈帧活得更久，因此需要 move 把捕获的值移入闭包。join 返回 Result<T, Box<dyn Any + Send>>，线程 panic 会被捕获为 Err。scoped threads（thread::scope）允许借用局部数据，因为作用域会等待所有线程结束。

          

            
rustspawn、move 与 joinPlayground ↗

            
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("worker {i}");
            thread::sleep(Duration::from_millis(10));
        }
    });
    handle.join().unwrap();
    println!("main done");
}

          

          

            
如果你来自 C++/Python

            

              
C++std::thread 需要显式 join/detach；Rust 的 JoinHandle 也是，但所有权检查会阻止闭包借用短命数据。

              
Python线程默认共享所有对象；Rust 的 move 决定哪些值进入线程，Send/Sync 决定能否跨线程。

              
Rust需要共享状态时用 Arc + 锁/通道；能 move 就 move，减少共享；scoped threads 适合“线程只活在一个作用域内”的场景。

            

          

          
底层原理线程闭包必须满足 Send，且通常需要 'static；move 把捕获值移入闭包，保证线程拥有数据。OS 线程由标准库创建，panic 会展开到线程边界并被 join 捕获。

          
常见坑
  • 忘记 move，闭包借用局部变量导致生命周期错误。
  • 忽略 join 的结果，线程 panic 被静默吞掉。
  • 用共享可变全局状态；优先通道或 Arc<Mutex<T>>。

        


        

          
7.2 共享状态

          
Arc<Mutex<T>> 是跨线程共享可变状态的标准组合：Arc 管所有权，Mutex 管互斥访问。

          
Arc 提供线程安全的引用计数，Mutex 提供互斥锁；lock() 返回 MutexGuard，离开作用域自动释放。锁可能中毒（持锁线程 panic），也可以选择忽略中毒。多个锁要避免死锁：固定加锁顺序、缩小临界区、考虑 RwLock 或无锁结构。

          

            
rustArc<Mutex<T>> 与多线程计数Playground ↗

            
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];
    for _ in 0..4 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            let mut n = counter.lock().unwrap();
            *n += 1;
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("{}", *counter.lock().unwrap());
}

          

          

            
如果你来自 C++/Python

            

              
C++std::shared_ptr<std::mutex> + lock guard 类似；Rust 把“共享所有权”和“互斥”拆成两个类型，组合显式。

              
PythonGIL 保护字节码，但复合操作仍需锁；Rust 的 Mutex 保护数据本身，类型系统确保访问必须持锁。

              
RustArc<Mutex<T>> 只保护锁内数据；锁外仍要通过 guard 访问。临界区尽量短，避免在锁内做 I/O。

            

          

          
底层原理MutexGuard 持有锁并在 Drop 时释放；Mutex 中毒表示持锁线程 panic，数据可能不一致。Rust 的 Mutex 不是重入锁，重复加锁会死锁。

          
常见坑
  • 在同一线程重复 lock()；非重入锁会死锁。
  • 锁内执行慢操作/await；扩大临界区并可能阻塞。
  • 多个锁顺序不一致；死锁风险。

        


        

          
7.3 通道

          
通道把“共享内存 + 锁”换成“消息 + 所有权转移”；mpsc 是多生产者单消费者。

          
std::sync::mpsc::channel 提供多生产者、单消费者通道；发送 send 会移动值，接收 recv 阻塞等待，try_recv 非阻塞。通道适合任务分发、日志、解耦；需要多消费者或更强功能时用 crossbeam-channel、Tokio mpsc 等。

          

            
rustmpsc 通道与所有权转移Playground ↗

            
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    thread::spawn(move || {
        for i in 1..=3 {
            tx.send(i).unwrap();
        }
    });
    for value in rx {
        println!("{value}");
    }
}

Pythonqueue.Queue 共享对象；Rust 的通道更强调“消息拥有数据”，减少共享可变状态。

              
Rust能用通道就不用共享锁；通道天然串行化访问，但要注意背压与关闭语义。

            

          

          
底层原理通道内部是队列 + 同步原语；send 可能阻塞（有界通道），recv 在无消息时阻塞。发送值会移动所有权；所有发送端 drop 后，接收端迭代结束。

          
常见坑
  • 忘记 drop 发送端，接收端迭代永不结束。
  • 无界通道堆积大量消息，内存上涨；需要背压。
  • 在通道消息里传共享引用；改为传拥有所有权的值。

        


        

          
7.4 数据并行

          
rayon 把顺序迭代器变成并行迭代器；它适合纯 CPU、可独立分片的数据处理。

          
rayon::prelude::* 提供 par_iter/into_par_iter，内部使用工作窃取线程池。数据并行要求任务之间没有共享可变状态，或者共享部分用锁/原子保护。I/O 密集任务不适合 rayon；异步 I/O 用 Tokio。

          

            
rustrayon 并行求和（需外部 crate）需 rayon

            
use rayon::prelude::*;

fn main() {
    let sum: i64 = (1..=1_000_000).into_par_iter().sum();
    println!("{sum}");
}

          

          

            
如果你来自 C++/Python

            

              
C++OpenMP/TBB 的并行循环类似；rayon 用迭代器表达并行，自动分片与工作窃取。

              
Pythonmultiprocessing 绕开 GIL；rayon 在线程内并行，要求任务可 Send/Sync。

              
Rust先确认是 CPU 密集且可分片；小任务/共享写多的场景可能不如串行。

            

          

          
底层原理rayon 维护一个工作窃取线程池；par_iter 把数据分片，任务在本地队列执行，空闲线程从其他队列窃取。共享可变状态仍需 Mutex/原子。

          
常见坑
  • 在并行闭包里修改同一个 Vec；需要分片或锁。
  • 把小任务放进 rayon，线程调度开销超过收益。
  • 用 rayon 做阻塞 I/O；线程池被占满。

        


        

          
7.5 Send、Sync 与线程/async 分工

          
Send 表示值可以跨线程转移，Sync 表示 &T 可以跨线程共享；它们是自动 trait，由字段类型决定。

          
Rc/RefCell 不是 Sync，不能跨线程；Arc/Mutex 通常是。编译器在 thread::spawn 或 tokio::spawn 时检查 Future/闭包是否 Send，因此跨 await 持有 MutexGuard 常导致编译错误。CPU 密集用线程/rayon 等并行方案，I/O 密集用 async。

          

            
rustRc 不能跨线程（编译错误示意）Playground ↗

            
use std::rc::Rc;

fn main() {
    let rc = Rc::new(1);
    // std::thread::spawn(move || println!("{rc}")); // Rc 不是 Send
    println!("{}", rc);
}

          

          

            

              
任务推荐原因

              
                
CPU 密集、可分片线程/rayon真正并行，减少墙钟时间

                
I/O 密集async/await等待时不占线程

                
共享可变状态Arc<Mutex<T>>显式锁与所有权

                
任务分发通道消息传递，解耦生产/消费

              
            

          

          

            
如果你来自 C++/Python

            

              
C++C++ 线程默认共享内存；Rust 用 Send/Sync 把“能否跨线程”变成编译期约束。

              
PythonGIL 让线程不能并行执行 Python 字节码；Rust 线程真正并行，但数据竞争由类型系统排除。

              
RustI/O 用 async，CPU 用线程/rayon；共享用锁，通信用通道；不要用 async 包装 CPU 循环。

            

          

          
底层原理Send/Sync 是 auto trait：编译器根据字段自动推导。一个类型不是 Send，通常是因为内部有 Rc、裸指针或线程本地状态。Arc<T> 只有在 T: Send + Sync 时才是 Send + Sync。

          
常见坑
  • 在 tokio::spawn 的 Future 里跨 await 持有 std::sync::MutexGuard。
  • 用 Rc 共享跨线程数据；改用 Arc。
  • 用线程池跑阻塞 I/O，耗尽工作线程。

        

      


      

        

          
Part 8 · Async Rust

          
Async Rust：惰性 Future 与运行时

          
Rust 的 async 不是“内置线程池”：标准库只提供 Future 抽象，执行器由运行时提供。理解 poll/Waker、Pin 与运行时边界，才能避免“async 里阻塞”“跨 await 持锁”等常见问题。这一部分以 Tokio 为主线。

        


        

          
8.1 Future 与 poll

          
Future 是惰性的状态机：执行器调用 poll，返回 Pending 时注册 Waker，就绪后再次 poll 返回 Ready。

          
async fn/async 块会被编译器转换为实现 Future 的状态机。poll 的 Pin<&mut Self> 保证状态机地址稳定；Context 携带 Waker，用于在 I/O 就绪时唤醒任务。标准库没有执行器，只有 Future trait 与 Waker 基础设施；Tokio、async-std 等运行时提供执行器与 reactor。

          

            
rust手写一个立即就绪的 FuturePlayground ↗

            
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct Ready(i32);

impl Future for Ready {
    type Output = i32;

    fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<i32> {
        Poll::Ready(self.0)
    }
}

fn main() {
    let mut f = std::pin::pin!(Ready(7));
    let waker = std::task::Waker::noop();
    let mut cx = Context::from_waker(waker);
    println!("{:?}", f.as_mut().poll(&mut cx));
}

如果你来自 C++/Python

            

              
C++C++ 协程也把状态机交给编译器，但执行器/调度由库/框架决定；Rust 的 Future 同样不包含运行时。

              
Pythonasyncio 自带事件循环；Rust 的 Future 只是契约，执行器由 Tokio 等 crate 提供。async 函数调用不会立即执行到完成，但会在第一次 poll 前保持惰性。

              
Rust理解 poll/Pending/Waker 之后，再看 Tokio 的 spawn/select!/timeout 就不会觉得是魔法。

            

          

          
底层原理Future 的 poll 可能被多次调用；返回 Pending 前必须注册 Waker，保证 I/O 就绪时能唤醒执行器。任务被唤醒后重新进入执行器队列，再次 poll 直到 Ready。

          
常见坑
  • 在 poll 里阻塞线程；会卡住整个执行器线程。
  • 返回 Pending 却没注册 Waker；任务永远不再被唤醒。
  • 以为 Future 创建即执行；Rust Future 是惰性的，必须被 poll/spawn。

        


        

          
8.2 Tokio 运行时

          
Tokio 提供执行器、定时器与异步 I/O；#[tokio::main] 启动运行时，tokio::spawn 创建任务。

          
Tokio 有单线程与多线程运行时；网络服务通常用多线程运行时。任务由 Tokio 调度，JoinHandle 等待结果。I/O 驱动（reactor）负责把 epoll/kqueue/IOCP 事件转成 Waker 唤醒。Tokio 不是标准库的一部分，需要显式依赖。

          

            
rustTokio spawn 与 JoinHandle（需 tokio）需 Tokio

            
#[tokio::main]
async fn main() {
    let handle = tokio::spawn(async { 42 });
    println!("{}", handle.await.unwrap());
}

          

          

            
如果你来自 C++/Python

            

              
C++你可能用 asio/executor 或自建事件循环；Tokio 提供电池齐全的运行时，但把运行时选择带进了项目。

              
Pythonasyncio.run 类似 #[tokio::main]；但 Rust 的运行时是库，不是语言内置。

              
Rust库代码尽量不绑定具体运行时；应用层选择 Tokio；需要 runtime-agnostic 时只依赖 Future/Stream trait。

            

          

          
底层原理Tokio 多线程运行时由工作窃取调度器、I/O driver、timer driver 组成；被唤醒的任务进入本地/全局队列，由 worker 线程执行。阻塞任务应放到 spawn_blocking。

          
常见坑
  • 在 async 任务里做 CPU 密集计算；阻塞 worker。
  • 用 std::thread::sleep；应使用 tokio::time::sleep。
  • 在库代码里硬编码 #[tokio::main]；库应只返回 Future。

        


        

          
8.3 异步 I/O、超时与取消

          
timeout/select!/join! 组合异步任务；取消是“丢弃 Future”，但要注意取消安全。

          
Tokio 的 timeout 返回 Result<T, Elapsed>，超时后丢弃内部 Future；select! 等待多个分支中第一个完成；join! 等待全部完成。取消安全意味着 Future 在任意 await 点被丢弃不会留下不一致状态；并非所有 Future 都取消安全（如部分 I/O 操作）。

          

            
rust超时示例（需 tokio）需 Tokio

            
use std::time::Duration;
use tokio::time::{sleep, timeout};

#[tokio::main]
async fn main() {
    let result = timeout(Duration::from_millis(10), sleep(Duration::from_millis(100))).await;
    println!("timed out: {}", result.is_err());
}

          

          

            
如果你来自 C++/Python

            

              
C++你会用 timer/asio 的 cancel；Rust 的取消通常通过 drop Future 实现，必须确认取消安全。

              
Pythonasyncio.wait_for 会取消协程；Rust 的 timeout 丢弃 Future，底层操作是否停止取决于实现。

              
Rust用 select! 处理竞速；用 timeout 限制等待；对关键 I/O 检查取消安全，避免半完成状态。

            

          

          
底层原理select! 轮询多个 Future，哪个先返回 Ready 就执行对应分支；未选中的 Future 被丢弃。取消安全取决于 Drop 时能否保持状态一致；Tokio 的部分操作（如 AsyncReadExt::read）是取消安全的。

          
常见坑
  • 假设 timeout 会停止底层网络请求；它只是丢弃 Future。
  • 在 select! 分支里持有锁；取消时锁的释放顺序复杂。
  • 忽略取消安全，导致部分写入/重复消费。

        


        

          
8.4 Stream

          
Stream 是异步版的 Iterator：一次可能返回 Pending，被唤醒后继续产出 Some(item)，结束时返回 None。

          
futures::Stream/tokio_stream::Stream 提供异步序列抽象；StreamExt 提供 map/filter/next/for_each 等组合器。与 Iterator 不同，next() 是 async 的；需要 while let Some(item) = stream.next().await。背压由消费者是否继续 poll 决定；有界通道/流控可防止生产过快。

          

            
rustStream 组合器（需 futures + tokio）需 futures

            
use futures::stream::{self, StreamExt};

#[tokio::main]
async fn main() {
    let sum: i32 = stream::iter(1..=5)
        .map(|n| n * 2)
        .fold(0, |acc, n| async move { acc + n })
        .await;
    println!("{sum}");
}

          

          

            
如果你来自 C++/Python

            

              
C++异步生成器/回调流类似；Rust 的 Stream 把 poll_next 与 Waker 组合成可组合的异步序列。

              
Pythonasync for 异步迭代器类似；Rust 的 Stream 需要运行时驱动，组合器来自 futures/tokio-stream。

              
Rust事件流/分页/WebSocket 适合 Stream；单值用 Future；需要背压时用有界通道或流控。

            

          

          
底层原理Stream 的 poll_next 返回 Poll<Option<Item>>；Pending 时注册 Waker，Ready(Some) 产出一个元素，Ready(None) 结束。组合器包装上游 Stream，按需 poll。

          
常见坑
  • 把 Iterator 的组合器直接用于 Stream；需要 async 版本。
  • 忘记处理流结束/错误；用 while let Some + 错误分支。
  • 生产速度远高于消费，导致无界缓冲。

        


        

          
8.5 常见坑

          
Async Rust 最容易踩的四个坑：跨 await 持锁、Future 不 Send、async 里阻塞、忽略 Pin/取消安全。

          
    
            
  • 跨 await 持锁：std::sync::MutexGuard 不是 Send，在 tokio::spawn 的 Future 里跨 await 会编译失败；缩小锁范围或用 tokio::sync::Mutex。
    • 
            
  • Future 不 Send：捕获了 Rc/RefCell 或非 Send 类型；改用 Arc/Mutex，或在单线程运行时上运行。
    • 
            
  • async 里阻塞：std::fs/CPU 循环/同步锁会阻塞 worker；用 spawn_blocking 或异步 API。
    • 
            
  • Pin/取消安全：手写 Future 需要正确实现 poll；丢弃 Future 前确认状态一致。
    • 
          

          

            
rust跨 await 持锁的编译错误示意（需 tokio）需 Tokio

            
use std::sync::Mutex;
use tokio::time::{sleep, Duration};

#[tokio::main]
async fn main() {
    let m = Mutex::new(0);
    let guard = m.lock().unwrap();
    // sleep(Duration::from_millis(1)).await; // error: guard 不是 Send
    drop(guard);
    sleep(Duration::from_millis(1)).await;
}

          

          

            
如果你来自 C++/Python

            

              
C++协程里跨 suspend 持锁同样危险；Rust 用 Send 检查把一部分问题前移到编译期。

              
Pythonasyncio 里持锁 await 可能导致死锁；Rust 的编译器会阻止 MutexGuard 跨 await（在多线程运行时）。

              
Rust锁内不做 await；用 tokio::sync::Mutex 仅在必须跨 await 持锁时；CPU 任务放 spawn_blocking。

            

          

          
底层原理tokio::spawn 要求 Future: Send + 'static，因为它可能在线程间迁移。跨 await 的局部变量必须能随状态机一起移动；MutexGuard 借用 Mutex 且非 Send，因此不能跨 await 存活。

          
常见坑
  • 用 std::sync::Mutex 跨 await；改用 tokio::sync::Mutex 或缩小范围。
  • 在 async 函数里调用 std::fs::read；用 Tokio 异步文件 API。
  • 把 CPU 密集任务放在 async 任务里；用 spawn_blocking。

        

      


      

        

          
Part 9 · Unsafe, FFI & Macros

          
Unsafe、FFI 与宏：边界上的工具

          
safe Rust 是默认，但系统编程需要和裸指针、C 库、编译期代码生成打交道。unsafe 不是“关闭检查”，而是一份需要证明的安全契约；FFI 与宏都建立在这份契约之上。这一部分只讲边界，不鼓励日常滥用。

        


        

          
9.1 Unsafe Rust

          
unsafe 解锁五种能力，但要求你证明不变量；unsafe 块不会关闭借用检查器，只允许编译器无法验证的操作。

          
unsafe 的五种能力：解引用裸指针、调用 unsafe 函数、访问/修改可变静态量、实现 unsafe trait、访问 union 字段。unsafe 代码必须满足安全契约：指针有效、对齐、不越界、没有数据竞争、别名规则正确。违反契约是未定义行为（UB），不是“可能 panic”。Miri 可以在部分场景下检测 UB。

          

            
rust最小 unsafe：裸指针修改，附安全契约Playground ↗

            
fn main() {
    let mut value = 41;
    let ptr = &mut value as *mut i32;
    // SAFETY: ptr 来自有效引用，且解引用时没有其他引用同时存在。
    unsafe {
        *ptr += 1;
    }
    println!("{value}");
}

          

          

            
如果你来自 C++/Python

            

              
C++你习惯指针与 UB；Rust 把“这段指针操作需要保证什么”显式写成 unsafe 块与安全注释，safe 代码可以依赖 unsafe 库的契约。

              
PythonC 扩展/ctypes 也需要手动管理内存；Rust 的 unsafe 是语言内置的边界标记，Miri 等工具可以检查部分 UB。

              
Rust默认不写 unsafe；需要时把 unsafe 封装在一个小函数里，对外提供 safe API，并用测试/Miri 验证契约。

            

          

          
底层原理safe Rust 的可靠性建立在“所有 unsafe 代码都遵守契约”上；编译器假设没有 UB，从而进行优化。UB 包括悬垂指针、越界、未对齐访问、数据竞争、违反别名规则等。Miri 是解释器，能检测部分 UB，但不是所有平台/FFI 场景都能覆盖。

          
常见坑
  • 把 unsafe 当成“关闭借用检查”；它只解锁特定操作，借用规则仍要遵守。
  • 写 unsafe 却不写安全契约；未来维护者无法判断前提。
  • 让 safe API 暴露未验证的 unsafe 假设；这是健全性漏洞。

        


        

          
9.2 FFI 与 C ABI

          
Rust 没有稳定 ABI；跨语言边界用 C ABI，配合 #[repr(C)]、extern "C" 与明确的所有权协议。

          
Rust 的类型布局默认不保证与 C 兼容；#[repr(C)] 让 struct 按 C 规则布局，extern "C" 指定调用约定。C++ 符号有名称修饰，需要 extern "C" 包装；Python 侧可用 PyO3 生成扩展。跨边界要约定谁分配/释放内存、字符串编码、错误如何返回、panic 不能穿过 FFI 边界。

          

            
rustFFI 声明与 repr(C)（需 C 库，未运行）需 C 库

            
#[repr(C)]
pub struct Point {
    x: f64,
    y: f64,
}

unsafe extern "C" {
    fn c_add(a: i32, b: i32) -> i32;
}

fn main() {
    let point = Point { x: 1.0, y: 2.0 };
    println!("{} {}", point.x, point.y);

    // SAFETY: 假设运行环境提供 c_add，且 C ABI 与签名匹配。
    let sum = unsafe { c_add(2, 3) };
    println!("{sum}");
}

          

          

            
如果你来自 C++/Python

            

              
C++你会用 extern "C" + #[repr(C)] 暴露稳定 C 接口；Rust 的 cxx crate 提供更安全的 C++ 互操作，bindgen 生成 C 绑定。

              
PythonPyO3 把 Rust 暴露为 Python 扩展；也可用 Process/JSON/HTTP 做进程级互操作，边界更松耦合。

              
Rust优先进程/JSON/HTTP 边界；需要性能或共享内存时再上 FFI；C++ 用 cxx，C 用 bindgen，Python 用 PyO3。

            

          

          
底层原理FFI 调用遵循 C ABI：参数寄存器/栈布局、返回值、调用约定由平台定义。Rust 的 extern "C" 生成 C ABI 符号；#[repr(C)] 保证字段布局。panic 跨 FFI 是 UB/未定义行为，需在边界捕获。

          
常见坑
  • 直接链接 C++ 符号；名称修饰导致找不到，需 extern "C"。
  • 让 panic 穿过 extern "C" 边界；用 catch_unwind 或返回错误码。
  • 字符串/内存所有权不清；约定谁分配、谁释放、用什么分配器。

        


        

          
9.3 宏

          
macro_rules! 做语法模板与可变参数，过程宏在编译期生成代码；宏很强，但会降低可读性与错误信息质量。

          
声明宏按 token 树匹配，适合减少重复样板；过程宏分 derive、attribute、function-like 三类，通常放在独立的 proc-macro crate 中，使用 syn/quote 解析与生成代码。宏卫生性（hygiene）减少名字冲突，但不是万能的；宏展开后的错误定位可能变差。

          

            
rustmacro_rules! 的表达式模板Playground ↗

            
macro_rules! square {
    ($x:expr) => {
        $x * $x
    };
}

fn main() {
    let n = 5;
    println!("{}", square!(n + 1));
}

          

          

            
如果你来自 C++/Python

            

              
C++预处理器是文本替换，模板是类型层面的代码生成；Rust 宏在 token/AST 层工作，类型检查仍在展开后进行。

              
Python装饰器/元类在运行时修改行为；Rust 宏在编译期生成代码，不改变运行时模型。

              
Rust能用函数/泛型/trait 解决就不要用宏；宏适合语法级重复、derive、DSL；公共宏要考虑 semver 与错误信息。

            

          

          
底层原理macro_rules! 在解析阶段按 token 树匹配并展开；过程宏是编译期运行的 Rust 程序，输入/输出 TokenStream。宏展开发生在类型检查之前，因此宏本身无法依赖类型信息。

          
常见坑
  • 用 $x:expr 后直接拼接 token，破坏优先级；用括号包住展开结果。
  • 过程宏 crate 与运行时 crate 混在一起；proc-macro crate 不能导出普通运行时项。
  • 宏错误信息难读；提供清晰的 compile_error! 与文档。

        


        

          
9.4 Edition 2024 与安全边界

          
Edition 2024 要求 unsafe extern 显式标记，收紧 static mut；把 unsafe 封装成可审计的小边界，是长期维护的关键。

          

            

              
实践做法工具

              
                
最小化 unsafe把 unsafe 限制在少数函数，外部提供 safe API代码审查、lint

                
写清契约// SAFETY: 说明指针/生命周期/线程前提文档、测试

                
检测 UB对可运行部分跑 Miricargo +nightly miri test

                
FFI 边界catch panic、明确分配器、版本化 C ABIcxx/bindgen/PyO3

                
静态可变优先 OnceLock/Mutex/原子类型标准库

              
            

          

          

            
如果你来自 C++/Python

            

              
C++你会把不安全代码封装在少数模块并写契约；Rust 的 unsafe 块让边界更显眼，Miri 提供额外的 UB 检测。

              
PythonC 扩展同样是 unsafe 边界；Rust 的 FFI 需要显式处理 panic、所有权与字符串编码。

              
Rust安全边界的目标不是“消灭 unsafe”，而是“让 unsafe 可审计、可测试、可替换”。

            

          

          
底层原理Rust 的健全性依赖“safe API 不会让调用方触发 UB”。如果 safe 函数内部有 unsafe，它必须保证所有调用路径都满足 unsafe 契约；否则整个库的 safe 保证失效。

          
常见坑
  • 在 unsafe 块里做太多事，难以审计；拆成最小操作。
  • 用 static mut 做全局缓存；Edition 2024 对引用有更严格限制。
  • 把 Miri 通过当成“绝对安全”；它不覆盖所有平台/FFI。

10.1 Cargo features、workspace 与发布

          
features 是编译期开关，必须可加性组合；workspace 共享 lockfile/target；发布前检查 semver、MSRV 与文档。

          
feature 不应改变公共 API 的语义，只应增加能力；下游可能同时启用多个 feature。可选依赖用 dep: 语法避免隐式 feature。发布 crate 前设置 description/license/repository/readme，跑 cargo package，确保文档与示例可用。

          

            
toml可选依赖与 feature

            
[package]
name = "my_crate"
version = "0.1.0"
edition = "2024"
license = "MIT OR Apache-2.0"

[features]
default = ["json"]
json = ["dep:serde_json"]

[dependencies]
serde_json = { version = "1", optional = true }

          

          

            
如果你来自 C++/Python

            

              
C++CMake options 也影响编译，但 Rust features 会被依赖图统一解析；下游的 feature 选择可能影响你的编译结果。

              
Pythonextras_require 类似 features；Rust 的 feature 是编译期，可能改变代码路径与依赖图。

              
Rustfeature 保持可加性；默认 feature 不要引入沉重依赖；workspace 统一版本与 lint；发布前跑 cargo package。

            

          

          
底层原理Cargo 在依赖图中合并同名 feature（feature unification），因此一个依赖被多个上游启用 feature 时，最终只有并集。feature 不应是互斥的“模式开关”，否则组合会爆炸。

          
常见坑
  • feature 之间互斥；下游同时启用时行为不确定。
  • 默认 feature 引入 tokio/openssl 等重依赖；库应默认轻量。
  • 发布前不改版本号就 breaking change。

        


        

          
10.2 测试与基准

          
单元测试放 #[cfg(test)]，集成测试放 tests/，文档测试写在文档注释里；基准用 criterion，属性测试用 proptest。

          
Rust 的测试是普通函数加 #[test]；cargo test 同时运行单元/集成/文档测试。异步测试需要运行时（如 #[tokio::test]）。基准测试不要用 debug 构建；criterion 提供统计分析。属性测试可以覆盖手工用例想不到的输入。

          

            
rust单元测试与 Result 测试Playground ↗

            
fn parse_port(s: &str) -> Result<u16, std::num::ParseIntError> {
    s.parse()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parses_valid_port() -> Result<(), Box<dyn std::error::Error>> {
        assert_eq!(parse_port("8080")?, 8080);
        Ok(())
    }

    #[test]
    #[should_panic]
    fn panics_on_invalid_port() {
        parse_port("nope").unwrap();
    }
}

fn main() {
    println!("{:?}", parse_port("8080"));
}

          

          

            
如果你来自 C++/Python

            

              
C++GoogleTest/Catch2 的 TEST 对应 #[test]；Rust 的测试运行器内建，不需要额外链接测试框架。

              
Pythonpytest 的 fixture/参数化需要额外模式；Rust 用普通函数/宏/属性测试库实现，测试与代码同 crate 或 tests/。

              
Rust测试公开行为；异步测试用 #[tokio::test]；性能用 release + criterion，不用 Instant::now 手工计时。

            

          

          
底层原理测试 harness 为每个 #[test] 生成测试函数，默认并行运行；--test-threads=1 可串行。文档测试会编译文档注释中的代码，防止示例腐烂。

          
常见坑
  • 在 debug 模式跑基准；优化级别不同。
  • 测试依赖共享全局状态；并行执行时互相干扰。
  • 异步测试忘记运行时；用 #[tokio::test] 或手动 block_on。

        


        

          
10.3 性能与剖析

          
Rust 的零成本抽象不是“自动很快”：分配、锁、I/O 与算法复杂度仍然决定性能；先测量，再优化。

          
release 构建开启优化，debug 构建保留调试信息与溢出检查。性能问题先用 profiler 找热点（perf、cargo flamegraph、pprof），再看分配与锁竞争。常见优化：预分配、避免不必要的 clone、用迭代器/切片、减少动态分派、调整数据结构、使用 #[inline] 前先测量。

          

            
rust预分配容量Playground ↗

            
fn main() {
    let mut v = Vec::with_capacity(1024);
    for i in 0..1024 {
        v.push(i);
    }
    println!("{}", v.len());
}

          

          

            
如果你来自 C++/Python

            

              
C++你会用 perf/VTune 找热点；Rust 的借用/所有权减少了部分运行时检查，但分配、锁与 I/O 仍是主要成本。

              
Python你习惯用 cProfile/py-spy；Rust 用 perf/flamegraph/pprof，release 构建差异很大。

              
Rust先 profile，再改数据布局/分配/锁；避免凭直觉加 unsafe；用 criterion 做稳定基准。

            

          

          
底层原理泛型与迭代器通常被内联与单态化，但动态分派、分配器、缓存局部性、锁竞争仍决定实际性能。LLVM 优化受 debug/release、LTO、codegen-units 等配置影响。

          
常见坑
  • 用 debug 跑基准得出错误结论。
  • 为优化加 unsafe 却没有 profile 证据。
  • 忽略分配器/锁竞争，只盯微观指令数。

Rust 生态已经覆盖 Web、CLI、序列化、异步、WASM 与嵌入式；选库时看维护活跃度、文档、MSRV、license 与 unsafe 使用。

如果你来自 C++/Python

            

              
C++你会组合 Boost/Abseil/框架；Rust 生态更偏向小 crate 组合，Cargo 解析依赖图。

              
Python你习惯“标准库 + PyPI”；Rust 的 std 较小，很多能力在 crates.io，需评估依赖质量。

常见坑
  • 只看下载量，不看维护活跃度与 docs。
  • 引入多个功能重叠的异步运行时；运行时耦合复杂。
  • 忽略依赖中的 unsafe/许可证/供应链风险。

C. 术语表

          
    
            
  • 所有权（ownership）：每个值有唯一所有者，所有者离开作用域时值被 drop。
    • 
            
  • 借用（borrowing）：通过 &T/&mut T 临时访问值，不转移所有权。
    • 
            
  • 生命周期（lifetime）：引用有效的区间；编译器用它证明引用不会悬垂。
    • 
            
  • 移动（move）：把所有权转移给新绑定，原绑定失效。
    • 
            
  • Copy/Clone：Copy 是隐式按位复制；Clone 是显式复制，可能深拷贝。
    • 
            
  • trait：共享行为的契约；可静态单态化或动态分派。
    • 
            
  • 单态化（monomorphization）：为每个具体类型生成专用代码。
    • 
            
  • trait object / dyn：带 vtable 的动态分派值。
    • 
            
  • 对象安全（object safety）：trait 能作为 trait object 使用的条件。
    • 
            
  • coherence/孤儿规则：trait 与类型的实现必须至少一个属于当前 crate。
    • 
            
  • Send/Sync：值能否跨线程转移/共享的 auto trait。
    • 
            
  • Pin：保证值地址稳定的包装，用于自引用 Future。
    • 
            
  • Future/Waker：惰性异步结果与唤醒机制。
    • 
            
  • UB（未定义行为）：违反语言契约后编译器不保证任何行为。
    • 
            
  • Miri：Rust 解释器，用于检测部分 UB。
    • 
            
  • FFI：跨语言调用边界，通常使用 C ABI。
